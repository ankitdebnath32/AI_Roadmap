For backend engineers building agentic GenAI systems

LangChain is a set of composable parts. LangGraph is the state machine that orchestrates them.

Most confusion about these two frameworks comes from learning APIs before learning what problem each layer solves. LangChain gives you standardized interfaces to models, prompts, retrieval, and tools; LangGraph gives you an explicit graph — nodes, edges, and shared state — to control how those parts execute, branch, loop, and pause for a human.

This workbook is architecture-first: every concept gets an explanation of why it exists before any API. Built for a backend engineer's instincts — you already understand interfaces, state machines, and distributed systems; here's how those same ideas show up in an agent framework.

The big picture

The five-stage progression: from a simple chain to a multi-agent system

Every concept in this workbook is a step along one continuous line. Watch what gets ADDED at each stage — that's the actual architectural story, more useful to hold in your head than any individual API.

Stage 1 — Simple chain: fixed, linear, no decisions

One direction, no branching, no memory of past runs. This is LCEL's | pipe operator at its simplest — pure LangChain, no LangGraph needed.

Stage 2 — Tool-calling agent: the LLM now makes a decision

The loop back from tool execution to the LLM is the first real branch point. A plain LCEL chain can't express "maybe loop back" cleanly — this is where LangChain's AgentExecutor historically stepped in, and where LangGraph later became the more explicit way to model it.

Stage 3 — Stateful agent: memory persists across turns

The agent now reads and writes a persistent state object across turns, not just within one call. This is the exact concept LangGraph formalizes into its State — stage 3 is really "stage 2 plus a state object," which is precisely the seam where LangGraph becomes the natural next tool.

Stage 4 — LangGraph workflow: the loop becomes an explicit graph

Nothing conceptually new happened — the loop and the branch from stage 2 are still here. What changed is that they're now EXPLICIT, inspectable graph edges instead of implicit control flow buried inside an executor's internals, which is exactly what makes checkpoints, interrupts, and human-in-the-loop possible in the next topics.

Stage 5 — Multi-agent system: a supervisor routes to specialized workers

Each worker is itself a small graph like stage 4 — a multi-agent system is a graph of graphs. The supervisor's job is purely routing and delegation; it typically holds no domain logic of its own, mirroring an orchestrator/dispatcher service in a microservices architecture.

LC 01 LangChain

What is LangChain?

LangChain is a framework providing standardized interfaces for the building blocks of LLM applications — models, prompts, output parsing, retrieval, and tools — so switching providers or composing pieces doesn't require rewriting integration code each time.

Think of it as an abstraction layer analogous to JDBC: you write against a common interface, and the concrete implementation (OpenAI, Anthropic, a specific vector store) is swappable underneath.

Architecture diagram
Prompt● Model● Output Parser
hello_langchain.py
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")
response = llm.invoke("Explain what LangChain is in one sentence.")
print(response.content)
Real-world use case
Any team building an LLM feature that might need to swap model providers later (cost, latency, compliance) benefits from coding against LangChain's common interfaces rather than a specific vendor SDK directly.
Common mistake
Treating LangChain as "the AI" itself rather than an integration/orchestration layer — it doesn't make the underlying model smarter; it standardizes how you call and compose it with other components.
Exercise
Install langchain-openai and make a single .invoke() call to a chat model, printing just the .content attribute.
Show a solution sketch
pip install langchain-openai, set OPENAI_API_KEY, then instantiate ChatOpenAI(model=...) and call .invoke("your prompt").content — the .content attribute holds the plain text response from the returned message object.
Interview question
How would you describe LangChain to someone who's never used it, using an analogy from backend development?
Show a strong answer
It's like JDBC or a repository interface pattern — a standardized abstraction over a category of external dependency (LLM providers, vector stores, retrievers) so your application code depends on an interface, not a specific vendor's SDK.
LC 02 LangChain

Why LangChain exists

Before frameworks like LangChain, every LLM application reimplemented the same plumbing from scratch: formatting prompts, parsing model output into structured data, chunking documents, and wiring tool calls — each provider's SDK has different method names and response shapes for conceptually identical operations.

LangChain exists to standardize that plumbing once, the same motivation behind ORMs standardizing database access across vendors.

Architecture diagram
Your app code● LangChain interfaces● OpenAI Anthropic Azure OpenAI
swap_providers.py
# Same downstream code works with either provider — only this line changes
from langchain_openai import ChatOpenAI
llm = ChatOpenAI(model="gpt-4o-mini")

# from langchain_anthropic import ChatAnthropic
# llm = ChatAnthropic(model="claude-sonnet-4-5")

response = llm.invoke("What's 2+2?")
Real-world use case
A company evaluating multiple LLM providers for cost, quality, or compliance reasons can swap the underlying model with a one-line change instead of rewriting integration code throughout the application.
Common mistake
Assuming standardization means IDENTICAL behavior across providers — different models still have different strengths, context limits, and quirks. LangChain standardizes the interface, not the model's actual behavior.
Exercise
Write the same simple chain twice, once using ChatOpenAI and once using a different provider's chat model class, keeping everything else identical.
Show a solution sketch
Define the prompt and parser once; only swap the llm variable's class and constructor arguments between runs — everything downstream of llm should require zero changes if you're using the standard Runnable interface correctly.
Interview question
What specific engineering problem does LangChain solve, independent of any particular LLM?
Show a strong answer
It eliminates the need to write bespoke integration code for every combination of model provider, prompt format, output parsing, and tool-calling convention — standardizing these into common interfaces the same way an ORM standardizes database access across different database vendors.
LC 03 LangChain

LangChain architecture

LangChain's architecture is organized in layers: langchain-core (base abstractions — messages, the Runnable interface, prompts), provider-specific integration packages (langchain-openai, langchain-anthropic, etc.), and langchain itself (higher-level chains and legacy agent utilities) — plus the separate but related LangGraph (stateful, graph-based orchestration) and LangSmith (observability).

Nearly everything above langchain-core is built on the Runnable interface, so understanding Runnable is understanding most of LangChain's composability.

Architecture diagram
langchain-core (Runnable, messages)● provider packages● langchain (chains)● LangGraph
layers_in_action.py
from langchain_core.prompts import ChatPromptTemplate   # core abstraction
from langchain_openai import ChatOpenAI                   # provider package
from langchain_core.output_parsers import StrOutputParser # core abstraction

prompt = ChatPromptTemplate.from_template("Summarize: {text}")
llm = ChatOpenAI(model="gpt-4o-mini")
parser = StrOutputParser()

chain = prompt | llm | parser   # each is a Runnable; | composes them
Real-world use case
Knowing this layering matters when debugging import errors or deciding whether a new capability belongs in a custom Runnable vs. reaching for LangGraph — architecture awareness prevents cargo-culting whichever API a blog post happened to use.
Common mistake
Importing from the wrong package — expecting a class in langchain that actually lives in langchain-core or a provider package. The package split has changed across versions, so understanding the LAYER a capability belongs to is more durable than memorizing exact import paths.
Exercise
Identify which package (langchain-core, langchain-openai, langchain, or langgraph) a ChatPromptTemplate, a ChatOpenAI instance, and a StateGraph each belong to.
Show the answer
ChatPromptTemplate → langchain-core. ChatOpenAI → langchain-openai (a provider integration package). StateGraph → langgraph, a separate package entirely from langchain.
Interview question
Why does LangChain split its functionality across multiple packages instead of one monolithic library?
Show a strong answer
Separating core abstractions from provider-specific integrations lets the framework support many providers without forcing every user to install every provider's SDK, and lets each piece version independently — similar to splitting a monolith into libraries with clear dependency boundaries.
LC 04 LangChain

Models

LangChain's model abstraction standardizes calling any LLM provider through the same methods — .invoke(), .stream(), .batch(), and their async equivalents — regardless of whether the underlying model is OpenAI, Anthropic, a local model, or an Azure-hosted deployment.

Chat models take a list of messages and return a message object, not just a raw string — this matters for multi-turn conversations and tool-calling, both of which need more than plain text.

Architecture diagram
Messages in● BaseChatModel● AIMessage out
model_calls.py
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
llm.invoke("Hi")                    # single call
llm.batch(["Hi", "Bye"])            # parallel batch calls
for chunk in llm.stream("Tell me a short story"):
    print(chunk.content, end="")
Real-world use case
Swapping between a cheap/fast model for simple tasks and a more capable model for complex reasoning using the identical .invoke() call signature in both cases, controlled by configuration rather than code changes.
Common mistake
Forgetting that chat models return a message OBJECT (with .content, .tool_calls, .response_metadata) rather than a plain string — code that expects a string from .invoke() will break or need .content appended everywhere.
Exercise
Call the same prompt with .invoke(), .batch() on a list of 3 prompts, and .stream(), printing the differences in what each returns.
Show a solution sketch
.invoke() returns one AIMessage; .batch() returns a list of AIMessages, one per input, run concurrently; .stream() returns an iterator of small message chunks whose .content fields you concatenate to reconstruct the full response as it's generated.
Interview question
Why does LangChain's chat model interface take and return message objects instead of plain strings?
Show a strong answer
Real LLM interactions are multi-turn and richer than plain text — a message carries a role (system/human/AI/tool), can include tool call requests, and preserves metadata (token usage, finish reason) a plain string would discard. Standardizing on messages keeps single-turn and multi-turn code using the same interface.
LC 05 LangChain

Prompts

A prompt in LangChain is the actual formatted input sent to a model — for chat models, a LIST of messages (system, human, AI, tool) rather than a single string, mirroring how you'd construct a request payload for a REST API.

Prompts are the mechanism through which everything else — retrieved context, tool results, conversation history — actually reaches the model.

Architecture diagram
SystemMessage+ HumanMessage● LLM
messages.py
from langchain_core.messages import SystemMessage, HumanMessage

messages = [
    SystemMessage(content="You are a helpful assistant."),
    HumanMessage(content="What is LangChain?"),
]
response = llm.invoke(messages)
Real-world use case
Building a support chatbot's system prompt separately from the per-request user message, so tone and instructions stay consistent while only the user content varies per call.
Common mistake
Hardcoding an entire prompt as one giant string when the underlying model actually expects a structured message list — losing the ability to leverage system-message-specific behavior a provider may implement differently from user turns.
Exercise
Construct a 3-message conversation (system, human, AI) manually using message classes and pass it to a chat model.
Show a solution sketch
Build a list containing SystemMessage, HumanMessage, and AIMessage instances in order, then call llm.invoke(messages) — the existing AI message provides conversational context the model uses when generating its next response.
Interview question
What's the difference between a prompt and a prompt template in LangChain?
Show a strong answer
A prompt is the actual, final list of messages sent to the model for one specific call. A prompt template is a reusable, parameterized blueprint that PRODUCES a prompt when filled with variables — the same relationship as a raw SQL string vs. a parameterized prepared statement.
LC 06 LangChain

Prompt templates

Prompt templates let you define a reusable, parameterized prompt structure once and fill in variables per call, rather than string-formatting prompts by hand throughout your codebase. They also validate that expected variables are provided and support composing multiple message templates together.

Architecture diagram
Template+ Variables● Formatted Messages
prompt_templates.py
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are an expert in {domain}."),
    ("human", "{question}"),
])
formatted = prompt.invoke({"domain": "backend engineering", "question": "What is a message queue?"})
Real-world use case
A single prompt template reused across an entire feature (e.g. a document-summarization endpoint), with the {text} variable populated per request — keeping the prompt's wording centralized and easy to update without touching call sites.
Common mistake
Manually f-string-interpolating user input directly into a prompt without a template — this loses variable validation and increases prompt-injection risk, since there's no structural separation between instructions and data.
Exercise
Build a ChatPromptTemplate with 2 variables and render it with two different sets of inputs, printing the resulting message list each time.
Show a solution sketch
Define the template with placeholders like {domain} and {question}, then call .invoke({...}) twice with different dictionaries — each call returns a distinct, fully-formatted message list ready to send to a model.
Interview question
Why prefer a ChatPromptTemplate over Python f-strings for building prompts?
Show a strong answer
Templates validate that required variables are supplied, keep the prompt structure (system vs. human messages) explicit rather than flattened into one string, and centralize prompt wording so it can be updated or swapped without touching every call site — closer to a templating engine than raw string concatenation.
LC 07 LangChain

Messages

Messages are LangChain's typed representation of one turn in a conversation: SystemMessage (instructions), HumanMessage (user input), AIMessage (model output, possibly with tool_calls), and ToolMessage (a tool's result, tied back to a specific tool call by ID).

This typed structure is what lets multi-turn, tool-using conversations be represented and passed around consistently.

Architecture diagram
HumanMessage● AIMessage(tool_calls)● ToolMessage● AIMessage(final)
message_roundtrip.py
from langchain_core.messages import ToolMessage, HumanMessage

messages = [HumanMessage(content="What's the weather in Paris?")]
ai_msg = llm_with_tools.invoke(messages)   # AIMessage, may include tool_calls
messages.append(ai_msg)

if ai_msg.tool_calls:
    for call in ai_msg.tool_calls:
        result = run_tool(call["name"], call["args"])
        messages.append(ToolMessage(content=str(result), tool_call_id=call["id"]))

final = llm_with_tools.invoke(messages)
Real-world use case
Multi-step tool-calling conversations require appending each message type to a running list in the exact order they occurred, since the model needs the full history including tool results to produce a coherent final answer.
Common mistake
Forgetting to include tool_call_id when constructing a ToolMessage — providers require this to match a tool result back to the specific tool call that requested it, especially when multiple tools are called in parallel.
Exercise
Manually build a 4-message list representing a full tool-call round trip, without actually calling an LLM, just to understand the message shapes.
Show a solution sketch
HumanMessage(question) → AIMessage(content="", tool_calls=[{...}]) → ToolMessage(content=result, tool_call_id=matching_id) → AIMessage(final answer) — construct each directly and print the list to see the exact shape a real conversation accumulates.
Interview question
Why does ToolMessage need a tool_call_id, given the model already knows what tool it asked to call?
Show a strong answer
A single AI turn can request MULTIPLE tool calls in parallel; the tool_call_id disambiguates which result corresponds to which specific request — the same way you'd correlate an async request/response pair by a request ID in a distributed system.
LC 08 LangChain

Structured output

Structured output means getting the model to return data in a specific, validated shape (a Pydantic model or JSON schema) rather than free-form text you'd need to parse yourself. LangChain's .with_structured_output() wraps a model so its response is coerced into and validated against your schema, typically leveraging the provider's native function-calling/JSON-mode under the hood.

Architecture diagram
LLM+ Pydantic Schema● Validated Object
structured_output.py
from pydantic import BaseModel

class Extraction(BaseModel):
    name: str
    age: int

structured_llm = llm.with_structured_output(Extraction)
result = structured_llm.invoke("John is 34 years old.")
print(result.name, result.age)  # a validated Extraction instance, not a string
Real-world use case
Extracting structured fields from unstructured text (e.g. parsing a support ticket into {category, priority, summary}) to feed into a downstream system that expects typed data, not free text.
Common mistake
Assuming structured output is 100% guaranteed to match the schema regardless of provider — it relies on the model's function-calling reliability, which varies by model and weakens with more complex/nested schemas. Always add validation/retry for production use.
Exercise
Define a Pydantic model with 3 fields and use with_structured_output() to extract them from a paragraph of unstructured text.
Show a solution sketch
Define a BaseModel subclass with the 3 typed fields, call llm.with_structured_output(YourModel), and invoke it with the paragraph — the returned object is an instance of YourModel with populated, type-validated fields.
Interview question
How does with_structured_output() actually get an LLM to return valid structured data?
Show a strong answer
It typically uses the provider's native tool-calling or JSON-mode capability — the schema is presented to the model as if it were a tool to call, and the returned arguments are parsed and validated against your Pydantic model, rather than relying on the model to spontaneously format prose as JSON correctly.
LC 09 LangChain

Output parsers

Output parsers convert a raw model response into a more usable Python object — historically LangChain's primary mechanism for structured output before native tool-calling-based structured output became reliable and preferred. Still relevant for parsing plain-text formats that don't need a full schema.

Architecture diagram
AIMessage● Output Parser● Python object
output_parsers.py
from langchain_core.output_parsers import StrOutputParser, JsonOutputParser

parser = StrOutputParser()
chain = prompt | llm | parser          # unwraps AIMessage.content to a plain string

json_parser = JsonOutputParser()
chain2 = prompt | llm | json_parser    # parses model output as JSON
Real-world use case
A simple summarization chain where you just want the plain text summary string, not the full AIMessage object — StrOutputParser is the common final step of nearly every basic LCEL chain.
Common mistake
Reaching for a custom output parser to extract structured JSON when with_structured_output() (backed by tool-calling) would be more reliable — parsing free-text JSON from a model's raw output is more fragile than using the provider's native structured-output mechanism.
Exercise
Build an LCEL chain ending in StrOutputParser, then swap in a JsonOutputParser against a prompt asking for JSON, and compare the return types.
Show a solution sketch
chain = prompt | llm | StrOutputParser() returns a plain str; swapping the final step to JsonOutputParser() against a prompt instructing JSON output returns a parsed dict instead — same chain shape, different terminal behavior.
Interview question
When would you use an output parser instead of with_structured_output()?
Show a strong answer
For simpler cases where you just want a plain string (StrOutputParser) or don't need strict schema validation. For anything requiring reliable, validated structured data, with_structured_output() backed by native tool-calling is generally the more robust modern choice.
LC 10 LangChain

Document loaders

Document loaders read content from a source — a file, URL, database, or API — and convert it into LangChain's standard Document object: text content plus a metadata dict. Downstream steps (splitting, embedding, retrieval) can then work uniformly regardless of where the content originated.

Architecture diagram
PDF / URL / DB● Loader● Document objects
load_pdf.py
from langchain_community.document_loaders import PyPDFLoader

loader = PyPDFLoader("policy.pdf")
docs = loader.load()   # list[Document], one per page typically
print(docs[0].page_content[:200], docs[0].metadata)
Real-world use case
Ingesting a mixed corpus (PDFs, web pages, database rows) into a single RAG pipeline using a different loader per source but a uniform Document output feeding into the same downstream chunking/embedding code.
Common mistake
Assuming all loaders produce clean, well-structured text — PDF and HTML loaders in particular can produce messy output (broken tables, stray whitespace) that needs inspection, mirroring the parsing-quality concern from RAG ingestion pipelines generally.
Exercise
Load a PDF or plain text file with an appropriate document loader and print the page_content and metadata of the first Document.
Show a solution sketch
Instantiate the matching loader class for your file type, call .load(), and inspect docs[0].page_content and docs[0].metadata — note what metadata fields (source path, page number) are populated automatically.
Interview question
What's the common interface every document loader in LangChain produces, regardless of source?
Show a strong answer
A list of Document objects, each with page_content (the text) and metadata (a dict — source, page number, etc.) — this uniform shape is what lets the rest of the ingestion pipeline stay source-agnostic.
LC 11 LangChain

Text splitters

Text splitters break Documents into smaller chunks before embedding — LangChain's implementation of the chunking concept. RecursiveCharacterTextSplitter tries to split on natural boundaries (paragraphs, then sentences, then words) before falling back to a hard character limit, preserving more coherent chunks than a naive fixed-size split.

Architecture diagram
Document● TextSplitter● Chunked Documents
split_docs.py
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)
chunks = splitter.split_documents(docs)   # list[Document], smaller pieces
Real-world use case
Preparing long PDFs or wiki pages for a vector store, where each resulting chunk keeps a copy of the original document's metadata so citations can still point back to the source.
Common mistake
Splitting AFTER converting documents to plain strings, losing the metadata attached to each Document — always use split_documents() (which propagates metadata to each chunk) rather than manually splitting raw text.
Exercise
Split a multi-paragraph Document with two different chunk_size values and compare how many resulting chunks each produces.
Show a solution sketch
Instantiate two splitters with different chunk_size values, call split_documents() on the same input with each, and compare len(chunks) — a smaller chunk_size should produce noticeably more chunks.
Interview question
Why does RecursiveCharacterTextSplitter usually produce better chunks than a naive fixed-character split?
Show a strong answer
It tries a hierarchy of separators (paragraph breaks, then sentences, then words) before falling back to a hard cut, so chunk boundaries tend to land on natural language boundaries rather than mid-sentence, better preserving each chunk's standalone coherence.
LC 12 LangChain

Embeddings

LangChain's Embeddings interface standardizes calling any embedding provider through .embed_query() (a single query string) and .embed_documents() (a batch of texts) — the same abstraction pattern as chat models, letting you swap embedding providers without rewriting downstream vector-store code.

Architecture diagram
Text● Embeddings interface● Vector(s)
embed.py
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vector = embeddings.embed_query("What is LangChain?")
doc_vectors = embeddings.embed_documents(["doc one text", "doc two text"])
Real-world use case
Embedding an entire document corpus once during ingestion (embed_documents, batched for efficiency) and embedding each incoming user query separately at request time (embed_query) — the same interface, two different call patterns matching a RAG pipeline's two stages.
Common mistake
Using a DIFFERENT embeddings instance/model for documents vs. queries — LangChain won't catch this mismatch for you, so keeping the same model/version pinned on both sides is a discipline you still need to enforce yourself.
Exercise
Embed 3 short sentences using embed_documents() and one query using embed_query(), then manually compute cosine similarity between the query vector and each document vector.
Show a solution sketch
Call embeddings.embed_documents([...]) for the 3 sentences and embeddings.embed_query(...) for the query, then implement or import a cosine similarity function and compare the query vector against each document vector to find the closest match.
Interview question
Why does LangChain's Embeddings interface have two separate methods, embed_query and embed_documents, instead of one generic embed() method?
Show a strong answer
Some embedding providers/models use different underlying representations optimized for queries vs. documents (asymmetric embedding), and batching behavior often differs too — splitting the interface lets implementations optimize each path appropriately while keeping the calling code simple.
LC 13 LangChain

Vector stores

LangChain's VectorStore interface standardizes adding documents (with automatic embedding) and performing similarity search against any vector database backend — Chroma, Pinecone, pgvector, Azure AI Search, FAISS — through the same .add_documents() / .similarity_search() methods, hiding each backend's specific API.

Architecture diagram
Chunked Documents● VectorStore.add_documents()● Chroma / Pinecone / pgvector
vector_store.py
from langchain_chroma import Chroma

vector_store = Chroma(embedding_function=embeddings, collection_name="docs")
vector_store.add_documents(chunks)
results = vector_store.similarity_search("What is LCEL?", k=4)
Real-world use case
Prototyping locally with an in-memory or file-based Chroma store, then swapping to a managed production vector store (Pinecone, Azure AI Search) by changing only the VectorStore instantiation, keeping the rest of the RAG pipeline's code unchanged.
Common mistake
Instantiating a new VectorStore (and losing previously added documents) on every request instead of maintaining a persistent connection/client — vector stores should typically be initialized once per application, not per request.
Exercise
Add 5 short text documents to a local Chroma vector store and run a similarity search query against them, printing the top 2 results.
Show a solution sketch
Instantiate Chroma with an embedding function, call add_documents() with 5 Document objects, then call similarity_search(query, k=2) and print each result's page_content.
Interview question
Why does LangChain's VectorStore interface handle embedding internally rather than requiring you to embed documents yourself first?
Show a strong answer
It lets add_documents() take raw Documents and handle calling the configured Embeddings model internally, keeping the common case simple — you can still embed manually and use lower-level methods if you need more control, but the default path avoids repetitive boilerplate.
LC 14 LangChain

Retrievers

A Retriever is a Runnable that wraps a search mechanism — most commonly a VectorStore's similarity search — behind a standard .invoke(query) interface returning a list of Documents. This lets retrieval slot directly into an LCEL chain like any other component, and lets you swap retrieval strategies without changing the chain's shape.

Architecture diagram
Query● Retriever● Documents
retriever.py
retriever = vector_store.as_retriever(search_kwargs={"k": 4})
docs = retriever.invoke("What is LCEL?")
Real-world use case
Composing a full RAG chain where the retriever's output feeds directly into a prompt template as context, entirely through the pipe operator, without custom glue code between retrieval and prompt construction.
Common mistake
Treating a retriever as always vector-similarity-based — LangChain retrievers can wrap hybrid search, keyword search, or a completely custom function. A class name like VectorStoreRetriever tells you the mechanism, but "Retriever" as a concept is a much broader interface.
Exercise
Wrap a vector store as a retriever and use it inside an LCEL chain that also includes a prompt template and LLM, building a minimal RAG chain end to end.
Show a solution sketch
retriever = vector_store.as_retriever(); build a prompt template expecting a {context} variable; compose a chain that runs the retriever, formats retrieved docs into context, and pipes into the prompt, llm, and a parser.
Interview question
Why is "Retriever" a separate abstraction from "VectorStore," rather than just calling similarity_search directly in your chain?
Show a strong answer
Retriever is a standard Runnable interface, so it composes with the pipe operator and other LangChain abstractions uniformly. It also decouples the retrieval STRATEGY from the specific storage backend, so a chain built against a Retriever doesn't need to know or care what's underneath.
LC 15 LangChain

Chains

A chain is a composed sequence of Runnables that together perform a multi-step task. LangChain historically shipped a large library of pre-built chain classes; the modern approach is to build chains explicitly with LCEL's pipe operator, which is more transparent, more debuggable, and doesn't hide what's actually happening inside a named class.

Architecture diagram
Component A● Component B● Component C
explicit_chain.py
from langchain_core.output_parsers import StrOutputParser

chain = prompt | llm | StrOutputParser()
result = chain.invoke({"text": "Summarize this..."})
Real-world use case
Any multi-step LLM task — retrieve then generate, format then call then parse — expressed as an explicit sequence rather than a single opaque function call, making it easy to insert logging, modify one step, or test steps independently.

LC 16 LangChain

LCEL (LangChain Expression Language)

LCEL is the composition syntax built on the Runnable interface — the | pipe operator chains Runnables sequentially, RunnableParallel (or a dict literal) runs multiple Runnables concurrently and merges their outputs, and every LCEL chain automatically gets .invoke(), .stream(), .batch(), and async variants for free, plus built-in tracing.

It's less "a special mini-language" and more "operator overloading on a common interface" — the same pattern as Java's Stream API chaining .filter().map().collect().

Architecture diagram
Retriever‖ Passthrough● Prompt● LLM● Parser
lcel_rag.py
from langchain_core.runnables import RunnableParallel, RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser

rag_chain = (
    RunnableParallel(context=retriever, question=RunnablePassthrough())
    | prompt
    | llm
    | StrOutputParser()
)
answer = rag_chain.invoke("What is LCEL?")
Real-world use case
Building any multi-input chain (like RAG, where you need BOTH retrieved context and the original question available to the prompt template) using RunnableParallel to fan out and merge, rather than writing custom orchestration code.
Common mistake
Assuming | always means strictly sequential — RunnableParallel actually runs its branches CONCURRENTLY, which matters for both correctness (each branch gets the same input) and performance (branches run in parallel, not one after another).
Exercise
Build an LCEL chain with a RunnableParallel step producing two outputs from the same input, then pipe both into a prompt template that uses both as variables.
Show a solution sketch
RunnableParallel(summary=summarize_chain, sentiment=sentiment_chain) | combine_prompt | llm — both branches receive the same original input independently, and their outputs are merged into a dict available to the next step.
Interview question
What does LCEL actually give you beyond just calling functions in sequence yourself?
Show a strong answer
Automatic support for streaming, batching, and async execution across the whole chain without writing that logic per-component, plus built-in observability. LCEL isn't new functionality per se — it's the Runnable interface's composability giving you these cross-cutting capabilities for free on any chain you build with it.

Wrapping an internal API call (checking inventory, looking up a customer record) as a tool so an agent can decide, based on the conversation, whether and when to call it.

LC 18 LangChain

Tool calling

Tool calling is the model-level capability where an LLM, given a set of available tools, can respond not with plain text but with a structured request to call one or more specific tools with specific arguments. Real-world use case
This is the foundational mechanism underneath every agent — an agent loop is essentially "call the model with tools bound, check for tool_calls, execute them, feed results back, repeat."

Assuming bind_tools() means the tool is automatically EXECUTED — it isn't. The model only returns a REQUEST to call a tool; your application code is responsible for actually running the function and feeding the result back as a ToolMessage.

Interview question

Show a strong answer
The model returns an AIMessage whose tool_calls field lists the tool name(s) and arguments it wants invoked — it never executes anything itself. Your application code inspects tool_calls, runs the actual corresponding function, and feeds the result back as a ToolMessage for the model's next turn.
LC 19 LangChain

Agents

An agent is a system where the LLM itself decides the sequence of actions to take — which tools to call, in what order, and when to stop — rather than following a fixed, developer-defined sequence like a chain. Modern LangChain favors building the agent loop explicitly in LangGraph over the older AgentExecutor class, since the loop's control flow benefits from being explicit and inspectable.

Real-world use case
A customer support assistant that needs to decide, per query, whether to look up an order, check a policy document, or just answer directly — a fixed chain can't express that conditional branching cleanly; an agent can.
Common mistake
Reaching for an agent when a fixed chain would do — if the sequence of steps is always the same regardless of input, you don't need dynamic decision-making, and a plain LCEL chain is simpler, cheaper, and more predictable.

What's the fundamental difference between a chain and an agent?
Show a strong answer
A chain's sequence of steps is fixed by the developer at build time. An agent's sequence of steps — including which tools to call, how many times, and when to stop — is decided dynamically by the LLM at run time, based on the specific input and intermediate results.
LC 20 LangChain

Memory / conversation state

Memory is how an application preserves context across multiple turns — the simplest form accumulates a growing list of messages and passes the full history to the model each turn; more sophisticated approaches summarize or window older turns. A chatbot that needs to remember earlier parts of the conversation without re-explaining context every turn — the message list itself IS the memory in the simplest implementation.

Why has LangChain's approach to "memory" shifted toward relying on LangGraph's state/checkpointing rather than a dedicated Memory abstraction?
Show a strong answer
A LangGraph graph's State already needs to track conversation and intermediate results for the graph to function at all — layering a separate Memory abstraction on top was redundant once graphs became the standard way to build stateful applications.

LC 22 LangChain

Streaming

Streaming returns a chain or model's output incrementally as it's produced, rather than waiting for full completion. Every Runnable in LCEL supports .stream() automatically, and streaming composes THROUGH a chain — tokens flow out through every intermediate step as they're produced, not just at the model level.

Real-world use case
A chat UI that shows the response appearing token-by-token rather than a multi-second blank wait — the "perceived latency" benefit, now at the concrete implementation level.

Interview question
Why does streaming need to be supported at the LCEL/Runnable level, not just at the raw model API level?
Show a strong answer
A chain composes multiple steps; if only the model streamed but the parser buffered everything before returning, the end-to-end chain wouldn't actually stream. LCEL's Runnable interface is designed so streaming support propagates through composed chains, not just the underlying model call.
LC 23 LangChain

Error handling

Error handling spans multiple layers: transient provider errors (rate limits, timeouts) which LangChain's model integrations often retry automatically, tool execution errors which need explicit handling since an unhandled exception crashes the whole run, and structured-output validation failures which may need a retry-with-correction strategy.

safe_chain = RunnableLambda(safe_tool_call)
Real-world use case
An agent whose tool occasionally fails (a flaky external API) should be able to see the failure as information rather than the whole agent run crashing on an unhandled exception.

Letting a tool's exception propagate uncaught up through the agent loop — this typically crashes the entire run rather than giving the LLM a chance to recover, retry with different arguments, or gracefully inform the user.

Show a strong answer
An uncaught exception typically crashes the entire chain/agent run; a caught exception returned as a normal tool result gives the LLM the chance to see the failure as information and decide how to proceed — retry, try a different tool, or tell the user — usually a better outcome than a hard crash.
LC 24 LangChain

Async execution

LangChain's Runnable interface provides async equivalents of every sync method — .ainvoke(), .astream(), .abatch() — letting an application handle many concurrent LLM/tool calls efficiently, the same motivation as async I/O in any backend framework rather than blocking a thread per request.

Real-world use case
A FastAPI backend serving many concurrent users' chat requests, where using async chain methods lets the server handle many in-flight LLM calls (I/O-bound, waiting on network responses) without needing a thread per request.

LLM calls are I/O-bound — most of the wait is spent on a network response from the provider, not CPU. LG 01 LangGraph

Why LangGraph exists

Agent control flow — branching, looping, pausing for human input, retrying failed steps — is genuinely hard to express clearly with plain function composition or a single black-box executor. LangGraph makes control flow an explicit, first-class GRAPH: nodes (units of work) and edges (transitions, including conditional ones) operating over a shared, typed State object.

The flow of execution becomes a data structure you can inspect, visualize, checkpoint, and resume — not implicit control flow buried in a loop.

Architecture diagram
Agent node→ Tool node ↻ explicit loop edge
Real-world use case
Any agent that needs to reliably pause and resume — waiting on a human approval, or surviving a server restart mid-task — needs its execution state to be explicit and serializable, which a plain Python call stack fundamentally isn't, but a LangGraph State is.
Common mistake
Reaching for LangGraph for every LLM application, even simple ones — a single LLM call or a simple linear chain doesn't need a graph. LangGraph earns its complexity when you need branching, loops, persistence, or human-in-the-loop, not by default.
Exercise
List 3 requirements from a hypothetical agent project that would justify choosing LangGraph over a plain LCEL chain, and 3 that would NOT.
Show example answers
Justify LangGraph: needs to pause for human approval mid-task; needs to survive a process restart and resume; needs a genuine loop with a variable number of iterations. Doesn't need it: a single fixed-sequence summarization task; a one-shot classification call; a simple RAG lookup with no branching.
Interview question
What specific limitation of plain function composition (or AgentExecutor) does LangGraph address?
Show a strong answer
Implicit control flow is hard to inspect, checkpoint, resume, or pause mid-execution for human input. LangGraph makes the control flow itself — nodes, edges, and state — an explicit data structure, enabling checkpointing, visualization, and interruption as first-class capabilities rather than something you'd have to hand-build.
LG 02 LangGraph

Graph-based agent workflows

A graph-based workflow models an agent's execution as nodes (units of work) connected by edges (which node runs next), with a shared State flowing through and being updated at each node. This is architecturally a finite state machine — a concept already familiar from workflow engines like Temporal or Camunda — just applied to LLM-driven decision points instead of purely deterministic ones.

Architecture diagram
START→ agent→ END
minimal_graph.py
from langgraph.graph import StateGraph, END
from typing import TypedDict

class State(TypedDict):
    messages: list

graph = StateGraph(State)
graph.add_node("agent", agent_node_fn)
graph.set_entry_point("agent")
graph.add_edge("agent", END)
app = graph.compile()
Real-world use case
Any workflow where the NEXT step genuinely depends on the outcome of the current step in a way a linear chain can't express — a document-processing pipeline that routes differently based on document type, for example.
Common mistake
Designing a graph with too many fine-grained nodes for simple logic that could live inside one node's function — use nodes/edges for genuinely distinct decision points, and keep straightforward sequential logic inside a single node's code.
Exercise
Sketch a 3-node graph for a workflow you're familiar with from backend experience (e.g. an order-approval process), identifying which parts are nodes and which are edges.
Show an example
Nodes: "validate order," "check inventory," "approve or reject." Edges: validate → check inventory (fixed); check inventory → approve (conditional: in stock) or reject (conditional: out of stock) — the conditional edge is where the "decision" logic lives, not inside either node.
Interview question
How is a LangGraph workflow architecturally similar to a state machine or workflow engine you might already know from backend systems?
Show a strong answer
Both model a process as discrete states/steps with defined transitions, and both benefit from making the current state explicit and persistable so a long-running process can be paused, inspected, and resumed. The LangGraph-specific addition is that state or transitions are often influenced by LLM output, not purely deterministic business rules.
LG 03 LangGraph

Nodes

A node is a single unit of work in a graph — typically a Python function (or Runnable) that takes the current State as input and returns a dict of updates to merge into it. Nodes are where actual work happens: calling an LLM, executing a tool, transforming data — edges only decide WHICH node runs next.

Architecture diagram
State in→ Node function→ State updates out
node.py
def agent_node(state: State) -> dict:
    response = llm.invoke(state["messages"])
    return {"messages": [response]}   # returned dict is merged into state

graph.add_node("agent", agent_node)
Real-world use case
A "call the LLM" node, a "run a tool" node, and a "format final response" node are typically separate nodes in a real agent graph, each with a single clear responsibility — similar to keeping a microservice's handler functions focused on one job.
Common mistake
Having a node function mutate the state object directly instead of returning updates to be merged — LangGraph expects nodes to return the delta to apply, not to mutate a shared object in place, and doing so can produce confusing bugs especially with checkpointing.
Exercise
Write a node function that takes a State with a "count" field and returns an update incrementing it by 1, then run it a few times to see the count change.
Show a solution sketch
def increment_node(state): return {"count": state["count"] + 1} — add it to a minimal graph with a loop edge back to itself (guarded by a condition) and observe the count field increasing across invocations.
Interview question
What does a LangGraph node function actually receive and return?
Show a strong answer
It receives the full current State and returns a dict containing only the fields it wants to update — LangGraph merges that returned dict into the graph's state according to each field's defined reducer behavior, rather than the node replacing the whole state object.
LG 04 LangGraph

Edges

An edge defines which node runs next after a given node completes. A normal edge is a fixed, unconditional transition; a conditional edge routes to different nodes based on a function that inspects the current state — this is how branching logic gets expressed in the graph itself rather than buried in a node's internal logic.

Architecture diagram
agent→ conditional → tools END
edges.py
graph.add_edge("agent", "tools")   # unconditional

graph.add_conditional_edges(
    "agent",
    lambda state: "tools" if state["messages"][-1].tool_calls else END,
)
Real-world use case
The classic agent loop's key decision — "does the last AI message contain a tool call, or is it a final answer" — is expressed as a conditional edge examining state, not an if-statement hidden inside a node.
Common mistake
Putting the ROUTING decision logic inside a node instead of a conditional edge — this works but defeats the purpose of making control flow explicit and visualizable. Routing belongs in the edge function, keeping nodes focused purely on doing work.
Exercise
Write a conditional edge function that routes to "retry" if a state field indicates failure, or to END otherwise, and wire it into a 2-node graph.
Show a solution sketch
def route(state): return "retry" if state.get("failed") else END; then graph.add_conditional_edges("worker", route) — the function only reads state and returns a node name (or END), containing no side effects itself.
Interview question
What's the architectural benefit of expressing a branching decision as a conditional edge rather than an if-statement inside a node?
Show a strong answer
It keeps the graph's control flow visible and inspectable as data — you can visualize or reason about all possible paths through the graph — rather than hidden inside arbitrary node code. This is exactly what makes graph visualization and testing routing logic in isolation tractable.
LG 05 LangGraph

State

State is the shared data structure flowing through every node — typically defined as a TypedDict or Pydantic model, declaring exactly what fields exist and, critically, HOW each field updates when multiple nodes contribute to it. The default merge behavior is "overwrite," but list-like fields commonly use an "append" reducer.

Architecture diagram
Node A writes→ State (merged via reducers)→ Node B reads
state.py
from typing import Annotated
from langgraph.graph.message import add_messages
from typing_extensions import TypedDict

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]   # appends new messages, doesn't overwrite
    step_count: int                            # overwritten by default
Real-world use case
A conversational agent's messages field needs to ACCUMULATE across turns (append), while a step_count field should simply be REPLACED with the latest value each time — per-field reducer behavior is what makes both patterns coexist in one State definition.
Common mistake
Defining every field with the default overwrite behavior, including message lists — this causes each node update to REPLACE the message history instead of appending, silently losing conversation context. Use the add_messages reducer for any field that should accumulate.
Exercise
Define a State TypedDict with one field using add_messages and one plain field, write two nodes that update both, and run them in sequence to observe each field's behavior.
Show a solution sketch
Each node returns {"messages": [new_msg], "step_count": new_value} — after running both nodes, messages should contain ALL messages from both nodes appended in order, while step_count reflects only the LAST node's returned value.
Interview question
Why does LangGraph require you to specify HOW a state field merges updates, rather than just always overwriting or always appending?
Show a strong answer
Different fields genuinely need different merge semantics — conversation messages need to accumulate, while a status flag or counter typically needs to be replaced. Making the reducer explicit per field avoids silently corrupting one pattern to satisfy the other, and makes merge behavior visible in the state definition itself.
LG 06 LangGraph

State transitions

A state transition is the combined effect of a node running and its returned update being merged into state, followed by an edge deciding the next node — this is the graph's fundamental step: read state, do work, merge an update, route. Every single graph execution is a sequence of these transitions until an END is reached.

Architecture diagram
Read state→ Node executes→ Merge update→ Edge routes next
Real-world use case
Understanding this step-by-step transition cycle is what makes checkpointing possible — the graph engine can persist state after ANY transition, since a transition is a well-defined, discrete unit of progress, not an arbitrary point in an in-flight function call stack.
Common mistake
Assuming state transitions happen "all at once" for parallel branches — when a graph has parallel nodes (via multiple edges from one node), each branch's update is computed independently before being merged together, and understanding the merge order matters when branches write to the same field.
Exercise
Trace through a 3-node graph by hand: for a given starting state, write out what each node returns and what the state looks like after each transition until reaching END.
Show the approach
Start with the initial state dict; for each node in execution order, note its return value, then show the merged state as it would look after applying that node's reducer rules — this hand-trace is exactly what LangGraph's debugging/visualization tools automate.
Interview question
Why is thinking of graph execution as a sequence of discrete state transitions useful for debugging?
Show a strong answer
Each transition is a well-defined checkpoint: you can inspect the exact state before and after any node ran, rather than trying to reconstruct what happened from a stack trace inside an opaque loop. This is the same value a well-instrumented state machine gives you over an equivalent tangle of nested conditionals.
LG 07 LangGraph

Conditional routing

Conditional routing is the pattern of using a conditional edge's function to inspect state and choose among several possible next nodes — the mechanism that lets a graph express "if X happened, go here; if Y, go there" as an explicit, testable function rather than nested logic buried in application code.

Architecture diagram
classify node→ billing node technical node general node
routing.py
def route_by_category(state) -> str:
    category = state["category"]
    return {"billing": "billing_node", "technical": "technical_node"}.get(category, "general_node")

graph.add_conditional_edges("classify", route_by_category)
Real-world use case
A support ticket triage agent that classifies an incoming request, then routes to a specialized handling node (billing, technical, general) based purely on that classification — the routing function is a small, independently testable piece of logic.
Common mistake
Writing a routing function with side effects (calling an LLM, mutating external state) — routing functions should be pure reads of the current state, deciding only where to go next; any actual work belongs in a node, not the edge function.
Exercise
Write a routing function for a 4-way branch based on a "priority" field (low/medium/high/critical) and unit test it directly, without running the graph.
Show a solution sketch
def route_priority(state): return {"low": "queue_low", ...}.get(state["priority"], "queue_low") — call it directly with a few sample state dicts in a test and assert the correct node name is returned for each case.
Interview question
Why should a conditional edge's routing function avoid side effects?
Show a strong answer
Keeping routing functions pure (read-only, deterministic given the state) makes them independently unit-testable without running the whole graph, and keeps the separation between "deciding what to do" (edges) and "doing it" (nodes) clean — mixing the two makes both harder to test and reason about.
LG 08 LangGraph

Loops

A loop is a conditional edge that routes back to a previously-executed node (or an earlier point in the graph), enabling repeated work until some condition is met — the classic agent tool-calling loop (call LLM, maybe call a tool, back to LLM) is the most common example, but any "keep trying until X" pattern is expressed the same way.

Architecture diagram
agent→ tools ↻ back to agent
Real-world use case
An agent that keeps calling tools and reasoning until it has enough information to answer, or a data-validation node that retries a transformation with corrected input up to N times before giving up.
Common mistake
Building a loop with no maximum iteration guard — an agent that keeps deciding "I need one more tool call" indefinitely (due to a bug, an unclear task, or a model quirk) will loop forever or until a cost/timeout limit is hit elsewhere; always track and cap iteration count in state.
Exercise
Add a step_count field to a looping graph's state, increment it in the looping node, and modify the routing function to force an exit once step_count exceeds a maximum.
Show a solution sketch
def route(state): return END if state["step_count"] >= MAX_STEPS else "agent" — the hard cap ensures the graph always terminates even if the model would otherwise keep looping indefinitely.
Interview question
Why is an explicit iteration limit a non-negotiable production requirement for any looping agent graph?
Show a strong answer
An agent's loop-continuation decision is made by an LLM, which can behave unpredictably — without a hard cap tracked in state, a bug or unclear task could cause an unbounded loop, directly translating into unbounded cost and latency. A hard step limit is the same safety net as a max-retry count on any automated retry loop.

Checkpoints

A checkpoint is a saved snapshot of a graph's state at a specific point in execution — LangGraph can automatically checkpoint after every node transition when a checkpointer is configured, which is what makes pausing, resuming, replaying, and recovering from failure possible instead of losing all progress if a process crashes mid-run.

Architecture diagram
Node runs→ Checkpoint saved→ Next node
checkpointing.py
from langgraph.checkpoint.sqlite import SqliteSaver

checkpointer = SqliteSaver.from_conn_string("checkpoints.db")
app = graph.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "conversation-42"}}
app.invoke({"messages": [("human", "Hi")]}, config=config)
Real-world use case
A long-running research agent that takes several minutes across many tool calls can crash or be restarted mid-task without losing all progress — resuming from the last checkpoint rather than starting over from scratch.
Common mistake
Forgetting to pass a consistent thread_id in the config — checkpoints are scoped per thread_id, so using a different or missing ID means the graph can't find and resume its prior state, effectively starting a fresh, unrelated run.
Exercise
Run a graph with a SQLite checkpointer across two separate invoke() calls using the same thread_id, and confirm the second call's execution has access to state from the first.
Show a solution sketch
Compile with a checkpointer, invoke once with a given thread_id, then invoke again with the SAME thread_id and a new message — inspect the resulting state to confirm messages from the first invocation are still present, proving the checkpoint was loaded.
Interview question
What real capability does a checkpointer unlock that a graph without one doesn't have?
Show a strong answer
Without a checkpointer, a graph's state exists only in memory for the duration of one invoke() call — nothing persists. With one, state is durably saved after each step, enabling resuming a paused/interrupted run, surviving process restarts, and replaying execution history, all keyed by thread_id.

Persistence

Persistence is the broader capability checkpoints enable: durable storage of graph state across process restarts, server instances, and time — backed by a real database (SQLite for development, Postgres or Redis for production) rather than an in-memory dict, which is essential once an agent needs to survive beyond a single request/process lifetime.

Architecture diagram
Graph state→ Checkpointer→ Postgres / Redis
production_persistence.py
from langgraph.checkpoint.postgres import PostgresSaver

checkpointer = PostgresSaver.from_conn_string("postgresql://user:pass@host/db")
app = graph.compile(checkpointer=checkpointer)
Real-world use case
An enterprise support agent handling a multi-day conversation with a human (e.g. an approval that takes hours to arrive) needs state stored durably in a real database, not memory that disappears if the serving process restarts.
Common mistake
Shipping SQLite (a fine choice for local development) as the persistence layer in a real multi-instance production deployment — SQLite doesn't handle concurrent access from multiple server instances well; production deployments need Postgres, Redis, or another properly concurrent backend.
Exercise
Compare the setup code for a SQLite checkpointer vs. a Postgres checkpointer, and identify what would need to change to move a project from development to production.
Show the answer
Only the checkpointer class and connection string typically change — SqliteSaver.from_conn_string("file.db") becomes PostgresSaver.from_conn_string("postgresql://..."); the graph definition, nodes, and edges remain untouched, since persistence is a swappable backend behind a common interface.
Interview question
Why might a team choose SQLite during development but Postgres or Redis for production persistence?
Show a strong answer
SQLite is simple and file-based, ideal for local iteration with no extra infrastructure, but doesn't handle concurrent writes from multiple server instances well. Production deployments typically run multiple instances behind a load balancer, requiring a properly concurrent, network-accessible database like Postgres or Redis.
LG 11 LangGraph

Interrupts

An interrupt pauses graph execution at a defined point — typically before or after a specific node — returning control to your application without completing the run, so something outside the graph (a human review, an external event) can happen before execution resumes exactly where it left off, made possible by the same checkpointing mechanism.

Architecture diagram
draft_response node→ ⏸ interrupt (paused)→ send_response node
interrupts.py
app = graph.compile(checkpointer=checkpointer, interrupt_before=["send_response"])

result = app.invoke({"messages": [...]}, config=config)
# execution paused before send_response — state is saved, control returned to caller

app.invoke(None, config=config)   # resume execution from exactly where it paused
Real-world use case
Pausing an agent right before it sends a customer-facing email or executes an irreversible action (a refund, a database write), giving a human the chance to review and approve before it actually happens.
Common mistake
Assuming an interrupt automatically notifies a human or waits indefinitely on its own — the interrupt just pauses execution and returns control to your application code; YOU need to build the notification, review UI, and the logic that eventually calls invoke(None, config) to resume.
Exercise
Add an interrupt_before to a 2-node graph, invoke it once to trigger the pause, inspect the returned state, then resume it and confirm the second node runs.
Show a solution sketch
compile(checkpointer=..., interrupt_before=["node_b"]); first invoke() call returns after node_a with node_b not yet run; calling invoke(None, config=same_config) resumes and runs node_b — inspect app.get_state(config) between the two calls to see the paused state.
Interview question
What has to be true about a graph for interrupt_before/interrupt_after to actually work?
Show a strong answer
The graph must be compiled with a checkpointer — interrupts rely on the same persistence mechanism to save state at the pause point and reload it correctly when resumed. Without a checkpointer, there's nowhere for the paused state to actually live between the pause and the resume call.
LG 12 LangGraph

Human-in-the-loop

Human-in-the-loop (HITL) is the design pattern built on interrupts and persistence: an agent pauses at a decision point, a human reviews the proposed state/action, and their input (approve, reject, edit) determines how — or whether — the graph resumes, typically by updating state before calling invoke(None, config) again.

Architecture diagram
Agent proposes action→ ⏸ Human reviews→ Approved: execute Rejected: re-plan
human_approval.py
state = app.get_state(config)
proposed_action = state.values["proposed_action"]

if human_approves(proposed_action):
    app.invoke(None, config=config)                       # resume as-is
else:
    app.update_state(config, {"proposed_action": None})   # clear and let agent re-plan
    app.invoke(None, config=config)
Real-world use case
An enterprise agent that drafts a refund but requires manager approval above a dollar threshold — the exact scenario Project 6 builds — using an interrupt before the "execute refund" node and a review UI that calls update_state based on the manager's decision.
Common mistake
Building HITL as a purely client-side UI convention (just hiding a "confirm" button in the frontend) without an actual server-side interrupt — this doesn't stop the agent from having already executed the action; genuine HITL requires the graph to actually pause execution server-side before the consequential step.
Exercise
Design (in pseudocode) a HITL flow for an agent that drafts an email: it should pause before sending, let a human edit the draft, and resume with the edited content rather than the original.
Show a solution sketch
interrupt_before=["send_email"]; after the pause, call app.update_state(config, {"email_draft": edited_text}) to overwrite the draft with the human's edit, THEN invoke(None, config) to resume — the send_email node then reads the updated (edited) draft, not the original.
Interview question
Why is LangGraph's checkpoint/interrupt mechanism a natural fit for human-in-the-loop, compared to hand-rolling a similar pause/resume system?
Show a strong answer
The graph's state is already the durable, checkpointed representation of exactly what needs review and exactly what's needed to resume — HITL doesn't need a separate persistence layer bolted on, it reuses the same checkpointing infrastructure the graph needs anyway for reliability, rather than building a parallel "pending approvals" system from scratch.

Retry handling

Retry handling can be implemented at the node level (LangGraph's built-in RetryPolicy automatically re-runs a node on exception) or at the graph level (a conditional edge routes back to the same node again if a state field indicates failure) — the two suit different kinds of failure.

Architecture diagram
node fails→ RetryPolicy retries→ succeeds, or routes to failure handling
retry_policy.py
from langgraph.pregel.retry import RetryPolicy

graph.add_node("call_flaky_api", flaky_node_fn, retry=RetryPolicy(max_attempts=3))
Real-world use case
A node that calls an external API prone to transient failures (rate limits, brief outages) benefits from a RetryPolicy handling backoff automatically, rather than every node author reimplementing retry logic.
Common mistake
Relying solely on RetryPolicy when the actual issue requires an adjusted approach (different arguments, a fallback tool) — RetryPolicy suits transient failures where retrying the identical call is likely to succeed, not logical failures needing a different strategy.
Exercise
Add a RetryPolicy to a node simulating occasional failures, and observe how many attempts occur before success or exhausting the retry limit.
Show a solution sketch
Write a node that raises an exception based on a random condition roughly 50% of the time, attach RetryPolicy(max_attempts=3), and run the graph several times, logging attempt counts to observe the retry behavior in action.
Interview question
What's the difference between a node-level RetryPolicy and a graph-level conditional-edge retry loop?
Show a strong answer
RetryPolicy automatically re-runs the SAME node on an exception, suited to transient technical failures. A conditional-edge retry loop routes back to a node with possibly modified state, suited to logical failures where the retry needs to actually try something different, not just repeat the identical call.
LG 16 LangGraph

Error recovery

Error recovery goes beyond retrying the same operation — it's designing explicit fallback paths in the graph itself: a dedicated "handle_failure" node a conditional edge routes to after retries are exhausted, which might notify a human, degrade gracefully, or roll back a partially-completed multi-step operation.

Architecture diagram
attempt node→ success → continue retries exhausted → handle_failure
error_recovery.py
def route_after_attempt(state) -> str:
    if state["last_result"] == "success":
        return "next_step"
    elif state["attempt_count"] < 3:
        return "retry_node"
    else:
        return "handle_failure"   # explicit recovery path, not just giving up silently
Real-world use case
A multi-step booking workflow (search flights, reserve, pay) needs an explicit recovery path if "pay" fails AFTER a reservation was already made — the recovery node might release the reservation, rather than leaving the system in an inconsistent state.
Common mistake
Treating "the retries failed" as the end of the story with no further handling — this can leave a multi-step process partially completed (a reservation held but never paid for) unless a dedicated recovery/rollback path is built into the graph.
Exercise
Design a graph for a 3-step process (reserve, charge, confirm) where a failure at the charge step routes to a "release_reservation" node before ending.
Show a solution sketch
reserve → charge → (success: confirm | failure: release_reservation → END) — the release_reservation node explicitly undoes the reserve step's side effect, rather than leaving a dangling reservation.
Interview question
Why does "retry a few times, then give up" often need a THIRD path beyond success and simple failure, in a multi-step agent workflow?
Show a strong answer
If earlier steps had side effects, simply giving up after exhausting retries can leave the system inconsistent. A dedicated recovery/rollback path handles undoing or compensating for those side effects — the same compensating-transaction pattern used in distributed systems (sagas) for multi-step operations without a single atomic commit.

A multi-agent workflow decomposes a complex task across multiple specialized agents, each with a focused responsibility, tools, and often its own sub-graph — rather than one agent trying to do everything with a huge, unfocused tool list and prompt. What's the actual engineering justification for splitting one agent into multiple specialized agents?
Show a strong answer
Each agent gets a narrower, clearer responsibility with a shorter, more focused prompt and smaller tool set, improving reliability per-agent — analogous to why a microservice with one clear job is often easier to reason about than a monolith — but at the cost of coordination overhead, so it's justified when a single agent's scope has genuinely grown unwieldy, not by default.

Supervisor architecture

A supervisor architecture designates one node/agent as the coordinator — it doesn't do domain work itself, but decides which specialized worker agent should handle the current step, then decides again after each worker's result comes back. This is directly analogous to an orchestrator or dispatcher service in a microservices architecture.

Architecture diagram
Supervisor (routes only)→ worker agent ↻ result reported back

    decision = llm.invoke(f"Given progress so far: {state['findings']}, which agent should act next: researcher, writer, or done?")
    return {"next_agent": decision.content}

def route_from_supervisor(state) -> str:
    return state["next_agent"] if state["next_agent"] != "done" else END
Real-world use case
A multi-agent research assistant where the supervisor decides, after each worker's turn, whether more research is needed, whether it's time to write, or whether the task is complete — the decision loop a human project manager would make delegating to a team.
Common mistake
Giving the supervisor its own domain logic (letting it also do some research or writing directly) instead of keeping it purely a router — this blurs responsibility and makes the system harder to reason about.
Exercise
Write a supervisor routing function that inspects a state field listing completed sub-tasks and decides which of 3 workers should run next, or returns END if all are complete.
Show a solution sketch

Interview question
In a supervisor architecture, why does it matter that the supervisor stays purely a router and doesn't also do domain work?
Show a strong answer
Keeping the supervisor's responsibility limited to routing keeps its logic simple, testable, and easy to reason about — mixing in domain work would blur the separation of concerns the architecture is built around, the same reason an API gateway shouldn't also contain business logic in a microservices system.

Comparisons

Five comparisons worth having crisp answers for

These come up constantly in interviews because they test whether you understand WHY each tool exists, not just what it does.

LangChain vs. LangGraph

LangChain
  • Standardized interfaces to models, prompts, retrieval, tools
  • Composition via LCEL's pipe operator — mostly linear/DAG-shaped
  • Best for: fixed-sequence tasks, RAG pipelines, simple tool-augmented calls
LangGraph
  • Explicit control flow — nodes, edges, shared state, cycles
  • Built-in checkpointing, interrupts, and human-in-the-loop
  • Best for: agents that branch, loop, pause, or need durable state

They're not competitors — LangGraph nodes typically CONTAIN LangChain components (a node's function often IS an LCEL chain or a model call). LangChain gives you the parts; LangGraph gives you the wiring diagram.

Chain vs. Agent

Chain
  • Sequence of steps fixed by the developer at build time
  • Predictable cost and latency — same steps every run
  • No dynamic decision-making about what to do next
Agent
  • Sequence of steps decided dynamically by the LLM at run time
  • Variable cost/latency depending on how many steps it takes
  • Can choose which tools to call, how many times, and when to stop

Default to a chain. Reach for an agent only when the correct sequence of steps genuinely can't be known in advance.

RAG pipeline vs. agentic RAG

RAG pipeline
  • Fixed: embed query → retrieve → generate, every time
  • One retrieval pass regardless of query complexity
  • Simple, cheap, predictable — the right default
Agentic RAG
  • The agent can decide to retrieve again, rephrase, or use other tools
  • Can handle multi-hop questions a single retrieval pass would miss
  • More expensive and slower — justify it with a measured failure mode

Agentic RAG is a special case of "chain vs. agent" applied specifically to retrieval — the same "measure first, add complexity only where justified" principle applies.

Stateless vs. stateful agents

Stateless
  • Each call is independent — no memory of prior turns
  • Simpler to scale horizontally — no session affinity needed
  • Fine for single-shot tasks: classify, summarize, extract
Stateful
  • State persists across turns/invocations (LangGraph's checkpointing)
  • Required for conversation, multi-step tasks, human-in-the-loop
  • Needs a real persistence backend and a thread_id scheme in production

Single-agent vs. multi-agent

Single-agent
  • One prompt, one tool set, one loop
  • Simpler to build, debug, and reason about
  • Can become unwieldy as tool count and prompt complexity grow
Multi-agent
  • Specialized agents, each with a narrower responsibility
  • Better reliability per-agent, at the cost of coordination overhead
  • Justified when a single agent's scope has genuinely grown unwieldy

from langchain_core.tools import tool
from langgraph.prebuilt import create_react_agent

@tool
def calculate(expression: str) -> str:
    """Evaluate a basic arithmetic expression, e.g. '12 * 4'."""
    try:
        return str(eval(expression, {"__builtins__": {}}))
    except Exception as e:
        return f"Could not evaluate: {e}"

@tool
def order_status(order_id: str) -> str:
    """Look up the status of an order by its ID."""
    return MOCK_ORDERS.get(order_id, "Order not found.")

Stateful LangGraph agent

Rebuilding Project 3's agent as an explicit LangGraph — the loop becomes visible edges, and conversation state persists across turns via checkpointing.

Requirements

  • Same tools as Project 3, but the agent loop is an explicit graph, not create_react_agent's black box.
  • Conversation state persists across multiple separate invoke() calls using the same thread_id.
  • A hard step limit prevents runaway tool-calling loops.

Architecture

START→ agent→ conditional → tools ↻ back to agent

Code

stateful_agent.py
from langgraph.graph import StateGraph, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode
from langgraph.checkpoint.sqlite import SqliteSaver
from typing import Annotated, TypedDict

class State(TypedDict):
    messages: Annotated[list, add_messages]

def agent_node(state: State) -> dict:
    return {"messages": [llm_with_tools.invoke(state["messages"])]}

def route(state: State) -> str:
    last = state["messages"][-1]
    return "tools" if getattr(last, "tool_calls", None) else END

graph = StateGraph(State)
graph.add_node("agent", agent_node)
graph.add_node("tools", ToolNode([calculate, order_status]))
graph.set_entry_point("agent")
graph.add_conditional_edges("agent", route)
graph.add_edge("tools", "agent")

app = graph.compile(checkpointer=SqliteSaver.from_conn_string("agent.db"))
config = {"configurable": {"thread_id": "user-42"}, "recursion_limit": 15}
app.invoke({"messages": [("human", "What's 12 * 4?")]}, config=config)

Testing & production notes

  • Test the routing function in isolation with hand-built state dicts containing and not containing tool_calls, without running the full graph.
  • Verify persistence by invoking twice with the same thread_id and confirming the second call has access to the first's message history.

Interview explanation

"The same agent behavior as a create_react_agent, rebuilt as an explicit graph so the loop, routing decision, and state are all inspectable — with SQLite checkpointing so a conversation's history survives across separate invoke() calls scoped by thread_id, and a recursion_limit bounding worst-case cost."

Resume bullet

Multi-agent research assistant

A supervisor routes between a researcher agent and a writer agent, each a focused sub-graph, until a final report is ready — exercising multi-agent workflows and supervisor architecture directly.

Requirements

  • A writer agent that drafts a report from accumulated findings.

Architecture

Supervisor→ Researcher Writer ↻ each reports back to supervisor

Code

multi_agent_research.py
class ResearchState(TypedDict):
    messages: Annotated[list, add_messages]
    findings: list[str]
    next_agent: str

def supervisor_node(state: ResearchState) -> dict:
    prompt = f"Findings so far: {state['findings']}. Next: researcher, writer, or done?"
    decision = llm.invoke(prompt).content.strip()
    return {"next_agent": decision}

def researcher_node(state: ResearchState) -> dict:
    finding = research_agent.invoke(state["messages"])
    return {"findings": state["findings"] + [finding]}

def writer_node(state: ResearchState) -> dict:
    report = writer_agent.invoke(f"Write a report from: {state['findings']}")
    return {"messages": [("ai", report)]}

def route(state: ResearchState) -> str:
    return state["next_agent"] if state["next_agent"] != "done" else END

graph = StateGraph(ResearchState)
graph.add_node("supervisor", supervisor_node)
graph.add_node("researcher", researcher_node)
graph.add_node("writer", writer_node)
graph.set_entry_point("supervisor")
graph.add_conditional_edges("supervisor", route)
graph.add_edge("researcher", "supervisor")
graph.add_edge("writer", "supervisor")

Testing & production notes

  • Unit test the supervisor's routing logic separately from the LLM call that produces its decision — mock the decision string and assert route() returns the right node name.
  • Cap total supervisor turns with recursion_limit — a supervisor that keeps deciding "more research" indefinitely is the multi-agent version of an unbounded single-agent loop.

Interview explanation

"A supervisor architecture with two specialized workers — the supervisor holds no domain logic, purely deciding which worker acts next based on accumulated findings, mirroring how a project manager would delegate to a research analyst and a writer on a real team."

Resume bullet

Designed a multi-agent research assistant using a supervisor architecture in LangGraph, coordinating a researcher and writer agent through explicit state-based routing.

support_agent.py
class SupportState(TypedDict):
    messages: Annotated[list, add_messages]
    proposed_refund: float
    approved: bool

def draft_resolution(state: SupportState) -> dict:
    amount = determine_refund_amount(state["messages"])
    return {"proposed_refund": amount}

def execute_refund(state: SupportState) -> dict:
    process_refund(state["proposed_refund"])
    return {"messages": [("ai", f"Refund of ${state['proposed_refund']} processed.")]}

graph = StateGraph(SupportState)
graph.add_node("draft_resolution", draft_resolution)
graph.add_node("execute_refund", execute_refund)
graph.set_entry_point("draft_resolution")
graph.add_edge("draft_resolution", "execute_refund")

app = graph.compile(checkpointer=checkpointer, interrupt_before=["execute_refund"])

# --- runs up to the interrupt ---
config = {"configurable": {"thread_id": "ticket-991"}}
app.invoke({"messages": [("human", "My order arrived broken.")]}, config=config)

# --- later, a human reviews and approves or edits ---
state = app.get_state(config)
if manager_approves(state.values["proposed_refund"]):
    app.invoke(None, config=config)                                    # resume as-is
else:
    app.update_state(config, {"proposed_refund": revised_amount})
    app.invoke(None, config=config)                                    # resume with the edit

Testing & production notes

  • Test that the graph genuinely pauses before execute_refund runs — assert the refund side effect has NOT happened between the first invoke() and the approval step.
  • Use a real database checkpointer in production — an approval might take hours, and the graph's paused state must survive well beyond a single server process's lifetime.
  • Log every approval decision (who approved, what was approved, when) as an audit trail — this is exactly the kind of consequential action that needs traceability.

Interview explanation

"An agent that drafts a decision but is architecturally prevented from executing anything irreversible without a human checkpoint — using interrupt_before on the execute node and a durable checkpointer so the pause can outlast a single process lifetime. This is the pattern I'd point to as the actual production answer to 'how do you keep an agent safe.'"
