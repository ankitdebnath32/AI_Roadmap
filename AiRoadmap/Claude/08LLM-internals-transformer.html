The big picture

From raw text to the next token: the whole pipeline

Hold this picture in your head through the rest of the workbook. Every topic from here on is a close-up of exactly one of these seven boxes.

Notice the loop at the end: the predicted token gets appended to the input and the whole pipeline runs again for the next position. That's the entirety of how an LLM "writes" — one token, one full forward pass, repeated.

01 Foundations

Neural networks basics

Intuition first
A neural network is a function made of many adjustable "knobs" (weights) arranged in layers. Each layer combines its inputs with its weights, then passes the result through a simple non-linear "squashing" function. Training nudges every knob, repeatedly, until the network's output matches what you want across a huge number of examples.

Nothing about any individual neuron is "intelligent" — the capability comes from having enough of them, arranged well, nudged correctly, many times over. In Java terms: a method pipeline where each step is output = activation(weights · input + bias), chained repeatedly, except the weights and bias are learned rather than hand-coded.

Diagram
Input layer→ Hidden layer(s)→ Output layer
One neuron's computation
output = activation(w₁x₁ + w₂x₂ + ... + b)
Interview question
Explain a neural network to someone who's never seen one, in terms a backend engineer would relate to.
Show a strong answer
It's a composite function built from layers of simple linear operations (a weighted sum plus a bias) each followed by a non-linear activation function, with the weights being learned parameters tuned via training rather than hardcoded — conceptually a deeply nested pipeline of configurable transform steps.
02 Foundations

Deep learning basics

Intuition first
"Deep" just means a network with MANY layers stacked up, rather than one or two. Each layer learns to represent the input a little more abstractly than the layer before — early layers might capture basic patterns, later layers capture increasingly abstract structure and meaning.

Depth lets the network build complex representations from simple building blocks, layer by layer — the same way complex software is built from small functions composed together, rather than one giant function trying to do everything at once.

Diagram
Layer 1: basic patterns→ Layer 2: combinations→ Later layers: abstract meaning
Interview question
Why does adding more layers (depth) tend to help more than adding more neurons to one layer (width)?
Show a strong answer
Depth lets the network compose simple learned features into progressively more abstract ones layer by layer, similar to building complex logic from small, reusable functions. A single very wide layer can theoretically approximate complex functions too, but depth tends to learn more efficiently for the kind of hierarchical structure found in language and images.
03 Foundations

Language modeling

Intuition first
A language model's core job is deceptively simple: given some text so far, predict what token is most likely to come next. Everything else — chatbots, code generation, summarization — is this one capability applied repeatedly, with the right input framing.

It's like autocomplete on your phone, but trained on a vastly larger amount of text with a vastly larger model, which lets the "obvious extension" of autocomplete become astonishingly capable. Getting good at this narrow prediction task turns out to require learning grammar, facts, and reasoning patterns as a side effect.

Diagram
"The cat sat on the"→ Language Model→ "mat" (highest probability)
Interview question
Why is "predict the next token" considered a surprisingly powerful training objective, given how simple it sounds?
Show a strong answer
Getting good at predicting the next token in truly diverse text requires implicitly learning grammar, facts, common-sense reasoning, and style — the model can't predict well without learning these things as a side effect, even though none of them were explicitly labeled as training targets.
04 Foundations

Tokenization

Intuition first
Before any text reaches the model's math, it's chopped into discrete pieces called tokens — not necessarily whole words. Modern tokenizers use subword tokenization, splitting common words into one token but splitting rarer or longer words into smaller pieces.

This strikes a practical balance: a whole-word vocabulary would need to be enormous and would fail completely on unseen words; a character-level vocabulary is small but makes sequences much longer and harder to extract meaning from directly. Subword tokenization gets the best of both.

Diagram
"unbelievable"→ "un" "believ" "able"
tokenize.py
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("gpt2")
tokens = tokenizer.tokenize("Tokenization is interesting")
print(tokens)  # ['Token', 'ization', 'Ġis', 'Ġinteresting']
Interview angle
A model's effective vocabulary is a few tens of thousands of tokens, not every word in English. This is exactly why unusual words, typos, or non-English text often split into more, smaller tokens — consuming more of your context budget per word.
Interview question
Why do modern LLMs use subword tokenization instead of whole-word or character-level tokenization?
Show a strong answer
It balances vocabulary size against sequence length — whole-word vocabularies are huge and can't handle unseen words, while character-level tokenization keeps the vocabulary tiny but makes sequences much longer. Subword tokenization gets common words as single efficient tokens while still representing rare words by breaking them into known pieces.
05 Foundations

Token IDs

Intuition first
Once text is split into tokens, each is looked up in a fixed vocabulary table and replaced with its integer index — a token ID. This is a pure lookup, like mapping a string key to a row number in a database table.

The ID itself carries no meaning — token ID 464 isn't "more" or "less" than token ID 212 in any semantic sense. It's just an address used to retrieve that token's learned embedding vector in the next step.

token_ids.py
token_ids = tokenizer.convert_tokens_to_ids(['Token', 'ization'])
print(token_ids)  # [30642, 1634]
Common misconception
Assuming token IDs encode meaning or similarity directly. Two semantically similar words can have wildly different, unrelated token IDs — all the meaning lives in the EMBEDDING the ID points to, not the ID number itself.
Interview question
Does the numeric value of a token ID carry any meaning?
Show a strong answer
No — the ID is an arbitrary index into a vocabulary lookup table, assigned essentially by whatever order tokens were added to the vocabulary. All semantic meaning lives in the embedding vector that ID retrieves, not in the ID itself.
06 Foundations

Embeddings

Intuition first
An embedding converts a token ID into a vector of numbers (e.g. 768 or 4096 of them) that captures something about that token's MEANING. Tokens used in similar contexts end up with similar vectors — "king" and "queen" end up numerically closer than "king" and "bicycle," purely as a learned consequence of training.

Think of it as a lookup table with one row per vocabulary token — conceptually a HashMap<TokenId, float[]>, except the vectors themselves are learned parameters, not hand-assigned. This is the step where a discrete, meaningless token ID becomes a point in a continuous "meaning space" the rest of the network can do math on.

Diagram
Token ID 30642→ Embedding lookup→ [0.2, -0.8, 0.5, ...]
The entire operation
embedding_vector = EmbeddingMatrix[token_id]
Interview angle
Embedding similarity is usually measured with cosine similarity (the angle between two vectors), not raw distance — the exact same embedding concept from vector databases and RAG, now appearing as the very first thing that happens inside an LLM.
Interview question
What does it mean for two tokens to be "close" in embedding space, and why does that emerge from training rather than being designed?
Show a strong answer
Closeness means their vectors point in similar directions in high-dimensional space, typically measured by cosine similarity. It emerges because tokens used in similar contexts get nudged toward similar vectors as a side effect of the model learning to predict surrounding text well — no one manually defines which words are "similar."
07 Foundations

Positional encoding

Intuition first
Embeddings tell the model WHAT each token is, but not WHERE it sits in the sequence — and word order obviously matters ("dog bites man" vs. "man bites dog" use identical tokens). Positional encoding adds information about each token's position into the mix.

The classic approach adds a position-specific pattern of numbers to each token's embedding before it enters the Transformer. Modern approaches (like RoPE) instead bake position into HOW attention computes relative distances between tokens — but the problem being solved is identical: give an otherwise order-blind mechanism a sense of sequence.

Diagram
Embedding+ Positional pattern→ Position-aware vector
Interview angle
Self-attention, by itself, is completely order-agnostic — it treats the input as a SET of tokens, not a SEQUENCE, unless position information is explicitly injected somewhere. This is the one sentence that answers nearly every interview question about why positional encoding exists.
Interview question
Why do Transformers need an explicit positional encoding step, when older architectures like RNNs didn't?
Show a strong answer
RNNs process tokens one at a time in order, so position is implicit in the processing sequence itself. Transformers process all tokens in parallel via attention, which has no inherent sense of order — without positional encoding, "the cat chased the dog" and "the dog chased the cat" would look identical to the attention mechanism.
08 Transformer

Transformer architecture

Intuition first
The Transformer replaced recurrent networks (RNNs/LSTMs) as the dominant way to process sequences, built around one key idea: let every token look at every other token directly (via self-attention) instead of passing information step-by-step through a chain.

The original 2017 architecture had two halves — an encoder (reads and understands input) and a decoder (generates output). Different LLM families use one half, the other, or both.

Diagram
Input embeddings→ Encoder stack Decoder stack→ Output
Interview question
At a high level, what problem did the Transformer architecture solve that previous sequence models struggled with?
Show a strong answer
It solved modeling long-range dependencies efficiently and in parallel — RNN-based models processed tokens sequentially, making them slow to train and prone to losing information from far earlier in a sequence. Self-attention lets every token directly access every other token in one step, regardless of distance.
09 Transformer

Encoder

Intuition first
An encoder reads an entire input sequence and produces a rich, contextual representation of it. Each token's output is informed by ALL other tokens — both before and after it — since encoder self-attention isn't restricted to looking only backward.

Encoders are good at UNDERSTANDING text fully, which is why they're used for classification, embedding generation, and as the "reading" half of translation models.

Diagram
Full input sequence→ Encoder (bidirectional attention)→ Contextual representations
Interview question
Why can an encoder's attention look at future tokens in the input, when a decoder generating text cannot?
Show a strong answer
An encoder is given the entire input sequence upfront and its job is to understand it fully — there's no "generation" happening, so there's nothing to hide. A decoder generating text one token at a time must not see tokens it hasn't generated yet, or it would be cheating by peeking at the answer.
10 Transformer

Decoder

Intuition first
A decoder generates output one token at a time, and its self-attention is MASKED so each position can only attend to itself and earlier positions — never future ones, since at generation time, future tokens don't exist yet.

This "causal masking" is what makes a decoder usable for actually writing text step by step. GPT-style models are decoders used alone — there's no encoder half at all.

Diagram
Previous tokens→ Decoder (causal/masked attention)→ Next token prediction
Interview question
What is "causal masking" and why is it necessary in a decoder?
Show a strong answer
Causal masking prevents a token's attention from looking at any token that comes after it, ensuring the model only uses information it would actually have at generation time — without it, the model could trivially "cheat" during training by looking ahead at the very token it's supposed to predict.
11 Transformer

Encoder-decoder models

Intuition first
An encoder-decoder model (the original Transformer, T5, BART) uses both halves: the encoder fully reads and understands the input, and the decoder generates output, cross-attending to the encoder's output at every step — not just attending to its own previous tokens.

This naturally fits tasks with a clear "transform this input into different output" shape — translation (English in, French out), summarization (long text in, short text out).

Diagram
Input→ Encoder→ Decoder (cross-attends + causal self-attention)→ Output
Interview question
Why is an encoder-decoder architecture a particularly natural fit for translation?
Show a strong answer
Translation has two distinct sub-tasks — fully understanding the source sentence (encoder) and generating a fluent target-language sentence conditioned on that understanding (decoder, cross-attending to the encoder) — a shape the two-part architecture directly mirrors.
12 Transformer

Decoder-only models

Intuition first
Decoder-only models (GPT-family, LLaMA, and most modern chat LLMs) drop the encoder entirely and just use a decoder, trained purely on next-token prediction over massive amounts of plain text.

There's no separate "input" and "output" sequence structurally — a user's prompt AND the model's response are just one long sequence of tokens, with the model predicting the next one at every position, causally masked throughout.

Diagram
Prompt + response-so-far tokens→ Decoder-only stack→ Next token
Interview question
How does a decoder-only model handle a "prompt" and a "response" if there's no architectural separation between them?
Show a strong answer
There isn't one architecturally — a prompt and its response are one continuous sequence of tokens to the model. The distinction between "user input" and "model output" is a convention enforced by how the application constructs the sequence (special tokens/roles, stopping generation at a turn boundary), not something the core architecture represents.
13 Transformer

Self-attention

Intuition first
Self-attention lets every token in a sequence directly gather information from every other token, weighted by how RELEVANT each other token is to it. In "the trophy didn't fit in the suitcase because it was too big," "it" needs to figure out, via attention, that it more likely refers to "trophy" than "suitcase."

It's called SELF-attention because the sequence attends to itself, as opposed to cross-attention, where a decoder attends to a different, separate sequence (the encoder's output).

Diagram
"it"attends strongly → "trophy" "suitcase" (weakly)

Try this live in the Attention lab further down this workbook.

Interview question
In one sentence, what problem does self-attention solve?
Show a strong answer
It lets every token build a representation informed by the other tokens most relevant to it, regardless of how far away they are in the sequence, rather than being limited to nearby context or having to pass information step-by-step through intermediate positions.
14 Transformer

Query, Key, and Value

Intuition first — the library analogy
Every token produces three vectors from itself via separate learned transformations: a Query ("what am I looking for?" — like typing a search term), a Key ("what do I have to offer, as a label for others to match against?" — like a book's spine label), and a Value ("here's my actual content, if you decide I'm relevant" — the book's actual text).

To decide how much attention token A should pay to token B, compare A's Query against B's Key — how well does what I'm looking for match what you're offering? The better the match, the more of B's Value gets pulled into A's new representation.

VectorLibrary analogyRole
QueryYour search termsWhat this token is looking for
KeyA book's spine label/tagsWhat this token advertises about itself
ValueThe book's actual textWhat actually gets passed along if relevant
Diagram
Token X→ three projections → Query Key Value
Three learned projections of the same input
Q = X·Wq   K = X·Wk   V = X·Wv
Interview angle
All three vectors come from the SAME input token, through three DIFFERENT learned weight matrices — nothing mystical, just three linear projections of the same starting point, each trained to be useful for a different role in the comparison.
Interview question
Using the library-search analogy, explain why Query and Key need to be separate vectors rather than just comparing tokens directly.
Show a strong answer
Comparing raw token vectors directly would force one representation to serve two different jobs — "what I'm looking for" and "what I offer as a match target." Learning separate Query and Key projections lets the model learn what makes a good SEARCH versus a good LABEL independently, the same reason a search box and a document's title field aren't the same piece of text in a real search system.
15 Transformer

Attention scores

Intuition first
An attention score measures how much one token's Query matches another token's Key — computed as the dot product of the two vectors: a single number that's larger when the vectors point in a similar direction, smaller or negative when they don't.

Every token computes a score against every other token (including itself), producing a full grid of raw match scores before anything is normalized into actual attention weights.

Raw attention score between tokens A and B
score(A,B) = Query_A · Key_B
Interview question
What does a high attention SCORE (before softmax) actually represent, intuitively?
Show a strong answer
It represents how well token A's "what I'm looking for" vector aligns with token B's "what I offer" vector — a high dot product means the two vectors point in a similar direction in that learned space, which the model has learned to associate with B being relevant for A.
16 Transformer

Scaled dot-product attention

Intuition first
This is the full, named operation: compute Query·Key scores for every pair, divide by the square root of the Key dimension (pure numerical stability — keeps softmax from becoming too extreme), apply softmax to turn scores into a probability distribution summing to 1, then use those probabilities as weights for a weighted sum of all the Value vectors.

The scaling step is a numerical-stability detail, not a conceptual leap — everything else is exactly what Query/Key/Value and attention scores already described.

The full operation
Attention(Q,K,V) = softmax(QKᵀ / √d_k) · V
Diagram
Q, K→ scores÷√d_k → softmax→ weighted sum of V

A full worked numerical example with real small numbers is in the Deep Dives section below.

Interview question
Why divide by the square root of the key dimension before applying softmax?
Show a strong answer
As Query/Key dimensionality grows, dot products tend to grow larger in magnitude too, which can push softmax into an extremely peaked, near one-hot distribution with very small gradients. Dividing by √d_k keeps scores in a numerically well-behaved range so training remains stable regardless of dimension size.
17 Transformer

Multi-head attention

Intuition first
Instead of computing attention once, the model computes it SEVERAL TIMES IN PARALLEL, each with its own independently-learned Query/Key/Value projections (each a "head"), then concatenates all the heads' outputs together.

Different heads tend to specialize in different kinds of relationships — one might track grammatical subject-verb agreement, another might track coreference ("it" → "trophy") — without anyone explicitly telling them to specialize; it emerges from training.

Diagram
Input→ Head 1 Head 2 ... Head N→ Concat + linear
Combining the heads
MultiHead(Q,K,V) = Concat(head₁, ..., head_h) · Wo
Interview angle
Multi-head attention doesn't dramatically increase total computation — each head typically operates on a smaller slice of the overall dimension (8 heads of dimension 64 instead of 1 head of dimension 512), so total compute is comparable. What you gain is the ability to learn several different kinds of relationships in parallel, not raw extra capacity.
Interview question
Why use multiple smaller attention heads instead of one large attention mechanism?
Show a strong answer
Different heads can specialize in learning different TYPES of relationships between tokens in parallel, which a single attention mechanism operating on the full dimension would have to learn to blend into one representation. Splitting into heads gives more structured flexibility at a similar total computational cost.
18 Transformer

Feed-forward network

Intuition first
After attention mixes information ACROSS tokens, each token's resulting vector is passed independently through a small feed-forward network (two linear layers with a non-linearity between them) that processes EACH position separately — no cross-token interaction in this step at all.

If attention is "gather information from everywhere relevant," the feed-forward network is "now think about what you gathered, on your own."

Diagram
Attention output→ Linear→ Activation→ Linear
Per-token, no cross-token mixing
FFN(x) = Linear₂(Activation(Linear₁(x)))
Interview question
What's the conceptual difference between what the attention layer does and what the feed-forward layer does, within one Transformer block?
Show a strong answer
Attention mixes information ACROSS different token positions, gathering relevant context from elsewhere. The feed-forward network then processes EACH token's resulting vector independently, with no interaction between positions — attention is "look around," the feed-forward network is "think it over, alone."
19 Transformer

Residual connections

Intuition first
A residual (skip) connection adds a layer's INPUT directly to its OUTPUT, rather than only passing the transformed version forward. Instead of output = Layer(x), you get output = x + Layer(x).

This solves a real training problem: very deep networks are prone to vanishing gradients, where the training signal needed to update early layers gets weaker and weaker as it propagates backward through many layers. Residual connections give gradients a direct, shorter path backward, making it practical to train dozens or even hundreds of stacked blocks.

The skip connection
output = x + Layer(x)
Interview question
Why are residual connections essential for training very deep Transformer stacks?
Show a strong answer
Without them, gradients have to flow backward through every layer during training and tend to vanish as the network gets deeper, making early layers barely update. Residual connections give gradients a direct shortcut around each layer, keeping training stable even with dozens of stacked blocks.
20 Transformer

Layer normalization

Intuition first
Layer normalization rescales the numbers within each token's vector so they have a consistent mean and variance, applied independently per token — keeping values from growing too large or too small as they pass through many stacked layers.

Think of it as resetting the "scale" of the numbers back to a sane, consistent range at each step, so no single layer's quirky output can throw off everything downstream.

Diagram
Raw vector (varying scale)→ LayerNorm→ Normalized vector (consistent scale)
The normalization
LayerNorm(x) = (x − mean) / std  →  scaled & shifted by learned parameters
Interview question
What problem does layer normalization solve, at an intuitive level?
Show a strong answer
As data flows through many stacked layers, the SCALE of the numbers can drift and become unstable, making training slower or less reliable. Layer normalization rescales each token's vector to a consistent, well-behaved range at each step, independent of what happened in earlier layers.
21 Transformer

Transformer blocks

Intuition first
A Transformer block is the repeating unit stacked N times to build the full model: self-attention (wrapped in a residual connection and layer norm), followed by a feed-forward network (also wrapped in its own residual connection and layer norm).

Modern models stack many of these identical blocks — GPT-3 has 96, some current models have well over 100 — each block refining the token representations a bit further.

Diagram
LayerNorm→ Self-attention+residual→ LayerNorm→ FFN+residual→ × N blocks
Interview question
If you had to draw one Transformer block from memory in an interview, what would it contain?
Show a strong answer
Self-attention wrapped in a residual connection and layer normalization, followed by a feed-forward network also wrapped in its own residual connection and layer normalization — that single block, repeated N times, is the entire model body.
22 Generation

Next-token prediction

Intuition first
After the final Transformer block, the model has one vector per position summarizing "everything relevant for predicting what comes next here." That vector gets multiplied by a big output matrix, producing one raw score PER TOKEN IN THE VOCABULARY — tens of thousands of numbers, one per possible next token.
Diagram
Final layer output→ × output matrix → Logits (one per vocab token)
Interview question
What does the model's final layer actually output, before any sampling happens?
Show a strong answer
A vector of raw scores — logits — one per token in the vocabulary, representing how strongly the model favors each possible next token given everything it's processed so far. Nothing is a probability yet at this point.
23 Generation

Logits

Intuition first
Logits are the raw, unnormalized scores for every token in the vocabulary — any real number, positive or negative, that don't sum to anything meaningful on their own. They're a RANKING signal (higher logit = more favored), not a probability, until softmax transforms them.
Interview question
Why can't you interpret a logit value directly as a probability?
Show a strong answer
Logits are unbounded real numbers with no constraint that they sum to 1 or stay within [0,1] — they're a relative ranking signal, not a probability distribution. Softmax is the specific transformation that converts them into something that behaves like a valid probability distribution.
24 Generation

Softmax

Intuition first
Softmax converts raw logits into a probability distribution — every value becomes positive, and they all sum to exactly 1 — by exponentiating each logit (amplifying the gaps between large and small values) and dividing by the sum of all exponentiated values.

The exponentiation is what makes softmax "soft" — a token with a slightly higher logit gets a noticeably higher probability, rather than everything flattening to roughly equal.

Softmax
softmax(xᵢ) = eˣⁱ / Σⱼ eˣʲ
softmax.py
import numpy as np

def softmax(logits):
    exp_logits = np.exp(logits - np.max(logits))  # subtract max for numerical stability
    return exp_logits / np.sum(exp_logits)

print(softmax([2.0, 1.0, 0.1]))  # [0.659, 0.242, 0.099]
Interview question
Why subtract the maximum logit before exponentiating, in a real softmax implementation?
Show a strong answer
It's a numerical-stability trick — exponentiating a large logit directly can overflow floating-point range, but subtracting the max first guarantees the largest exponentiated value is e⁰ = 1, producing the exact same final probabilities without the overflow risk.
25 Generation

Sampling

Intuition first
Sampling is the step of actually PICKING one token from the probability distribution, rather than always picking the single highest-probability one (greedy decoding). Sampling introduces controlled randomness, weighted by probability — what makes output feel varied rather than robotically identical every run.
Diagram
Probability distribution→ Sampling strategy→ One chosen token
Interview question
What's the difference between greedy decoding and sampling, and when might you prefer each?
Show a strong answer
Greedy decoding always picks the highest-probability token, producing deterministic, often repetitive output — useful for reproducibility or focused factual answers. Sampling picks weighted by probability, producing more varied, natural-feeling output — generally preferred for creative or conversational generation, at the cost of reproducibility.
26 Generation

Temperature

Intuition first
Temperature reshapes the probability distribution BEFORE sampling by dividing every logit by the temperature value before softmax. Below 1, the distribution gets MORE peaked (more confident/deterministic); above 1, it FLATTENS (more randomness, giving weaker tokens a better chance). At 1, nothing changes.
Temperature-scaled sampling
probabilities = softmax(logits / temperature)

Try this live in the Temperature lab further down this workbook — the math there is the exact formula above, computed in real time.

Interview question
What does setting temperature to a very low value (like 0.1) actually do to the output, mechanically?
Show a strong answer
Dividing logits by a small temperature amplifies the DIFFERENCES between them before softmax, pushing the resulting distribution toward being extremely peaked around the already-highest-scoring tokens — in the limit, this approaches greedy decoding, making output nearly deterministic.
27 Generation

Top-k

Intuition first
Top-k sampling restricts the candidate pool to only the K highest-probability tokens, discarding everything else, then renormalizes those K probabilities to sum to 1 before sampling — preventing a sample from ever landing on a genuinely bizarre, extremely-low-probability token.
Diagram
Full distribution (thousands)→ Keep top K→ Renormalize & sample
Interview question
Why might top-k sampling behave poorly if k is fixed at a single value across very different situations?
Show a strong answer
A fixed k treats a confident distribution (only 2-3 meaningfully likely tokens) the same as an uncertain one (dozens plausible) — it might needlessly restrict options in the uncertain case or fail to restrict enough in the confident case. This is exactly the motivation for top-p as an adaptive alternative.
28 Generation

Top-p

Intuition first
Top-p (nucleus) sampling keeps the SMALLEST set of highest-probability tokens whose cumulative probability adds up to at least p (e.g. 0.9). The pool size adapts automatically — a confident distribution might only need 2 tokens to reach 90%, an uncertain one might need 50.
Diagram
Full distribution→ sort, accumulate → Keep until cumulative ≥ p→ Renormalize & sample

Try both top-k and top-p live in the Top-k/Top-p lab further down this workbook.

Interview question
Why is top-p often preferred over a fixed top-k in production systems?
Show a strong answer
Top-p adapts the candidate pool size to the model's actual confidence at each step — few candidates when sure, more when uncertain — rather than applying a one-size-fits-all cutoff count regardless of how peaked or flat the distribution actually is.
29 Generation

Context window

Intuition first
The context window is the maximum number of tokens (input plus generated output combined) a model can process in a single forward pass. Anything beyond that limit doesn't exist to the model — it's not "forgotten," it was never part of the sequence being processed.

A larger window lets a model consider more surrounding text at once, but self-attention's compute cost grows roughly quadratically with sequence length — exactly why context windows aren't simply unlimited.

Interview question
Why can't context windows simply be made arbitrarily large?
Show a strong answer
Self-attention's cost grows roughly quadratically with sequence length — every token attends to every other token, so doubling sequence length roughly quadruples attention computation. This makes very long context windows substantially more expensive in compute and memory, a deliberate engineering trade-off.
30 Generation

KV cache (conceptual level)

Intuition first
Recomputing Key and Value vectors for ALL previous tokens at every new generation step would be wasteful — those vectors don't change once computed, since they only depend on tokens that are already fixed. The KV cache stores them, so each new step only computes Q/K/V for the NEW token and reuses cached K/V for everything before it.
Diagram
Token 1: compute K,V → cache→ Token 2: cache→ Token N: new K,V only; reuse rest
Interview question
Why does a KV cache matter specifically for autoregressive generation, but not as much during training?
Show a strong answer
During training, the full sequence is known upfront and processed in one parallel pass, so there's no repeated step-by-step recomputation to avoid. During inference, generation happens one token at a time — without caching, each new token would require recomputing Key and Value for every previous token from scratch, which matters enormously for latency and cost.
31 Scale & training

Model parameters

Intuition first
Parameters are literally the numbers (weights and biases) inside the model that get adjusted during training — every weight matrix in every attention head, every feed-forward layer, every embedding table entry. "A 7-billion-parameter model" is a literal count of adjustable numbers, not a metaphor.
Interview question
What exactly is a "parameter" in an LLM, concretely?
Show a strong answer
A single learnable number — one entry in a weight matrix or bias vector anywhere in the model, including the embedding table and every attention/feed-forward weight. The total parameter count is literally the sum of how many such numbers exist across the entire model.
32 Scale & training

Model size

Intuition first
Model size usually refers to total parameter count, which correlates with — but doesn't perfectly determine — capability. Data quality/quantity and training technique matter enormously too, which is why a well-trained smaller model can sometimes outperform a poorly-trained larger one.
Interview angle
"Bigger is better" was the dominant intuition for a while (scaling laws showed predictable gains with more parameters and data), but the field has shifted toward recognizing that data quality and post-training technique can let smaller models compete with larger ones on many practical tasks.
Interview question
Is a model with more parameters always better than one with fewer?
Show a strong answer
Not necessarily — parameter count correlates with raw capability potential, but training data quality/quantity and post-training technique matter enormously too. A well-trained smaller model can outperform a poorly-trained larger one, especially on narrow tasks.
33 Scale & training

Pre-training

Intuition first
Pre-training is the initial, massive training phase where a model learns from a huge corpus of mostly-unlabeled text using next-token prediction — no instructions, no chat format, just raw text. This is where the vast majority of a model's raw knowledge, grammar, and reasoning capability comes from.
Diagram
Massive raw text corpus→ Next-token prediction training→ Pre-trained "base" model
Interview question
What does a freshly pre-trained "base" model actually behave like, before any further training?
Show a strong answer
It's good at predicting plausible continuations of text, but not necessarily good at FOLLOWING INSTRUCTIONS — asked a question, it might continue it as if it were an exam question followed by more questions, rather than answering it, since that's also a plausible continuation in its training data.
34 Scale & training

Instruction tuning

Intuition first
Instruction tuning fine-tunes the base model on examples formatted as (instruction, desired response) pairs — teaching it the BEHAVIOR of actually answering questions helpfully, rather than just continuing text plausibly. This is the step that turns a raw text-predictor into something that behaves like an assistant.
Diagram
Base model+ (instruction, response) examples→ Instruction-following model
Interview question
Why does a model need instruction tuning at all, if pre-training already taught it so much about language?
Show a strong answer
Pre-training teaches the model to predict plausible text continuations, which isn't the same behavior as answering a question helpfully and directly. Instruction tuning specifically trains the behavioral pattern of responding to an instruction the way a helpful assistant would, using curated examples of exactly that behavior.
35 Scale & training

RLHF

Intuition first
RLHF (Reinforcement Learning from Human Feedback) further refines behavior using human preference data: humans compare pairs of outputs and say which they prefer, a "reward model" learns to predict those judgments, and the main model is then trained via reinforcement learning to produce outputs the reward model scores highly.
Diagram
Human preference comparisons→ Train reward model→ RL fine-tuning
Interview question
Why is RLHF considered an additional step beyond instruction tuning, rather than a replacement for it?
Show a strong answer
Instruction tuning teaches the basic behavior of following instructions using explicit examples, but doesn't capture more nuanced human preferences about style, helpfulness, or safety that are hard to specify as a fixed set of example responses. RLHF uses comparative human judgments to further shape behavior, refining rather than replacing instruction tuning.
36 Scale & training

DPO concept

Intuition first
DPO (Direct Preference Optimization) achieves a similar GOAL to RLHF — aligning a model with human preferences — without training a separate reward model or running full reinforcement learning. It directly optimizes on pairs of (preferred, dispreferred) responses using a more straightforward, supervised-learning-style loss.
Interview question
What's the practical advantage of DPO over classic RLHF?
Show a strong answer
DPO achieves similar preference-alignment goals without the complexity and instability of training a separate reward model and running full reinforcement learning — it directly optimizes on preference pairs with a simpler loss, making the training pipeline more stable in practice.
37 Scale & training

Fine-tuning

Intuition first
Fine-tuning, generally, means taking an already-trained model and training it FURTHER on a smaller, specific dataset to adapt its behavior — either updating ALL parameters (full fine-tuning, expensive) or just a small added subset (parameter-efficient fine-tuning, next topics).
Diagram
Pre-trained model+ domain-specific examples→ Specialized model
Interview question
How does fine-tuning relate to instruction tuning and RLHF — are they the same thing?
Show a strong answer
Instruction tuning and RLHF are both specific kinds of fine-tuning — fine-tuning is the general umbrella term for any further training on top of a pre-trained base model, with different data and objectives for each specific variant.
38 Scale & training

LoRA

Intuition first
LoRA (Low-Rank Adaptation) fine-tunes a model WITHOUT updating its original weights at all. Instead, it adds small, separate "adapter" matrices alongside the original weights, and only those small matrices get trained — the original, much larger weights stay completely frozen.
Diagram
Frozen original weights+ small trainable LoRA adapters→ combined effective behavior
LoRA's modification
output = Wx + (B·A)x    (W frozen; A, B small and trainable)
Interview angle
Because the original weights never change, you can keep ONE copy of the base model in memory and swap between many different LoRA adapters cheaply — a genuinely practical production benefit, not just a training-time optimization.
Interview question
Why does LoRA make it practical to serve many different fine-tuned variants of the same base model?
Show a strong answer
Because LoRA leaves the original weights frozen and only adds small adapter matrices, you can keep a single copy of the expensive base model in memory and swap in different, much smaller adapter weights per task or customer — rather than needing a full separate copy of the entire model for each variant.
39 Scale & training

PEFT

Intuition first
PEFT (Parameter-Efficient Fine-Tuning) is the umbrella category of techniques — LoRA being the most popular — that adapt a model by training only a small number of additional or selected parameters, rather than the entire model.

The motivation across all PEFT methods is the same: full fine-tuning of a large model requires enormous GPU memory (storing gradients and optimizer state for every parameter) and storage per variant; PEFT dramatically reduces both.

Interview question
What's the relationship between PEFT and LoRA?
Show a strong answer
PEFT is the general category of techniques for adapting a model by training only a small subset of parameters; LoRA is the most widely used specific PEFT technique, but other methods (prefix tuning, adapter layers, prompt tuning) also fall under the same umbrella, sharing the same motivation.
40 Scale & training

Quantization

Intuition first
Quantization reduces the numerical precision used to store a model's weights — from 16-bit or 32-bit floating-point down to 8-bit or even 4-bit — shrinking memory footprint substantially (often 2-4x or more) at some cost to precision.
Diagram
Full precision (32-bit)→ Quantization→ Reduced precision (8-bit / 4-bit)
Interview question
Why does reducing a model's numerical precision not destroy its usefulness entirely?
Show a strong answer
Neural network weights are generally robust to small amounts of numerical imprecision — behavior emerges from the aggregate pattern across millions or billions of weights, not any single weight's exact value. Quality typically degrades gradually, not catastrophically, until very aggressive quantization.
41 Scale & training

Inference

Intuition first
Inference is simply RUNNING a trained model to produce output, as opposed to TRAINING it — a forward pass through the network, with no weight updates happening at all.

In production, "inference" covers everything that happens when a request gets a response: tokenize the input, run it through the model (using the KV cache for generation), sample the output, detokenize back to text.

Diagram
User input→ Tokenize→ Forward pass(es)→ Sample + detokenize
Interview question
What's the difference between training and inference, in terms of what's actually computationally happening?
Show a strong answer
Training computes a forward pass AND a backward pass (gradients, weight updates) across many examples repeatedly. Inference only computes a forward pass for a given input, with no weight updates — a read-only use of the already-trained model.
42 Scale & training

Open-source vs. proprietary models

Intuition first
Open-weight models (Llama, Mistral) release their trained parameters publicly — anyone can download, run, inspect, and fine-tune them on their own infrastructure. Proprietary models (GPT, Claude, Gemini) are only accessible via API — you get a response, never the weights themselves.
Open-weight
  • Self-hostable — data never leaves your infrastructure
  • Full customization via fine-tuning
  • Requires real ML infrastructure expertise to run well
Proprietary
  • Often at the raw capability frontier
  • Zero infrastructure management — just an API call
  • Data leaves your control; ongoing usage cost; no internals access
Interview question
What's the real trade-off a company faces when choosing between an open-weight model and a proprietary API?
Show a strong answer
Control and data locality versus convenience and often raw capability — open-weight models can be self-hosted with full customization but require real ML infrastructure expertise; proprietary APIs are operationally simple and often at the frontier, but involve ongoing cost, sending data to a third party, and no ability to inspect or modify the model.
Worked example

A full numerical attention example, by hand

Three tiny tokens, 2-dimensional vectors, real arithmetic. This is the exact same computation a real model does with 4096-dimensional vectors and 100,000 tokens — just small enough to check every step with a calculator.

Three tokens: "I", "love", "AI". Skipping the embedding/projection step for clarity, here are their (made-up, hand-picked for clean numbers) Query, Key, and Value vectors directly:

TokenQueryKeyValue
"I"[1, 0][1, 0][1, 2]
"love"[0, 1][0, 1][3, 1]
"AI"[1, 1][1, 1][2, 2]

We'll compute the new representation for "AI" (token 3) attending over all three tokens.

Step 1 — raw scores: Query(AI) · Key(each token)

score("AI","I")  = [1,1]·[1,0] = 1
score("AI","love") = [1,1]·[0,1] = 1
score("AI","AI")   = [1,1]·[1,1] = 2

Step 2 — scale by √d_k (d_k = 2, so √2 ≈ 1.414)

0.707,   0.707,   1.414

Step 3 — softmax → attention weights

"I"
0.248
"love"
0.248
"AI"
0.504

Step 4 — weighted sum of Value vectors

0.248·[1,2] + 0.248·[3,1] + 0.504·[2,2] = [2.00, 1.75]

That final vector, [2.00, 1.75], is "AI"'s new, attention-updated representation — a blend of all three tokens' Value vectors, weighted by how relevant each one was judged to be. Notice "AI" attends most to itself (0.504) here purely because its Query and Key happened to produce the highest score — in a real trained model, these numbers come from millions of training examples shaping the Wq/Wk/Wv matrices, not from hand-picked values like this toy example.

Why, explained

Why GPT is decoder-only

GPT's core task is open-ended text generation — continue this text indefinitely, in any domain — rather than a well-defined "transform input X into output Y" task like translation. A decoder-only architecture, trained purely on next-token prediction over massive diverse text, is the architecturally simplest fit for "generate text that continues from whatever came before," without the structural assumption of a fixed input/output split that encoder-decoder models bake in.

Decoder-only also scales more simply — one stack, one training objective — which made it easier to scale up to enormous size and data, a major factor in why GPT-style models pulled ahead in raw generative capability as scale increased.

Because a decoder-only model treats prompt and response as one continuous sequence, it naturally handles flexible, varied input (chat-formatted conversations, few-shot examples, arbitrary mixed content) without redesigning the architecture for each new usage pattern. The SAME architecture handles translation, summarization, coding, and chat, all as "predict the next token given everything so far" — whereas an encoder-decoder's structural split is more naturally suited to tasks that genuinely have a distinct input and output.

Why, explained

Why Transformers replaced RNNs

RNNs process a sequence one token at a time, feeding each step's hidden state into the next. This creates two real problems: processing is inherently SEQUENTIAL, so you can't parallelize across the sequence during training, making it brutally slow at today's dataset sizes; and information from early in a long sequence has to survive being passed through many sequential steps to influence predictions much later, tending to degrade or vanish — the "long-range dependency" problem, even with LSTM/GRU variants designed to mitigate it.

Self-attention solves both at once: every token can attend directly to every other token in a SINGLE step regardless of distance, and the whole computation can be parallelized on GPU hardware — the practical unlock that made training at today's scale feasible in reasonable time.

Why, explained

Why attention is powerful

Attention lets the model dynamically decide, for every token and every input, exactly which OTHER tokens matter most for understanding this one — and that decision is LEARNED and CONTEXT-DEPENDENT, not fixed. The word "bank" attends to completely different other words depending on whether the sentence is about a river or about money, and the model figures out which tokens to weight heavily purely from learned Query/Key matching, not a hard-coded rule.

This dynamic, content-based routing of information is categorically more flexible than earlier fixed mechanisms, like a convolution that always looks at the same fixed set of neighboring positions regardless of content. Attention looks wherever the content says to look.

Why, explained

Why context windows matter

The context window is the ENTIRE world the model can see for a given request — anything not included, whether a long document, earlier conversation turns, or relevant background information, functionally doesn't exist for that forward pass.

This has direct, practical consequences for anyone building on top of an LLM: it bounds how much retrieved context a RAG system can include, how much conversation history a chatbot can "remember" without summarization, and how large a codebase or document an agent can reason about in one shot. Context window size is frequently the actual hard constraint shaping an application's architecture, more than raw model capability is.

Interview prep

Explain it in an interview

Six scripts worth practicing out loud until they feel natural, not memorized. Interviewers are listening for structure and confidence, not word-for-word recall.

Explain the Transformer in 2 minutes

"A Transformer is built around one core idea: self-attention, which lets every token directly look at every other token and decide how relevant each one is, rather than processing tokens one at a time in order like older RNN-based models did.

The pipeline: input text is split into tokens, each becomes a vector via embedding lookup, and since attention has no inherent sense of order, positional information gets added in.

Then the real work happens in a stack of identical Transformer blocks, dozens of them. Each block has two parts: self-attention — every token computes a Query, Key, and Value, compares its Query against every other token's Key for attention scores, turns those into weights with softmax, and blends every other token's Value into its own new representation — and a feed-forward network that processes each token's updated vector independently. Both parts are wrapped in residual connections and layer normalization, which is what makes stacking so many blocks trainable.

Multiple heads of attention run in parallel, so the model tracks several kinds of relationships at once.

After the final block, the model projects each position's vector into a score for every possible next token — logits — and softmax turns those into a probability distribution to sample from.

That's the whole thing: embed, add position, repeatedly attend and process, predict the next token."

Explain attention in 1 minute

"Attention lets each token figure out which other tokens are relevant to it, and pull information from those specifically — rather than treating all context equally or only looking at fixed nearby positions.

Concretely: every token produces a Query (what am I looking for) and a Key (what do I represent). Compare one token's Query against every other token's Key — a dot product — for a raw relevance score per pair. Softmax turns those into weights summing to 1. Use those weights to compute a weighted average of every token's Value — the actual content — and that average becomes the token's new representation.

The key insight: which tokens matter is decided dynamically, based on content, not by a fixed rule."

Explain LLM inference

"Inference is running the already-trained model to generate a response — no learning happens, only a forward pass.

For one request: tokenize the input, convert to embeddings plus positional info, run it through the full Transformer stack, producing logits for the next token. Softmax (optionally reshaped by temperature) turns those into probabilities, a sampling strategy picks one token, and it gets appended to the sequence.

Then the whole process repeats for the next token — except the KV cache lets the model reuse the Key/Value vectors it already computed for every earlier token, so it only does fresh computation for the newest one. This repeats until a stop condition is met.

So: tokenize once, then loop — forward pass, sample, append — until done, with the KV cache making each loop iteration cheap."

RAG vs. fine-tuning

"RAG changes WHAT information the model has access to, by retrieving relevant content into the prompt at request time. Fine-tuning changes the model's weights, baking new behavior or knowledge directly in through additional training.

Use RAG when knowledge changes often, needs attribution, or needs per-user scoping. Use fine-tuning when you need to change HOW the model behaves — format, tone, domain reasoning — not just what facts it knows. Many systems use both."

Fine-tuning vs. prompt engineering

"Prompt engineering changes nothing about the model — it's entirely about how you phrase the input to get better behavior from a frozen model. Fast to iterate, always the first thing to try.

Fine-tuning actually changes the model's weights, achieving more reliable, deeply ingrained behavior changes than prompting alone — especially for narrow, repetitive tasks — but costs real time, data, and compute.

Practical order: try prompt engineering first; reach for fine-tuning when prompting hits a measured reliability ceiling, not preemptively."

LoRA vs. full fine-tuning

"Full fine-tuning updates every parameter, requiring gradients and optimizer state for the entire model — extremely memory-hungry, with a complete separate model copy per variant.

LoRA freezes the original weights and only trains small added adapter matrices — a tiny fraction of parameters, far less memory to train, and a tiny adapter file per variant instead of a full model copy. You can keep one base model loaded and swap adapters cheaply at serving time.

Trade-off: full fine-tuning has more raw capacity to change behavior since every weight can move; LoRA is constrained to what its low-rank adapters can express — usually sufficient, but can hit a ceiling for very large behavior changes."
