The foundation of every production RAG system

Text becomes numbers. Meaning becomes geometry. Search becomes distance.

An embedding maps a piece of text to a point in high-dimensional space, where nearby points mean similar things. Everything else in RAG — chunking, vector databases, ANN indexes, hybrid search, reranking — exists to make "find the nearby points" fast, accurate, and production-grade at scale.

Built for a backend engineer: expect real formulas, real trade-offs, real Python, and a full head-to-head of pgvector, Pinecone, Qdrant, Weaviate, and Azure AI Search.

A query goes through the same embedding model (topic 34), lands in the same vector space, and the database finds documents whose vectors are close to it (topics 7–10). Everything from here is about doing that reliably at production scale.

01 Embeddings fundamentals

What are embeddings?

An embedding is a fixed-length list of numbers — a vector — that represents the meaning of a piece of text, produced by a neural network trained so that semantically similar inputs produce numerically similar vectors. Think of it as a deterministic function float[] embed(String text): the same input always gives the same output vector for a given model, and that vector — never the raw text — is what you actually store, index, and search over.

"The cat sat on the mat" and "a feline rested on the rug" would produce vectors that land close together despite sharing almost no words, because the model captures meaning, not surface tokens.

Production note
An embedding is only as good as the model that produced it. A vector from one model is NOT compatible with a vector from a different model — or even a different version of the same model. Mixing them silently corrupts similarity search with no error thrown (more in topic 4).
Interview question
How would you explain an embedding to someone who's never touched machine learning?
Show a strong answer
It's a GPS coordinate for meaning. Instead of latitude/longitude placing a location on a map, an embedding places a piece of text on a "meaning map," where things that mean similar things end up near each other — and you measure how similar two things are by measuring the distance between their coordinates.
02 Embeddings fundamentals

Why text needs to be converted into vectors

Computers compare numbers efficiently — distance, sorting, indexing — but have no native way to compare "meaning" in raw text. String equality or substring matching only catches exact wording, missing paraphrases, synonyms, and related concepts entirely. Converting text into vectors moves the problem from "do these strings match" to "how far apart are these two points" — a well-understood geometric problem with decades of fast algorithms behind it.

A traditional keyword search for "cancel my subscription" won't match a document that says "how to end your membership" — no shared words — but their embeddings land close together because the underlying meaning overlaps.

Trade-off
Vectorizing enables semantic matching, but loses exact-match guarantees — a vector search might rank a loosely related document above an exact keyword match. This is exactly why production systems often combine both (hybrid search, topic 30) rather than replacing keyword search outright.
Interview question
Why can't you just use a SQL LIKE '%keyword%' query for a "smart search" feature?
Show a strong answer
LIKE only catches exact substring matches — it has no notion of meaning, so it misses synonyms, paraphrases, and related concepts entirely. Vectorizing text into embeddings and comparing distances captures semantic relatedness, at the cost of needing a whole new kind of index — a vector index — to search efficiently.
03 Embeddings fundamentals

Semantic representation

"Semantic" means meaning-based. A semantic representation encodes what a piece of text is about, not which characters or words it contains — captured implicitly by a model trained on massive text corpora to place related concepts near each other in vector space, as a side effect of learning to represent language well.

The classic demonstration: in well-trained embedding spaces, the vector arithmetic king − man + woman lands close to queen — the space has implicitly learned a "royalty" direction and a "gender" direction as separate, combinable axes of meaning.

Trade-off
Semantic representation is powerful but opaque — you can't inspect an embedding's 1,536 numbers and know what "concept" dimension 47 represents. This makes embeddings hard to debug directly, which is why practical debugging focuses on input/output behavior (does this query retrieve the right documents?) rather than inspecting vector internals.
Interview question
If two texts share zero words in common, can their embeddings still be highly similar? Why?
Show a strong answer
Yes — embeddings encode meaning, not vocabulary overlap, so two paraphrases with completely different word choices can land very close together in vector space. That's exactly the property that makes semantic search more powerful than keyword matching for natural-language queries.
04 Embeddings fundamentals

Embedding models

An embedding model is the specific neural network that performs the text→vector conversion. Different models — OpenAI's text-embedding-3, Azure OpenAI's equivalent deployments, open-source models like BGE or E5, Cohere's embed models — produce different vector spaces with different dimensionality, training data, and quality/cost/speed trade-offs. A vector from one model has no meaningful relationship to a vector from another.

LARGER PROPRIETARY MODELS
Capture more nuance at higher cost/latency — a reasonable default when quality matters most and you're comfortable with an API dependency.
SMALLER / SELF-HOSTED MODELS
Give cost and privacy control at some quality cost — worth it when data can't leave your infrastructure or volume makes per-call pricing unworkable.
Production note
The single most common production bug in RAG systems: embedding queries and documents with different models, or different versions of the same model. The resulting vectors live in incompatible spaces, and similarity scores become meaningless garbage — with no error thrown. Pin and version your embedding model choice exactly like a critical library dependency.
Interview question
Your RAG search quality degraded significantly overnight with no code changes. What's one of the first things you'd check?
Show a strong answer
Whether the embedding model or its version changed underneath you — a provider silently updating a default model alias, for example. Even a minor version change can shift the vector space enough that previously-stored document embeddings no longer align well with newly-generated query embeddings, and re-embedding the full document set is often the actual fix.
05 Embeddings fundamentals

Dimensions

Dimensionality is the length of the vector an embedding model produces — common sizes range from a few hundred to a few thousand (384, 768, 1536, 3072). Each dimension is one axis in the model's learned meaning space: more dimensions can capture more nuance, but cost more storage, memory, and compute for every downstream distance calculation.

Trade-off
Higher dimensionality generally means better semantic fidelity but higher storage cost — a 3072-dim float32 vector is 12KB; multiply by millions of chunks — and slower search unless the index compensates. Many providers now offer dimension-reduction options, returning a shorter, cheaper vector that trades a bit of accuracy for major storage and speed savings.
Production example
A team storing 50 million document chunks chose a 768-dimension model over a 3072-dimension one specifically to keep index size and query latency within budget, accepting a small, measured accuracy trade-off validated against their eval set.
Interview question
Would you always pick the embedding model with the highest dimensionality? Why or why not?
Show a strong answer
No — higher dimensionality trades off directly against storage cost, memory footprint, and query latency at scale. The right choice depends on measuring actual retrieval accuracy on your own data against those costs, since a marginal accuracy gain from more dimensions may not be worth doubling your storage and search cost at production volume.
06 Embeddings fundamentals

Vector space

Vector space is the abstract N-dimensional coordinate system that all embeddings from a given model live in — every chunk of text you've ever embedded with that model becomes one point in this same shared space, which is precisely what makes comparing any two of them (query vs. document, document vs. document) a well-defined geometric operation.

Distance and direction in this space are meaningful with respect to semantic relationships — but only within the same model's space. You cannot meaningfully compare a point from one model's space to a point from a different model's space, since the axes themselves mean different things.

Production note
Because the space is defined by training data, it inherits whatever biases, blind spots, or coverage gaps existed in that data. A general-purpose model may represent common web-text concepts well but poorly capture a company's internal jargon — a real driver behind fine-tuned or domain-specific embedding models.
Interview question
What does it actually mean, mechanically, for a vector database to "search" this vector space?
Show a strong answer
It means taking the query's vector — one point in the space — and finding the stored document vectors that are closest to it by some distance metric. Geometrically, it's identical to the classic nearest-neighbor search problem from computational geometry, just applied to a space with hundreds or thousands of dimensions instead of 2 or 3.
07 Similarity & distance

Similarity

Similarity is the general umbrella term for "how close are two vectors" — the actual number that comes out of comparing two embeddings, computed via one of several metrics (cosine similarity, Euclidean distance, dot product), each with different mathematical properties and different appropriateness depending on the embedding model and use case.

"Similar" in vector space doesn't mean "identical in wording" — it means "nearby in the model's learned meaning space," a different and often more useful notion of similarity for search than exact or fuzzy string matching.

Trade-off
Different metrics can produce different rankings of the same candidate documents for the same query. Choosing the wrong metric for a given embedding model — e.g. raw dot product on non-normalized vectors when the model expects cosine similarity — is a subtle, easy-to-miss production bug that silently degrades search quality.
Interview question
If two similarity metrics disagree about which of two documents is "more similar" to a query, is one of them simply wrong?
Show a strong answer
Not necessarily — different metrics capture different geometric properties (angle vs. straight-line distance vs. magnitude-sensitive alignment), so disagreement can reflect a genuinely different, valid notion of "closeness." What matters in practice is which metric the embedding model was actually trained/intended for, since using the wrong one can degrade quality even when the metric itself is mathematically valid.
08 Similarity & distance

Cosine similarity

Cosine similarity measures the cosine of the angle between two vectors, ignoring their magnitude entirely. It answers "do these two vectors point in the same direction" — which aligns remarkably well with "do these two pieces of text mean similar things," since most modern text embedding models are specifically trained and normalized for this metric.

Formula
cos(θ) = (A · B) / (‖A‖ × ‖B‖)

Ranges from −1 (opposite direction) to 1 (same direction). 0 means perpendicular — unrelated.

Because it ignores magnitude, cosine similarity is naturally robust to differences in text length — a short sentence and a long paragraph about the same topic can still point in a similar direction even if their raw vector magnitudes differ, which matters a lot for real documents of varying length.

Try it
Jump to the interactive cosine similarity visualizer in the Interactive Labs section to see the angle and the score move together in real time.
Interview question
Why is cosine similarity generally preferred over raw Euclidean distance for comparing text embeddings?
Show a strong answer
It's magnitude-invariant — it only cares about direction, which corresponds to semantic orientation regardless of how "long" or "intense" the vector happens to be. Most embedding models are trained with this exact property in mind, whereas Euclidean distance is sensitive to magnitude differences that don't necessarily reflect a meaningful semantic difference.
09 Similarity & distance

Euclidean distance

Euclidean distance measures the straight-line, "as the crow flies" distance between two points in vector space — the familiar Pythagorean distance generalized to N dimensions. Unlike cosine similarity, it's sensitive to both direction and magnitude: two vectors pointing the same direction but with very different lengths will have a nonzero Euclidean distance even though their cosine similarity would be 1.

Formula
d(A, B) = √( Σ (Aᵢ − Bᵢ)² )
USE WHEN
Magnitude genuinely carries meaning for your embedding model or use case — some specialized or non-text (image/audio) embeddings encode signal in vector length.
AVOID WHEN
Your embedding model was designed and normalized around cosine similarity — most standard text-embedding models fall here.
Production note
Using Euclidean distance on embeddings designed for cosine similarity can subtly distort rankings by introducing sensitivity to magnitude differences the model wasn't controlling for. Always check what metric an embedding model's documentation actually recommends rather than assuming.
Interview question
Two vectors point in exactly the same direction but have different lengths. What would cosine similarity say, and what would Euclidean distance say?
Show a strong answer
Cosine similarity would be 1 (identical direction, magnitude-invariant), while Euclidean distance would be nonzero and grow larger the more their lengths differ. The same two vectors can look "identical" under one metric and "different" under another — exactly why metric choice matters and isn't just a stylistic detail.
10 Similarity & distance

Dot product

The dot product is the sum of the element-wise products of two vectors. Mathematically, it's the numerator inside the cosine similarity formula, before dividing out the magnitudes — so used alone, it's sensitive to both the angle between vectors and their magnitudes.

Formula
A · B = Σ (Aᵢ × Bᵢ)

Some vector databases and embedding models specifically pre-normalize vectors to unit length. In that special case, dot product and cosine similarity become mathematically identical — dividing by a magnitude of 1 changes nothing — and computing a raw dot product is cheaper than computing full cosine similarity, which is why some production systems default to it purely as a performance optimization.

Production note
Using dot product on vectors that are NOT normalized silently reintroduces magnitude sensitivity, distorting rankings in a way that looks like a "quality" bug but is actually a metric-mismatch bug. Always confirm whether your vectors are normalized before choosing dot product as your similarity metric.
Interview question
Why would a production system deliberately choose dot product over cosine similarity, given they can produce different results?
Show a strong answer
If the vectors are already normalized to unit length, dot product and cosine similarity are mathematically equivalent, but dot product is computationally cheaper — it skips the magnitude-normalization division at query time. Some vector databases and embedding models are specifically designed around this shortcut, trading algorithmic simplicity for measurable throughput gains at scale.
11 Search & chunking

Semantic search

Semantic search is the retrieval technique that uses embeddings and vector similarity — rather than keyword matching — to find documents whose meaning matches a query, even when the wording differs substantially. It's the direct practical application of everything in topics 1–10: embed the query with the same model used for documents, compute similarity against every stored document vector, and return the top-k most similar.

Trade-off
Semantic search excels at conceptually related queries but can underperform on queries that hinge on an exact term — a product SKU, an error code, a proper noun — where keyword matching is actually more reliable. This is the core motivation for hybrid search (topic 30).
Interview question
When would semantic search alone give a WORSE result than plain keyword search?
Show a strong answer
When the query's value comes from an exact token match rather than conceptual meaning — an error code, a part number, a legal clause number — semantic search may return conceptually related but factually wrong results, while a keyword match would find the exact string reliably. Production retrieval usually combines both rather than choosing one exclusively.
12 Search & chunking

Chunking

Chunking is splitting a long document into smaller pieces before embedding. A single embedding vector represents an entire input as ONE point — cramming a 50-page document into one vector would average away most of its specific content. Smaller, focused chunks each get their own vector, preserving more granular, retrievable meaning.

The chunk is the actual unit of retrieval in a RAG system — when a query matches, you get back chunks, not whole documents, so chunk boundaries directly determine what context the LLM sees.

Trade-off
There's no universally correct chunk size or strategy — it's one of the highest-leverage tuning decisions in a RAG system, and getting it wrong (too big, too small, boundaries that split key facts) is one of the most common root causes of poor retrieval quality in production.
Interview question
Why can't you just embed each entire document as a single vector and skip chunking?
Show a strong answer
A single vector has to represent everything in that document — for anything beyond a short document, that averaging destroys the specific detail needed to match a narrow query. Even if retrieval matched the right document, you'd have to feed the entire document into the LLM's context rather than just the relevant part, wasting context budget and diluting relevance.
13 Search & chunking

Chunk size

Chunk size is how large each chunk is, usually measured in tokens or characters — a direct trade-off between precision (smaller chunks are more narrowly focused, so a match is more likely to be genuinely relevant) and context (larger chunks preserve more surrounding information, reducing the risk a key fact gets cut off mid-thought).

TOO SMALL
Chunks lose surrounding context needed to make sense of an isolated fact — a chunk that's just "45%" with the sentence explaining what it refers to cut into a different chunk.
TOO LARGE
Multiple unrelated topics get crammed into one chunk, diluting its embedding's relevance to any single query and wasting context budget when retrieved.
Production note
Many systems start around 200–500 tokens per chunk and tune from there based on measured retrieval quality on their own eval set — there's no universal "correct" number, only one that's been measured to work for a specific document type and query pattern.
Interview question
Your RAG system retrieves technically-matching chunks that lack enough context for the LLM to answer confidently. What would you investigate first?
Show a strong answer
Chunk size — if chunks are too small, they may capture an isolated fact stripped of the context needed to interpret it (a number without its subject, a pronoun without its referent). Increasing chunk size, or increasing overlap so more surrounding context survives into each chunk, is often the first thing to test against your eval set.
14 Search & chunking

Chunk overlap

Chunk overlap means adjacent chunks share a bit of text at their boundary — e.g. the last 50 tokens of chunk N are repeated as the first 50 tokens of chunk N+1 — a deliberate redundancy that prevents a key sentence from being split awkwardly across two chunks with neither half retrievable on its own.

Trade-off
More overlap reduces the risk of losing context at boundaries, but increases total storage (content duplicated across chunks) and can slightly dilute distinctiveness between adjacent chunks, since shared content makes their embeddings more similar to each other.
Production note
A common heuristic is roughly 10–20% of the chunk size as overlap — validate against an eval set rather than assume, since the right amount depends heavily on how densely information-packed your source documents are.
Interview question
What specific failure mode does chunk overlap protect against, mechanically?
Show a strong answer
A sentence or fact that would otherwise be split at exactly a chunk boundary, leaving half of it in one chunk and half in the next, with neither chunk containing the complete thought needed to answer a query about it. Overlap ensures content near a boundary appears complete in at least one of the two adjacent chunks.
15 Search & chunking

Sentence-based chunking

Sentence-based chunking splits text along actual sentence boundaries — rather than a fixed character or token count — and groups sentences together up to a target chunk size, respecting the natural grammatical unit of a sentence rather than cutting mid-sentence at an arbitrary character count.

Trade-off
Requires a reliable sentence-boundary detector — harder than it sounds, since abbreviations, decimal numbers, and quotations can confuse naive splitting on periods — and sentences vary wildly in length, so a "target chunk size" is only approximate when built by grouping variable-length sentences.
Interview question
What's a practical risk of naively splitting text on periods to detect sentence boundaries?
Show a strong answer
Periods appear in many places that aren't sentence endings — abbreviations ("Dr.", "e.g."), decimal numbers ("3.14"), initials — so a naive period-based splitter produces incorrect boundaries on real-world text. Production systems use a proper sentence-boundary detection library or model rather than a simple string split.
16 Search & chunking

Recursive chunking

Recursive chunking splits text hierarchically by trying a sequence of separators in order of preference — first double newlines (paragraphs), then single newlines, then sentences, then words — recursively subdividing any piece still too large after the current separator, until every resulting chunk fits the target size.

It's a pragmatic, general-purpose default that respects natural document structure without needing document-type-specific logic, which is why it's the default chunking strategy in many popular RAG frameworks.

Trade-off
It's a heuristic based on formatting characters (newlines), not actual meaning — a paragraph boundary doesn't guarantee a topic boundary, so recursive chunking can still occasionally split a coherent idea across chunks if the document's formatting doesn't align with its logical structure.
Interview question
Why is recursive chunking often a better default than naive fixed-character-count chunking?
Show a strong answer
It respects the document's existing structural boundaries (paragraphs, then sentences, then words) before falling back to a hard cut, so chunks are more likely to end at a natural break rather than mid-word or mid-sentence — while still guaranteeing every chunk fits the target size, unlike pure sentence-based chunking which can produce oversized chunks for very long sentences.
17 Search & chunking

Semantic chunking

Semantic chunking uses embeddings themselves to decide where chunk boundaries should go: it embeds individual sentences (or small groups), measures similarity between consecutive sentences, and inserts a boundary specifically where similarity drops significantly — signaling a topic shift — rather than using a fixed size or formatting rule at all.

Because boundaries end up aligned with actual topic shifts rather than an arbitrary character count, the resulting chunks are each more topically coherent, which can improve retrieval precision.

Trade-off
Computationally more expensive — it requires embedding at a finer granularity just to decide where to cut, before the "real" chunk embeddings are even created — and chunk sizes become inherently variable and unpredictable, complicating downstream context-budget planning compared to a fixed-size strategy.
Interview question
When would the extra cost of semantic chunking actually be worth it over a simpler recursive chunking strategy?
Show a strong answer
When measured retrieval quality shows topic-boundary misalignment from fixed-size chunking is a significant source of poor results — for example, densely-packed technical documents where topics shift frequently within what would otherwise be one paragraph. For more uniformly-structured documents, the simpler and cheaper recursive approach often performs comparably.
18 Metadata

Metadata

Metadata is structured information attached to a chunk alongside its vector — source document name, page number, section title, author, creation date, access-control tags, document type — stored as regular fields, not embedded into the vector itself, and retrievable/filterable independently of similarity search.

Vectors alone can't answer "only search documents from the last 30 days" or "only search documents this user is authorized to see" — that requires structured fields you can filter on directly, which is exactly what metadata provides alongside the vector.

Production note
Deciding what metadata to capture at ingestion time matters a lot: adding a new metadata field later usually means re-processing (or at least re-indexing) your entire existing document set — unlike a normal database schema migration, you can't always backfill cheaply if the original raw source isn't still available.
Interview question
Why store metadata alongside the vector rather than trying to encode everything into the embedding itself?
Show a strong answer
Embeddings capture fuzzy, semantic similarity — they're not designed for exact structured queries like date ranges, access control, or categorical filters, which need to be checked exactly, not approximately. Metadata fields let you combine fast exact filtering with fuzzy similarity search in the same query, each doing the job it's actually good at.
19 Metadata

Metadata filtering

Metadata filtering narrows a vector search to only chunks matching specific criteria, combined with the similarity comparison — e.g. "find the most similar chunks, but only among documents tagged category=HR and dated after 2024-01-01." It combines exact structured filtering with fuzzy semantic search in one query.

Nearly every real RAG application needs some form of scoping: multi-tenant systems filter by customer/organization ID (a security requirement, not just a relevance nicety), versioned systems filter out outdated documents, and permission-aware systems filter by what the requesting user can actually see.

Production note
Metadata filtering applied AFTER similarity search (filtering the top-k results) can silently return fewer results than requested if many top matches get filtered out. Better vector databases support filtering integrated into the index traversal itself (pre-filtering), which is more efficient and doesn't waste top-k slots on results that were always going to be filtered out.
Interview question
In a multi-tenant RAG application, why is metadata filtering by tenant/organization ID a security requirement, not just a relevance feature?
Show a strong answer
Without an enforced filter, a similarity search has no inherent concept of "which organization's data this is" — it will happily return the most semantically similar chunk regardless of tenant, meaning a query from one customer could retrieve another customer's private data purely because it's semantically similar. Metadata filtering enforced at the query layer — not just trusted to the LLM afterward — is what actually prevents that cross-tenant data leak.
20 Vector DBs & indexing

Vector databases

A vector database is a system specialized for storing embeddings and performing fast similarity search over millions or billions of them. The core problem it solves: a brute-force "compare the query to every stored vector" approach becomes too slow at real scale, so vector databases build specialized indexes that make similarity search approximately — not exhaustively — fast.

It's not a replacement for a regular database — most production systems still need a relational/document store for transactional data, and either use a purpose-built vector database alongside it, or add a vector extension to an existing database (like pgvector for PostgreSQL).

Trade-off
Purpose-built vector databases (Pinecone, Qdrant, Weaviate) are optimized for vector workloads and often offer more advanced indexing/filtering out of the box, at the cost of new infrastructure to operate. A vector extension on an existing database (pgvector) keeps operational surface area smaller, at some feature/performance ceiling at very large scale.
Interview question
Why can't you just use a regular relational database with a brute-force loop to do vector search?
Show a strong answer
At small scale you actually can — brute-force comparison against every row works fine for thousands of vectors. Comparing against millions or billions one by one becomes far too slow for real-time search, exactly the problem approximate nearest neighbor indexes (HNSW, IVF) are built to solve.
21 Vector DBs & indexing

Vector indexes

A vector index is the specialized data structure a vector database builds over stored vectors to make similarity search fast without comparing the query against every single stored vector — the vector-space equivalent of a B-tree index in a relational database, built around geometric/approximate nearest-neighbor structures instead of sorted keys.

Exact nearest-neighbor search in high-dimensional space is expensive, so approximate nearest neighbor (ANN) indexes trade a small, tunable amount of accuracy for a massive speedup — finding 9 of the true top 10 in milliseconds usually beats finding all 10 in seconds.

Trade-off
Every ANN index has tunable parameters trading recall (how often it finds the true nearest neighbors) against speed and memory. There's no free lunch — the right operating point depends on your latency budget and how sensitive your application is to occasionally missing a genuinely relevant chunk.
Interview question
What's the fundamental trade-off every vector index has to make, and why?
Show a strong answer
Recall versus speed/memory. Finding the exact true nearest neighbors reliably requires either comparing against everything (slow at scale) or building an index that approximates the search, occasionally missing a genuine match in exchange for being dramatically faster. This trade-off is tunable but never fully escapable in high-dimensional similarity search.
22 Vector DBs & indexing

Approximate nearest neighbor search

ANN search is the general class of algorithms vector indexes use to find "probably the closest" vectors to a query quickly, instead of "definitely the closest" vectors slowly — accepting a small, controlled chance of missing the true best match in exchange for search times that scale far better with data size.

Exact nearest-neighbor search in high-dimensional space suffers from the "curse of dimensionality" — as dimensions increase, the spatial-partitioning tricks that make exact search fast in low dimensions stop providing much speedup, so ANN approaches trade guaranteed correctness for practical speed instead.

Trade-off
How "approximate" you're willing to be is a tunable dial via index-specific parameters, letting you trade recall for latency. Most production systems tune this by measuring actual retrieval quality against actual query latency on real traffic patterns.
Interview question
Why does exact nearest-neighbor search become impractical as the number of dimensions grows, even though it's straightforward at low dimensions?
Show a strong answer
Spatial-partitioning techniques that make exact search fast in 2 or 3 dimensions lose effectiveness as dimensionality increases — points tend to become nearly equidistant from each other in very high-dimensional spaces, broadly known as the curse of dimensionality. Approximate methods that don't rely on those partitioning assumptions become necessary for practical performance.
23 Vector DBs & indexing

HNSW

HNSW (Hierarchical Navigable Small World) is one of the most widely-used ANN algorithms. It builds a multi-layered graph where each vector is a node connected to a handful of its nearest neighbors — searches start at a sparse top layer for a fast coarse jump toward the right neighborhood, then descend through progressively denser layers for fine-grained refinement, similar in spirit to a skip list but in high-dimensional space.

HNSW offers a strong recall/speed trade-off and supports incremental insertion of new vectors without a full index rebuild — it's the default or most common index type across pgvector, Qdrant, Weaviate, and many others.

Trade-off
HNSW's graph structure uses more memory than some alternatives (each node stores multiple neighbor connections across layers), and build/insert cost is higher than simpler index types — but for most RAG workloads, query-time speed and incremental-update support are worth it.
Interview question
Why is HNSW's ability to support incremental insertion important for a production RAG system, specifically?
Show a strong answer
Real document collections grow continuously — new tickets, new pages, new versions — and rebuilding an entire index from scratch every time new content arrives would be operationally painful and slow. HNSW's graph structure lets new vectors be added incrementally, matching how RAG systems actually receive data in production.
24 Vector DBs & indexing

IVF, at a conceptual level

IVF (Inverted File Index) takes a different approach: it first clusters all stored vectors into a fixed number of groups ("buckets," found via a clustering algorithm like k-means) based on their position in vector space, then at query time only searches within the few buckets whose centers are closest to the query — rather than checking every vector, or traversing a graph like HNSW.

IVF indexes tend to have a smaller memory footprint than graph-based approaches and can offer very fast search once built — often combined with vector compression techniques (like product quantization) for even further memory savings at very large scale.

Trade-off
The clustering step must be done over a representative sample of the data upfront, and the index doesn't handle continuously-arriving new data as gracefully as HNSW — heavy insertion without periodic re-clustering can degrade search quality as new data stops matching the original cluster boundaries well.
Interview question
In what scenario might you prefer IVF over HNSW, even though HNSW generally has strong recall?
Show a strong answer
At very large scale where memory footprint is the binding constraint and the dataset is relatively stable — not receiving a constant, high-velocity stream of new vectors. IVF's smaller memory footprint, especially combined with quantization, can be the deciding factor when a graph-based index's memory overhead becomes prohibitive.
25 Platforms

PostgreSQL + pgvector

pgvector is an open-source PostgreSQL extension adding a vector data type and similarity operators (<-> Euclidean, <#> negative dot product, <=> cosine distance) directly into Postgres — store embeddings as just another column, join them against your existing relational data, and query with regular SQL plus these operators, with HNSW and IVFFlat index support.

If your application already runs on PostgreSQL, pgvector means vector search doesn't require adopting a new database — you get transactional consistency between vector data and relational data, a genuine advantage since a document and its embedding can be inserted in the SAME transaction.

Interview question
What's the single biggest advantage of pgvector over a separate, purpose-built vector database, architecturally?
Show a strong answer
Transactional consistency and operational simplicity — vector data lives in the same database as relational data, in the same transactions, backed up by the same tooling, with no cross-system consistency problem to solve. The trade-off is a lower performance/feature ceiling at extreme scale compared to purpose-built alternatives.

Pinecone

Pinecone is a fully-managed, purpose-built vector database offered as a cloud service — you don't provision or manage servers or indexes directly; you push vectors and metadata via an API and Pinecone handles sharding, indexing, and scaling behind the scenes.

For teams wanting vector search working quickly without operating infrastructure, Pinecone's fully-managed model removes a large class of operational concerns — index tuning, cluster scaling, replication — at the cost of vendor lock-in and a recurring managed-service cost that scales with usage.

Interview question
What's the main trade-off a team accepts by choosing a fully-managed vector database like Pinecone over a self-hosted option?
Show a strong answer
Reduced operational burden — no cluster management, scaling, or index tuning to own — in exchange for less infrastructure control, a recurring cost tied to a specific vendor, and a genuine migration cost if you ever need to move away. A classic managed-service trade-off, applied to vector search.
27 Platforms

Qdrant

Qdrant is an open-source vector database (written in Rust), available both self-hosted and as a managed cloud offering, known for strong filtering capabilities — rich, structured metadata queries combined tightly with vector search — and a payload model that treats metadata as a first-class part of every point, not a bolted-on afterthought.

Teams that need both flexibility (self-host or managed cloud) and strong, efficient metadata filtering combined with vector search often reach for Qdrant specifically because filtering is a core capability rather than an add-on.

Interview question

Show a strong answer
When retrieval queries routinely need to combine vector similarity with several structured constraints at once — access control, category, date range — and that filtering needs to be efficient at the index level rather than a slow post-filter step. Qdrant's payload-first design is built specifically around that combined query pattern.

Teams wanting an integrated experience — schema definition, automatic embedding generation, hybrid search, and a structured query language all built in — rather than assembling separate pieces themselves often find Weaviate's more opinionated, batteries-included approach a good fit.

30 Hybrid & advanced retrieval

Hybrid search

Hybrid search combines keyword-based search (typically BM25, a well-established lexical scoring algorithm) with vector-based semantic search in a single query, then fuses the two separate rankings into one final result list — usually via Reciprocal Rank Fusion (RRF), which combines rankings without requiring the two very different score scales to be directly comparable.

Keyword and vector search have complementary weaknesses: keyword search misses paraphrases but nails exact terms; vector search captures meaning but can under-rank an exact required term. Hybrid search gets the benefits of both.

Trade-off
Running two search paths and fusing results adds complexity and some latency compared to a single path — worth it when measured retrieval quality shows a meaningful gain, which is common enough that hybrid search is close to a default best practice for production RAG rather than an advanced optimization.
Interview question
Why can't you just directly average a BM25 score and a cosine similarity score to combine keyword and vector results?
Show a strong answer
The two scores live on completely different, incompatible scales — BM25 is unbounded and corpus-dependent, cosine similarity is bounded between −1 and 1 — so a raw average would be dominated by whichever score happens to have a larger numeric range, not whichever result is more relevant. Rank-based fusion like RRF combines the rankings instead of raw scores, avoiding this scale-mismatch problem entirely.
31 Hybrid & advanced retrieval

Keyword search vs. vector search

Keyword search (BM25/TF-IDF-style) scores documents by exact term overlap, weighted by term rarity and frequency — fast, interpretable, excellent at exact-match scenarios, with zero understanding of synonyms or paraphrasing. Vector search scores by semantic similarity in embedding space — the reverse profile: strong at paraphrase/synonym matching, weaker at guaranteeing an exact required term appears.

LEAN ON KEYWORD SEARCH
Queries with must-have exact terms — part numbers, names, codes, exact phrases.
LEAN ON VECTOR SEARCH
Natural-language, conceptual queries where the "right" answer might use completely different wording.

In practice, most production systems don't have to choose — they run both (hybrid search, topic 30).

Interview question
Give a concrete example of a query where keyword search would outperform vector search, and one where the reverse is true.
Show a strong answer
Searching an exact error code like "ERR_CONN_04521" — keyword search finds the exact string reliably, while vector search might return conceptually related but wrong documents. Conversely, searching "how do I get a refund" against a document titled "Reversing a charge on your account" — vector search recognizes the semantic match despite zero shared words, while keyword search would likely miss it entirely.
32 Hybrid & advanced retrieval

Semantic ranking

Semantic ranking (a specific feature, notably in Azure AI Search) is an additional, separate re-scoring step applied AFTER an initial search retrieves a candidate set — using a more sophisticated language-understanding model to reorder those candidates by deeper contextual relevance, rather than relying solely on the initial retrieval scores.

Initial retrieval is optimized for speed over a large candidate pool; semantic ranking is optimized for accuracy over a much smaller candidate set — running a heavier model against the entire corpus for every query would be too slow. This "retrieve broadly, then rerank precisely" pattern is common in production.

Trade-off
Adds latency (an extra model pass) in exchange for improved ranking quality — usually worthwhile for RAG since a few milliseconds of added latency is a much smaller cost than the LLM generating a wrong answer from poorly-ranked context.
Interview question
Why would you run semantic ranking on only the top 50 initial results rather than the entire document collection?
Show a strong answer
Semantic ranking uses a more computationally expensive model than initial retrieval, so running it against every document for every query would be far too slow. Running it only against a smaller candidate set already narrowed by fast initial retrieval keeps the pipeline both fast and accurate — the classic two-stage retrieve-then-rerank pattern.
33 Hybrid & advanced retrieval

Reranking

Reranking is the general term for taking an initial set of retrieved candidates and reordering them using a different, typically more accurate (and more expensive) model or signal than whatever produced the initial ranking. Semantic ranking is one implementation; dedicated cross-encoder reranker models — which jointly process the query and each candidate document together, rather than comparing separately-computed embeddings — are another common approach.

A cross-encoder sees the query and candidate together in one pass, modeling fine-grained interactions two independently-computed embeddings can't capture — at the cost of being far too slow to run against an entire corpus, which is why it's used only as a reranking step over a small candidate set, never as primary retrieval.

Trade-off
Reranking reliably improves final ranking quality in most RAG systems, but adds a real latency and cost line item to every query — validate whether (and how aggressively) to rerank against your own eval set's measured improvement, not just because it's popular.
Interview question
Why is a cross-encoder reranker not used as the PRIMARY retrieval mechanism, even though it's often more accurate than embedding similarity?
Show a strong answer
A cross-encoder has to process the query jointly with EACH candidate document, so its cost scales with the number of documents compared — completely impractical against a full corpus of millions of documents per query. It's used only as a second-stage reranking step over the small candidate set a fast initial retrieval method has already narrowed down.
34 Retrieval pipeline

Query embedding

Query embedding is running the user's search query — not a document — through the same embedding model used for documents, at request time, to produce the vector compared against stored document vectors. It happens on every single request, unlike document embedding, which happens once at ingestion time.

Since vector spaces are model-specific, embedding the query with a different model — or even a different version — than what embedded the documents produces a vector in an incompatible space. Similarity scores become meaningless even though the code runs without error: one of the most common, hardest-to-detect production bugs in RAG.

Production note
Query embedding adds real per-request latency — an API call or model inference before vector search can even start. Measure it explicitly as part of your retrieval latency budget; it's easy to overlook when profiling only the vector database's search time.
Interview question
A RAG system's search results look completely unrelated to the query, despite documents being correctly embedded and stored. What's a likely root cause to check first?
Show a strong answer
Whether the query is being embedded with the same model (and version) used to embed the stored documents. A mismatch produces a vector in an incompatible space, so similarity scores become essentially meaningless noise even though no error occurs — exactly matching a symptom of "completely unrelated" results.
35 Retrieval pipeline

Document embedding

Document embedding is running each chunk of a document through the embedding model at ingestion time — when a document is added to the system — producing the vectors stored in the vector database ahead of any query. It's a batch, offline-ish process, distinct from the per-request query embedding step.

A large document collection might mean embedding millions of chunks once, versus one query per user request — document embedding is often the larger total cost, while query embedding is the larger per-request latency concern.

Production note
Documents change — new versions are published, old ones deleted or superseded — so a production system needs a defined re-embedding/re-indexing strategy for updated content, not just one-time initial ingestion. Stale embeddings for outdated versions are a real, recurring source of retrieval quality problems if this isn't actively managed.
Interview question
Your company's internal wiki gets updated constantly. What's the architectural implication for your RAG system's document embedding step?
Show a strong answer
You need an ongoing ingestion pipeline — not a one-time batch job — that detects changed or new content and re-embeds/re-indexes it, ideally removing or marking outdated chunks as stale. A RAG system serving embeddings from a months-old wiki snapshot will confidently retrieve and present outdated information as if it were current.
36 Retrieval pipeline

Retrieval pipeline

The retrieval pipeline is the full end-to-end system connecting every concept in this workbook: documents get chunked, each chunk is embedded and stored with metadata in a vector database behind an ANN index. At query time, the query is embedded with the same model, similarity search runs — often combined with keyword search for hybrid retrieval — candidates get filtered by metadata and optionally reranked, and the final top results are handed to the LLM as context.

Why it's the right level to debug at
So many stages can independently cause a retrieval quality problem — wrong chunk size, mismatched embedding models, a missing metadata filter, an overly strict similarity threshold — that production debugging almost always means isolating WHICH stage is actually failing, rather than assuming the LLM itself, at the very end of the chain, is the problem.
Production note
Every stage adds latency and has its own tunable parameters. A mature RAG team builds an evaluation set measuring end-to-end retrieval quality — not just individual-stage correctness — so any change (a new chunk size, a different index parameter, adding reranking) can be validated against real, measured impact rather than intuition.
Interview question
A user reports that the RAG chatbot "just doesn't know things it should know." Walk through how you'd debug this across the pipeline.
Show a strong answer
Start at the beginning and check each stage: was the relevant document actually ingested and chunked in a way that keeps the needed fact intact? Was it embedded and stored correctly? Does the query, once embedded, actually land near that chunk in vector space? Is a metadata filter accidentally excluding it? Only after confirming retrieval is actually surfacing the right chunk would you look at whether the LLM is failing to use correctly-retrieved context — in most real cases, the root cause is earlier in the pipeline, not the final generation step.

2. Calculating cosine similarity

similarity.py
import numpy as np

def cosine_similarity(a: list[float], b: list[float]) -> float:
    a, b = np.array(a), np.array(b)
    dot = np.dot(a, b)
    norm_a = np.linalg.norm(a)
    norm_b = np.linalg.norm(b)
    if norm_a == 0 or norm_b == 0:
        return 0.0
    return float(dot / (norm_a * norm_b))

query_vec = get_embedding("cancel my subscription")
doc_vec = get_embedding("how to end your membership")
score = cosine_similarity(query_vec, doc_vec)
print(f"similarity: {score:.4f}")   # e.g. similarity: 0.8734

3. Chunking documents

chunking.py
def chunk_text(text: str, chunk_size: int = 500, overlap: int = 50) -> list[str]:
    """Fixed-size chunking with overlap, splitting on word boundaries."""
    words = text.split()
    chunks = []
    step = max(1, chunk_size - overlap)
    i = 0
    while i < len(words):
        chunk_words = words[i:i + chunk_size]
        chunks.append(" ".join(chunk_words))
        if i + chunk_size >= len(words):
            break
        i += step
    return chunks

chunks = chunk_text(long_document_text, chunk_size=200, overlap=30)
print(f"produced {len(chunks)} chunks")

5. Searching vectors

search.py
def search_similar(query: str, top_k: int = 5):
    query_vec = get_embedding(query)
    cur.execute(
        """
        SELECT content, metadata, 1 - (embedding <=> %s::vector) AS similarity
        FROM document_chunks
        ORDER BY embedding <=> %s::vector
        LIMIT %s
        """,
        (query_vec, query_vec, top_k)
    )
    return cur.fetchall()

results = search_similar("how do I request time off?", top_k=3)
for content, metadata, similarity in results:
    print(f"{similarity:.4f}  {metadata}  {content[:60]}...")

def search_with_filter(query: str, category: str, top_k: int = 5):

7. Building a simple vector search system

Putting it all together: an in-memory engine implementing the same core ideas a production vector database implements at much larger scale.

simple_vector_search.py
import numpy as np

class SimpleVectorSearch:
    """A minimal, in-memory vector search engine."""

    def __init__(self, embed_fn):
        self.embed_fn = embed_fn
        self.vectors: list[np.ndarray] = []
        self.chunks: list[str] = []
        self.metadata: list[dict] = []

    def add_document(self, text: str, metadata: dict, chunk_size: int = 200, overlap: int = 30):
        for chunk in chunk_text(text, chunk_size, overlap):
            self.vectors.append(np.array(self.embed_fn(chunk)))
            self.chunks.append(chunk)
            self.metadata.append(metadata)

    def search(self, query: str, top_k: int = 3, filter_fn=None):
        query_vec = np.array(self.embed_fn(query))
        scores = []
        for i, vec in enumerate(self.vectors):
            if filter_fn and not filter_fn(self.metadata[i]):
                continue
            scores.append((cosine_similarity(query_vec, vec), i))
        scores.sort(reverse=True)
        return [
            {"score": s, "text": self.chunks[i], "metadata": self.metadata[i]}
            for s, i in scores[:top_k]
        ]

engine = SimpleVectorSearch(embed_fn=get_embedding)
engine.add_document(handbook_text, metadata={"source": "handbook.pdf", "category": "HR"})
engine.add_document(security_policy_text, metadata={"source": "security.pdf", "category": "IT"})

results = engine.search("how do I reset my password?", top_k=3,
                         filter_fn=lambda m: m["category"] == "IT")
for r in results:
    print(f"{r['score']:.4f}  {r['text'][:60]}...")

Azure focus

Azure AI Search deep dive

Since a large share of enterprise RAG systems get built on Azure, here's the platform in more depth than the comparison table above could hold.

Architecture

An Azure AI Search service hosts one or more indexes — schema definitions describing fields, their types (text, vector, filterable/facetable metadata), and how each field can be queried. A single index can hold plain text fields, one or more vector fields, and structured metadata fields side by side, so a single query can combine full-text, vector, and filter logic in one request rather than juggling separate systems.

Vector indexes

Vector fields in Azure AI Search are backed by an HNSW (or, in some configurations, exhaustive KNN for smaller datasets) index, configured with parameters like m (connections per node) and efConstruction/efSearch (build/query-time search breadth) — the same recall/speed trade-off dial described in topic 23, exposed directly as index configuration.

Hybrid search

A single query can include both a text query (scored with BM25) and a vector query (scored with cosine/similarity), with Azure AI Search fusing the two rankings — this is topic 30's Reciprocal Rank Fusion pattern, offered as a built-in query option rather than something you implement yourself.

Semantic ranking

An optional second-stage reranking layer that re-scores the initial result set using a deeper language-understanding model, producing a refined ranking plus (in many configurations) extractive captions and answers highlighting the most relevant passage — a direct implementation of the "retrieve broadly, then rerank precisely" pattern from topic 32, available as a request-time flag on top of an existing index.

Metadata filters

Fields marked filterable in the index schema can be filtered using OData filter syntax (e.g. category eq 'HR' and createdDate gt 2024-01-01), combined with the search query in the same request — the same metadata-filtering discipline from topics 18–19, expressed in Azure AI Search's specific filter syntax.

Integration with Azure OpenAI

Azure AI Search can call an Azure OpenAI embedding deployment directly as part of indexing (via a "vectorizer" configuration) and at query time, so query text can be sent as plain text and automatically embedded using the same configured model — reducing (but not eliminating) the risk of the query/document model-mismatch bug from topic 34, since both sides route through the same configured deployment.

hybrid_query.py — Azure AI Search hybrid + semantic query
from azure.search.documents import SearchClient

7. EvaluateWrite 10 test queries with a manually-verified "correct" expected chunk each. Measure how many your system actually retrieves in its top-3.
8. TuneChange ONE variable (chunk size, overlap, or top-k) and re-measure step 7 — did it help, hurt, or do nothing?
Definition of done
You can type a natural-language question unrelated to any exact keyword in your documents, and get back a relevant chunk in the top 3 results — with a measured accuracy number from step 7, not a vibe.

Reference

Cheat sheet

TermOne-line definition
EmbeddingA fixed-length vector representing the meaning of a piece of text.
Vector spaceThe shared N-dimensional coordinate system all of one model's embeddings live in.
Cosine similaritySimilarity based on the angle between two vectors; ignores magnitude.
Euclidean distanceStraight-line distance between two vectors; sensitive to magnitude.
Dot productSum of element-wise products; equals cosine similarity if vectors are normalized.
ChunkingSplitting a document into smaller pieces before embedding.
Chunk overlapShared text between adjacent chunks, protecting against boundary cuts.
Metadata filteringNarrowing a vector search using exact structured fields alongside similarity.
Vector databaseA system specialized for storing and searching embeddings at scale.
ANN searchApproximate nearest neighbor search — trades a little accuracy for a lot of speed.
HNSWA graph-based ANN index; strong recall/speed trade-off; supports incremental insertion.
IVFA clustering-based ANN index; smaller memory footprint; less graceful with streaming inserts.
Hybrid searchFusing keyword (BM25) and vector search rankings into one result list.
Reciprocal Rank FusionA rank-based method for combining two rankings without comparable score scales.
Semantic rankingA second-stage rerank of initial results using a deeper relevance model.
RerankingGeneral term for reordering retrieved candidates with a more accurate, more expensive signal.
Cross-encoderA reranker model that jointly processes query and candidate together.
Query embeddingEmbedding the search query, at request time, with the same model used for documents.
Curse of dimensionalityWhy exact nearest-neighbor search stops scaling well as dimensions increase.
Retrieval pipelineThe full chunk → embed → store → search → filter → rerank → LLM flow.
