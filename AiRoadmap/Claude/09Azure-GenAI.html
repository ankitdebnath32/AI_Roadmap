The big picture

The reference architecture, end to end

Every project in this workbook is a subset of this pipeline. Know what each box does and, just as importantly, when a simpler architecture wouldn't need it at all.

When do you actually need each box?

ComponentUse it when...Skip it when...
API ManagementYou need centralized auth, rate limiting, or multiple client types (web, mobile, partners) hitting the same backend.You have one internal client and the backend already handles auth — APIM adds latency and cost for no benefit.

Key VaultAlways, for any secret — this one isn't optional in production.Never skip it; use managed identity to avoid even needing Key Vault secrets for Azure-to-Azure calls.
P1 · 01 Azure OpenAI

Azure OpenAI architecture

Azure OpenAI Service hosts OpenAI's models (GPT-4o, embedding models, etc.) inside Azure's own infrastructure and security boundary. Architecturally, it's a regional Azure resource exposing REST endpoints — the same pattern as any other Azure Cognitive Services resource you've likely already consumed.

Unlike calling OpenAI's public API, every request stays within Azure's network boundary, authenticates via Entra ID or API keys, and is covered by Azure's compliance certifications, regional data residency, and networking controls (private endpoints, VNets) — the same controls you'd apply to any other Azure PaaS resource.

Java / Spring angle
Think of an Azure OpenAI resource exactly like any other managed Azure service you've consumed from a Spring Boot app — an endpoint plus credentials, wrapped by a client SDK. Same mental model as calling Cosmos DB or Azure SQL from your application layer.
Diagram
Subscription→ Resource Group→ Azure OpenAI resource→ Model deployment(s)
AoaiClient.java
OpenAIClient client = new OpenAIClientBuilder()
    .endpoint("https://my-resource.openai.azure.com/")
    .credential(new AzureKeyCredential(apiKey))
    .buildClient();
Version note
The resource type is sometimes still referenced as "Cognitive Services" in older docs/CLI output (kind=OpenAI) — current guidance increasingly refers to it directly as an "Azure OpenAI" resource. Check which generation of docs/SDK you're reading.
Interview question
How is an Azure OpenAI resource different, architecturally, from calling OpenAI's public API directly?
Show a strong answer
It's a regional Azure PaaS resource within your own subscription and network boundary — requests never leave Azure's network with private endpoints configured, authentication integrates with Entra ID/RBAC like any other Azure resource, and it's covered by Azure's compliance and data-residency guarantees, none of which apply calling OpenAI's public API directly.
P1 · 02 Azure OpenAI

Model deployment

You don't call a model directly by name — you first create a "deployment," assigning a name you choose to a specific model version with its own throughput allocation (capacity). Your application code calls the deployment name, not the underlying model name.

This indirection lets you swap which model version backs a deployment, or run multiple deployments side by side, without changing application code — just the deployment reference, or even keeping the same deployment name pointing at a newer model version.

Java / Spring angle
Directly analogous to aliasing a database connection pool name in application.yml while the underlying database engine version changes behind it — your code references a stable logical name, not the literal implementation detail.
application.yml
azure:
  openai:
    endpoint: https://my-resource.openai.azure.com/
    deployment-name: gpt-4o-chat-prod
Production note
Name deployments by PURPOSE (gpt-4o-chat-prod, gpt-4o-mini-classify) rather than literal model version, so a future model upgrade doesn't require an application code change — just a deployment update.
Interview question
Why does Azure OpenAI require creating a "deployment" rather than calling a model directly?
Show a strong answer
A deployment decouples your application's reference (a stable name you choose) from the specific underlying model version and its provisioned capacity — letting you swap model versions or scale capacity without changing application code that only references the deployment name.
P1 · 03 Azure OpenAI

Chat/completions concepts

The chat completions API is the core way to interact with GPT-family models: send a list of messages (system, user, assistant roles) and get back a generated assistant message. The legacy, pure "completions" API (plain text in, text continuation out) is largely superseded even for single-turn tasks, since modern deployed models are chat-tuned.

ChatExample.java
List<ChatRequestMessage> messages = List.of(
    new ChatRequestSystemMessage("You are a helpful assistant."),
    new ChatRequestUserMessage("What is Azure AI Search?")
);
ChatCompletions completions = client.getChatCompletions(
    "gpt-4o-chat-prod",
    new ChatCompletionsOptions(messages)
);
String reply = completions.getChoices().get(0).getMessage().getContent();
Interview question
Why would you use the chat completions API even for a single-turn, non-conversational task?
Show a strong answer
Modern deployed models are specifically tuned for the chat message format; using the legacy plain completions API with them either isn't supported or produces worse results, since the model wasn't primarily trained/tuned for that raw text-continuation interface.
P1 · 04 Azure OpenAI

Embeddings

Azure OpenAI also hosts embedding models (text-embedding-3-small/large, ada-002) through the same deployment mechanism — deployed separately from your chat model, with its own deployment name, called via a dedicated embeddings endpoint to convert text into vectors for semantic search, typically stored in Azure AI Search.

EmbedExample.java
EmbeddingsOptions embeddingsOptions = new EmbeddingsOptions(List.of("What is Azure AI Search?"));
Embeddings embeddings = client.getEmbeddings("text-embedding-3-small-deploy", embeddingsOptions);
List<Float> vector = embeddings.getData().get(0).getEmbedding();
Production note
The SAME embedding model/deployment must be used for both indexing documents and embedding queries at search time, or vector comparisons become meaningless. Pin the deployment name in configuration, not just the model family.
Interview question
Why do you need a SEPARATE deployment for an embedding model, distinct from your chat model deployment?
Show a strong answer
Embedding models and chat models are architecturally different models serving different purposes — a deployment is tied to one specific model, so generating embeddings and generating chat responses requires two separate deployments, even under the same Azure OpenAI resource.
P1 · 05 Azure OpenAI

Structured outputs

Structured outputs constrain a chat completion's response to conform to a JSON schema you define, so the output is reliably parseable into a specific structure — directly analogous to deserializing a REST response into a Java POJO, except here generation itself is constrained to match that shape, not just parsed after the fact.

StructuredOutput.java
ChatCompletionsOptions options = new ChatCompletionsOptions(messages);
options.setResponseFormat(new ChatCompletionsJsonSchemaResponseFormat(
    new ChatCompletionsJsonSchemaResponseFormatJsonSchema("TicketExtraction")
        .setSchema(BinaryData.fromObject(jsonSchemaMap))
        .setStrict(true)
));
Version note
Full structured-output schema enforcement depends on BOTH the model version AND the Azure OpenAI API version supporting it — older API versions only support looser "JSON mode" (valid JSON guaranteed, not schema-conformant). Confirm both before relying on it.
Interview question
What's the difference between Azure OpenAI's "JSON mode" and full structured outputs with a schema?
Show a strong answer
JSON mode guarantees syntactically valid JSON but says nothing about its SHAPE — fields could be missing, extra, or wrongly typed. Structured outputs with a schema additionally enforce conformance to a specific structure, which is what you actually want when deserializing into a typed object.
P1 · 06 Azure OpenAI

Tool/function calling

Tool calling lets you describe functions (name, description, JSON-schema parameters) to the model; the model can respond with a structured request to call one, which your application code — never Azure OpenAI itself — actually executes, then feeds the result back as a tool message for the next turn.

ToolDefinition.java
ChatCompletionsFunctionToolDefinition getOrderStatusTool = new ChatCompletionsFunctionToolDefinition(
    new ChatCompletionsFunctionToolDefinitionFunction("get_order_status")
        .setDescription("Look up the status of a customer order by ID.")
        .setParameters(BinaryData.fromObject(parametersSchema))
);
options.setTools(List.of(getOrderStatusTool));
Security note
The model's tool call is a request, not a command — your backend must independently validate arguments and check authorization before executing anything, exactly the same tool-execution security boundary covered for agentic systems generally.
Interview question
Who actually executes a tool call Azure OpenAI's model requests?
Show a strong answer
Your application code — Azure OpenAI only returns a structured request (function name + arguments). Your backend decides whether to execute it, validates the arguments, and sends the result back as part of the next chat completion call.
P1 · 07 Azure OpenAI

Streaming

Streaming returns a chat completion's tokens incrementally as they're generated, via server-sent events, rather than waiting for the full response — the same "perceived latency" win covered generally for LLM applications, now at the Azure SDK level. Your backend typically needs to relay the stream through to the client (e.g., as its own SSE or WebSocket stream), not just consume it server-side.

StreamingExample.java
IterableStream<ChatCompletions> chatCompletionsStream =
    client.getChatCompletionsStream("gpt-4o-chat-prod", new ChatCompletionsOptions(messages));

for (ChatCompletions chunk : chatCompletionsStream) {
    if (!chunk.getChoices().isEmpty()) {
        String delta = chunk.getChoices().get(0).getDelta().getContent();
        if (delta != null) responseEmitter.send(delta);  // relay to the client
    }
}
Production note
If your backend sits behind Azure API Management or a load balancer, confirm streaming responses pass through without buffering the whole response first — some gateway configurations buffer by default, silently defeating the latency benefit.
Interview question
Why might streaming "not work" even though your code correctly calls the streaming API?
Show a strong answer
An intermediate layer — an API gateway, a load balancer, or even certain reverse proxy configurations — may buffer the entire response before forwarding it to the client, which silently collapses the streaming benefit into a single delayed response even though the Azure OpenAI call itself streamed correctly.
P1 · 08 Azure OpenAI

Model selection

Azure OpenAI offers multiple model families and sizes (e.g., a flagship GPT-4-class model, a smaller/faster/cheaper "mini" variant, embedding models of different sizes) — choosing between them is a genuine engineering trade-off between capability, latency, and cost per request, not a default to always pick the biggest.

Production note
Route different parts of your application to different deployments based on actual need — use a smaller, cheaper model for classification/routing/simple extraction tasks, and reserve the flagship model for genuinely complex reasoning or generation, the same cost-conscious instinct you'd apply to choosing compute SKUs for different workloads.
Interview question
How would you decide which Azure OpenAI model to use for a given feature in your application?
Show a strong answer
Measure the task's actual complexity requirements against cost and latency budgets — a simple classification or extraction task rarely needs the flagship model; reserve that for genuinely complex reasoning, and validate the cheaper model's accuracy against a test set before committing, rather than assuming bigger is always necessary.
P1 · 09 Azure OpenAI

Tokens

Azure OpenAI bills and rate-limits by token count — both input (prompt) and output (completion) tokens — not by request count or characters. The exact tokenizer depends on the model family; estimate roughly 4 characters per token for English text, but validate with an actual tokenizer library for anything cost-sensitive.

Production note
Track token usage per request as a first-class metric in Application Insights (the API response includes usage counts) — this is your most direct lever for both cost attribution and catching a context-construction bug that's silently bloating prompts.
Interview question
Why is token count, not character count, the right unit for estimating Azure OpenAI cost?
Show a strong answer
Billing and rate limits are both defined in tokens, and the character-to-token ratio varies by language, content type, and the specific tokenizer a model family uses — a cost estimate based on character count can be meaningfully wrong, especially for non-English text or code.
P1 · 10 Azure OpenAI

Context limits

Each model has a maximum context length (combined input + output tokens) that varies by model family and version — exceeding it returns an error from the API, it doesn't silently truncate. Application code needs to proactively manage this: windowing conversation history, summarizing older turns, or limiting how much retrieved RAG context gets included.

Common mistake
Assuming a model's context limit means "I can always send that much" without accounting for the OUTPUT tokens you also need room for — a request that maxes out input tokens can leave no budget for the response, causing a truncated or failed generation.
Interview question
What happens if a request exceeds a deployment's context limit, and how should your application handle it?
Show a strong answer
The API returns an error rather than silently truncating — application code needs to proactively keep the combined input+expected-output tokens under the limit, typically via conversation windowing/summarization or capping retrieved RAG context, and handle the error gracefully if it still occurs.
P1 · 11 Azure OpenAI

Temperature

Temperature controls how deterministic vs. varied generated output is — a request parameter on every chat completions call, identical in meaning to temperature anywhere else in this space (it reshapes the probability distribution before sampling). Lower values (near 0) suit factual extraction and classification; higher values suit creative or varied generation.

Temperature.java
ChatCompletionsOptions options = new ChatCompletionsOptions(messages);
options.setTemperature(0.2);  // low temperature for consistent, factual responses
Production note
Set temperature explicitly and deliberately per use case rather than leaving the default — a RAG answer-generation call and a creative marketing-copy generator in the same application likely want very different values.
Interview question
Why might a production RAG system set temperature close to 0 rather than the default?
Show a strong answer
A RAG answer should faithfully reflect retrieved context, not creatively embellish it — a low temperature reduces the chance of the model wandering into plausible-sounding but unsupported additions, favoring consistent, grounded output over variety.
P1 · 12 Azure OpenAI

Rate limits

Azure OpenAI enforces rate limits per deployment, typically expressed as tokens-per-minute (TPM) and requests-per-minute (RPM) — exceeding them returns an HTTP 429, with a Retry-After header indicating how long to back off. This is architecturally identical to rate limiting on any other Azure or third-party API you've integrated with.

RetryWithBackoff.java
RetryPolicy retryPolicy = new RetryPolicy(
    new ExponentialBackoff(5, Duration.ofSeconds(1), Duration.ofSeconds(30))
);
OpenAIClient client = new OpenAIClientBuilder()
    .endpoint(endpoint)
    .credential(credential)
    .retryPolicy(retryPolicy)
    .buildClient();
Production note
The Azure SDK clients support configurable retry policies out of the box — use them rather than hand-rolling retry logic, and always honor the Retry-After header's value rather than a fixed backoff when the API provides one.
Interview question
Your application starts getting 429s from Azure OpenAI under load. What are your options, beyond just retrying?
Show a strong answer
Implement backoff-aware retry honoring Retry-After, request a quota increase if usage is consistently near the limit, consider a request queue to smooth bursty traffic, or distribute load across multiple deployments/regions (Provisioned Throughput Units or multiple deployments) if volume genuinely requires more capacity than one deployment's quota allows.
P1 · 13 Azure OpenAI

Quotas

Quota is the total throughput capacity allocated to your subscription for a given model/region, which you then distribute across one or more deployments — distinct from rate limits (the per-deployment ceiling at any given moment). Think of quota as the budget you allocate, and a deployment's rate limit as how much of that budget one specific deployment is configured to use.

Production note
Request quota increases proactively based on projected traffic, well before you need it — quota increase requests go through an approval process and aren't instantaneous, unlike scaling most other Azure compute resources.
Interview question
What's the difference between a quota and a rate limit in Azure OpenAI?
Show a strong answer
Quota is the total throughput capacity your subscription has been allocated for a model/region; a rate limit is how much of that quota a specific deployment is configured to actually use at any given moment. You can have unused quota while still hitting a deployment's configured rate limit.
P1 · 14 Azure OpenAI

Content filtering

Azure OpenAI applies content filters to both prompts and completions by default, screening for categories like hate, violence, self-harm, and sexual content, returning a filtered/flagged response (and metadata about why) rather than silently passing harmful content through. Filter configurations (sensitivity thresholds) can be customized per deployment through Azure AI Content Safety configuration, within policy limits.

Interview angle
A response can be blocked by content filtering even when the underlying model would have produced a reasonable answer — your application needs to handle the filtered-response case explicitly (checking the finish_reason/content_filter_results), not just assume every call returns a normal completion.
Interview question
How should your application code handle a response that gets blocked by content filtering?
Show a strong answer
Check the response's finish reason / content filter results explicitly, and have a defined fallback behavior (a generic message, logging for review, or escalation) rather than assuming every API call returns normal generated content — a filtered response is a distinct, expected case to handle, not an error to just retry blindly.
P1 · 15 Azure OpenAI

Responsible AI

Microsoft requires an attestation of intended use before provisioning Azure OpenAI access, and provides a broader Responsible AI framework — content filtering (previous topic), abuse monitoring, transparency documentation, and usage guidelines — that applications built on Azure OpenAI are expected to operate within. This isn't just policy paperwork; it shapes real architectural decisions like whether abuse-monitoring data retention is acceptable for your use case.

Production note
For sensitive or regulated workloads, review Microsoft's data usage and retention policies specifically for Azure OpenAI (distinct from general Azure policies) — abuse monitoring involves some data retention by default, which may interact with compliance requirements depending on your industry and data classification.
Interview question
Why does Responsible AI matter architecturally, not just as a compliance checkbox?
Show a strong answer
It shapes real design decisions — what content filtering thresholds are appropriate for your use case, what abuse-monitoring data retention your compliance requirements can tolerate, and what transparency/disclosure obligations your product needs to meet when AI-generated content reaches end users.
P1 · 16 Azure OpenAI

Authentication

Azure OpenAI supports two authentication mechanisms: API keys (a resource-level static secret) and Entra ID (Azure AD) token-based authentication via managed identity or service principal — the exact same two options you already know from securing any other Azure resource.

Java / Spring angle
If you've ever authenticated a Spring Boot app to Azure Key Vault or Azure SQL using DefaultAzureCredential from the Azure Identity library, the exact same credential chain works for Azure OpenAI — no new authentication concept to learn.
Interview question
What are the two authentication options for Azure OpenAI, and which would you default to in production?
Show a strong answer
API keys (a static resource-level secret) or Entra ID token-based auth via managed identity/service principal. Default to Entra ID with managed identity in production for Azure-to-Azure calls — it eliminates a static secret to manage, rotate, and potentially leak entirely.
P1 · 17 Azure OpenAI

Managed identity

A managed identity lets your Azure compute resource (Container App, Function App, App Service) authenticate to Azure OpenAI (and any other Azure resource) without storing any credential at all — Azure itself manages the identity's lifecycle and credential rotation, and your code just requests a token via DefaultAzureCredential.

ManagedIdentityAuth.java
TokenCredential credential = new DefaultAzureCredentialBuilder().build();
OpenAIClient client = new OpenAIClientBuilder()
    .endpoint("https://my-resource.openai.azure.com/")
    .credential(credential)
    .buildClient();
Production note
This is the single highest-leverage security decision in an Azure GenAI architecture: no API key means no key to leak in logs, source control, or a misconfigured environment variable — eliminate the class of vulnerability entirely rather than managing it carefully.
Interview question
Why is managed identity considered a stronger security posture than even a carefully-managed API key stored in Key Vault?
Show a strong answer
An API key, even in Key Vault, is still a static secret that could theoretically be retrieved, logged, or exfiltrated at some point in its lifecycle. Managed identity eliminates the secret entirely — there's no credential to leak, because the application never possesses one; Azure issues short-lived tokens behind the scenes, tied to the resource's own identity.
P1 · 18 Azure OpenAI

API keys

API keys are a simpler, resource-level static credential — convenient for local development, quick prototyping, or scenarios outside Azure (a client that isn't itself an Azure resource and can't use managed identity). Every Azure OpenAI resource has two keys, allowing rotation without downtime: rotate one while the other stays active, then swap.

Common mistake
Using an API key in production Azure-to-Azure communication just because it was the fastest way to get a prototype working — this is the exact case managed identity exists to replace, and the switch is usually a small, contained change once you've validated the prototype.
Interview question
Why does Azure OpenAI provide two API keys per resource instead of one?
Show a strong answer
It enables zero-downtime key rotation — rotate the first key while traffic continues using the second, verify everything still works, then rotate the second key, rather than having a single key whose rotation would require a coordinated cutover with a risk window.
P1 · 19 Azure OpenAI

RBAC

Azure OpenAI defines its own RBAC roles — most importantly "Cognitive Services OpenAI User" (can call inference endpoints) and "Cognitive Services OpenAI Contributor" (can also manage deployments) — assigned to a managed identity, service principal, or user, scoped to the resource (or a broader scope like the resource group). This is the exact same RBAC model as any other Azure resource, just with roles specific to this service.

assign-rbac.sh
az role assignment create \
  --assignee "<managed-identity-principal-id>" \
  --role "Cognitive Services OpenAI User" \
  --scope "/subscriptions/<sub-id>/resourceGroups/<rg>/providers/Microsoft.CognitiveServices/accounts/<aoai-resource>"
Production note
Grant "OpenAI User" to application identities that only need to call inference, and reserve "OpenAI Contributor" for deployment/infrastructure-management identities — the same least-privilege principle you'd apply to database read vs. schema-modification permissions.
Interview question
What's the difference between the "Cognitive Services OpenAI User" and "Cognitive Services OpenAI Contributor" roles?
Show a strong answer
OpenAI User can call inference endpoints (chat completions, embeddings) but can't manage the resource itself. OpenAI Contributor can additionally create/modify/delete model deployments and resource configuration — a much broader permission that should be reserved for infrastructure/deployment identities, not application runtime identities.
P1 · 20 Azure OpenAI

Secure configuration

Beyond authentication, securing an Azure OpenAI deployment end-to-end means: private endpoints (so traffic never traverses the public internet), disabling public network access where feasible, network security groups/firewall rules restricting which subnets can reach the resource, and diagnostic settings routing logs to a SIEM or Log Analytics workspace for audit — the same defense-in-depth checklist you'd apply to any sensitive Azure PaaS resource.

Production note
Treat "can this resource be reached from the public internet at all" as the first security question for any production Azure OpenAI deployment handling sensitive data — a private endpoint plus disabled public access closes an entire category of risk before authentication is even relevant.
Interview question
Beyond authentication, what network-level controls would you put around a production Azure OpenAI resource handling sensitive data?
Show a strong answer
A private endpoint so traffic stays on the Azure backbone network, disabled public network access, network security group rules limiting which subnets/resources can reach it, and diagnostic logging routed to a Log Analytics workspace or SIEM for audit — the same network-isolation checklist applied to any sensitive Azure PaaS resource.
P2 · 01 Azure AI Search

Azure AI Search architecture

Azure AI Search (formerly "Azure Cognitive Search") is a managed search-as-a-service resource — provision a search service at a chosen pricing tier, create one or more indexes within it, and query via REST API or SDK. It's fully managed with built-in vector search, semantic ranking, and an AI enrichment pipeline.

Java / Spring angle
If you've integrated Spring Data Elasticsearch, the mental model transfers almost directly — an index is like an Elasticsearch index, documents are like Elasticsearch documents, and the azure-search-documents SDK plays the role your Elasticsearch client would.
SearchClientSetup.java
SearchClient searchClient = new SearchClientBuilder()
    .endpoint("https://my-search.search.windows.net")
    .credential(new AzureKeyCredential(apiKey))
    .indexName("my-index")
    .buildClient();
Version note
The service was renamed from "Azure Cognitive Search" to "Azure AI Search" — docs, SDKs, and portal UI elements may still reference the old name depending on when last updated. Functionally the same service.
Interview question
How would you explain Azure AI Search's role to someone who's used Elasticsearch before?
Show a strong answer
A comparable managed search service — indexes, documents, fields, queries — but fully managed by Azure with native vector search and semantic ranking built in, rather than needing to self-host or bolt on vector search separately.
P2 · 02 Azure AI Search

Indexes

An index is the schema-defined container for your searchable documents — define its fields upfront (name, type, which search behaviors each supports), similar to a table schema, though changes are more restrictive than a relational ALTER TABLE — some field changes require rebuilding the index entirely.

IndexDefinition.java
List<SearchField> fields = List.of(
    new SearchField("id", SearchFieldDataType.STRING).setKey(true),
    new SearchField("content", SearchFieldDataType.STRING).setSearchable(true),
    new SearchField("contentVector", SearchFieldDataType.collection(SearchFieldDataType.SINGLE))
        .setSearchable(true).setVectorSearchDimensions(1536).setVectorSearchProfileName("my-profile")
);
SearchIndex index = new SearchIndex("my-index", fields);
indexClient.createOrUpdateIndex(index);
Production note
Changing certain field attributes (like making a non-filterable field filterable) typically requires dropping and recreating the index, not an in-place migration — plan schema with this constraint in mind.
Interview question
Why can't you always just add a capability (like making an existing field filterable) to an index the way you'd add a database column index?
Show a strong answer
Certain field attributes are fixed at index-creation time because they determine how the search engine physically stores and indexes that field's data — changing them requires rebuilding the index from scratch, which needs to be planned for in any re-indexing strategy.
P2 · 03 Azure AI Search

Documents

A document is one record in an index — a JSON object matching the index's schema, uniquely identified by a key field. Documents are uploaded individually or in batches, and can be added, updated (merge or full replace), or deleted through the same document-operations API.

UploadDocument.java
SearchDocument doc = new SearchDocument();
doc.put("id", "doc-1");
doc.put("content", "Azure AI Search supports hybrid retrieval.");
doc.put("contentVector", embeddingVector);
searchClient.uploadDocuments(List.of(doc));
Interview question
What's the difference between a "merge" and an "upload" document operation?
Show a strong answer
Upload replaces the entire document (or creates it) — fields not included get cleared. Merge only updates the specific fields provided, leaving other existing fields untouched — the same distinction as a full PUT versus a partial PATCH.
P2 · 04 Azure AI Search

Fields

Each field declares its data type and which behaviors it supports: searchable (full-text search applies), filterable (usable in $filter expressions), sortable, facetable, and retrievable. Multiple behaviors can be enabled simultaneously, but each one has a real storage/performance cost.

Common mistake
Marking every field searchable/filterable/facetable "just in case" — each enabled capability bloats the index and can slow indexing/queries. Design field attributes based on actual query patterns, the same discipline applied to database indexing.
Interview question
Why wouldn't you just mark every field as searchable, filterable, and facetable to keep your options open?
Show a strong answer
Each enabled capability has a real storage and performance cost. Field attributes should be driven by actual, known query patterns, the same discipline applied to deciding which database columns actually need an index.
P2 · 05 Azure AI Search

Indexers

An indexer is a configured, schedulable pipeline that automatically pulls data from a connected data source, optionally runs it through enrichment steps (skillsets — chunking, embedding generation, OCR), and populates an index — eliminating custom code to manually read and upload documents yourself.

indexer-definition.json
{
  "name": "blob-indexer",
  "dataSourceName": "blob-datasource",
  "targetIndexName": "my-index",
  "schedule": { "interval": "PT1H" }
}
Production note
Indexers are optional — push documents directly via the upload API (a "push" model) instead when you need custom processing logic a skillset doesn't support, or your data doesn't live in a directly-connectable source.
Interview question
When would you choose push-based indexing over using an Azure AI Search indexer?
Show a strong answer
When document processing needs custom logic a built-in skillset doesn't support, when source data doesn't live in a directly-connectable data store, or when indexing needs to happen synchronously as part of an application workflow rather than on a schedule.
P2 · 06 Azure AI Search

Data sources

A data source is a connection definition (connection string/credentials + container/table reference) telling an indexer WHERE to pull documents from — Blob Storage, Cosmos DB, Azure SQL, and others are supported natively. It's a separate, reusable resource from the indexer itself.

data-source.json
{
  "name": "blob-datasource",
  "type": "azureblob",
  "credentials": { "connectionString": "ResourceId=...;" },
  "container": { "name": "documents" }
}
Production note
Prefer a managed-identity-based connection for a data source over an embedded connection string where supported — access to Blob Storage/Cosmos DB should follow the same "no static secret" principle as everything else.
Interview question
Why is a data source defined as a separate resource from the indexer that uses it?
Show a strong answer
Separating the connection definition from the indexing job lets multiple indexers reuse the same data source, and lets the connection be managed independently from indexing schedule/logic — the same separation of concerns as a reusable datasource bean separate from the repository that uses it.
P2 · 07 Azure AI Search

Vector search

Vector search stores embedding vectors as a dedicated field type and finds the nearest vectors to a query vector using approximate nearest neighbor algorithms (HNSW by default) — the general vector-similarity retrieval concept, now native to this index rather than needing a separate vector database.

VectorQuery.java
VectorizedQuery vectorQuery = new VectorizedQuery(queryEmbedding)
    .setFields("contentVector")
    .setKNearestNeighborsCount(5);
SearchOptions options = new SearchOptions().setVectorSearchOptions(
    new VectorSearchOptions().setQueries(vectorQuery)
);
SearchPagedIterable results = searchClient.search(null, options, Context.NONE);
Production note
Choose the algorithm's parameters (HNSW's efConstruction/efSearch, or exhaustive KNN for smaller datasets needing exact results) based on your actual scale and latency/accuracy trade-off — the default is a reasonable start, not a decision to skip validating.
Interview question
Why would Azure AI Search be a reasonable choice for vector search instead of standing up a dedicated vector database?
Show a strong answer
If you already need full-text/hybrid search and filtering, Azure AI Search gives you vector search as a native capability of the SAME service, avoiding the operational overhead of running a separate specialized vector database alongside existing search infrastructure.
P2 · 08 Azure AI Search

Hybrid search

Hybrid search combines vector similarity with traditional keyword (BM25-based) search in a single query, fusing the two rankings internally via Reciprocal Rank Fusion — addressing vector search's blind spot for exact terms while keeping semantic matching strength. It's literally one API call with both a search text and a vector query specified together.

HybridQuery.java
SearchOptions options = new SearchOptions()
    .setVectorSearchOptions(new VectorSearchOptions().setQueries(vectorQuery));
SearchPagedIterable results = searchClient.search(queryText, options, Context.NONE);  // text + vector = hybrid
Production note
Hybrid search is close to default best practice for enterprise RAG on Azure — the fusion logic is handled natively, with no manual RRF implementation needed on your side.
Interview question
How does Azure AI Search implement hybrid search, from your application code's perspective?
Show a strong answer
A single search call including BOTH a text query and a vector query — the service internally runs both the keyword and vector searches and fuses the rankings using Reciprocal Rank Fusion, returning one combined result set. You don't implement the fusion logic yourself.
P2 · 09 Azure AI Search

Semantic ranking

Semantic ranking is an optional additional reranking step applied to your top results using a deep learning model to better capture relevance beyond raw term/vector matching — the cross-encoder reranking concept from RAG generally, offered as a managed, built-in feature enabled via a query parameter.

SemanticRanking.java
SearchOptions options = new SearchOptions()
    .setQueryType(QueryType.SEMANTIC)
    .setSemanticSearchOptions(new SemanticSearchOptions().setSemanticConfigurationName("my-semantic-config"));
Production note
Semantic ranking only reranks a capped number of top results and has its own pricing/throughput implications — validate the actual relevance improvement against your own eval set before assuming it's always worth enabling.
Interview question
How does Azure AI Search's semantic ranking relate to the general concept of reranking in a RAG pipeline?
Show a strong answer
It's a managed implementation of the same idea — take fast retrieval's top candidates and reorder them with a more sophisticated relevance model — except Azure hosts and manages that model for you, enabled via configuration rather than deploying a separate cross-encoder yourself.
P2 · 10 Azure AI Search

Filters

Filters ($filter, OData syntax) narrow results by exact field-value conditions alongside relevance-ranked search — essential for combining relevance with access control, freshness, or categorical scoping. Filters apply deterministically: a document either matches or it doesn't, unlike continuous relevance scoring.

FilterQuery.java
SearchOptions options = new SearchOptions()
    .setFilter("tenantId eq 'tenant-42' and category eq 'policy'");
Security note
In any multi-tenant RAG system, the tenant-scoping filter must be constructed server-side from the authenticated caller's identity, never accepted as a client-supplied parameter.
Interview question
Why is a $filter expression the right mechanism for multi-tenant isolation, rather than relying on relevance ranking alone?
Show a strong answer
Filters are deterministic and exclusionary — a document either passes or is excluded entirely, regardless of relevance score. Relying on ranking alone to "deprioritize" another tenant's data would still risk exposing it; filtering guarantees it's never returned at all.
P2 · 11 Azure AI Search

Vectorizers

A vectorizer configures Azure AI Search to automatically call an embedding model at QUERY time, converting a text query into a vector internally — your application sends plain text and gets hybrid/vector results back, without a separate embeddings call for every query. This is specifically a query-time convenience; documents still need embeddings generated at indexing time.

vectorizer.json
{
  "name": "aoai-vectorizer",
  "kind": "azureOpenAI",
  "azureOpenAIParameters": {
    "resourceUri": "https://my-resource.openai.azure.com",
    "deploymentId": "text-embedding-3-small-deploy"
  }
}
Production note
A vectorizer ties the embedding model/deployment to your index configuration — changing embedding models later means updating the vectorizer config AND re-embedding/re-indexing existing documents.
Interview question
What problem does a vectorizer solve, specifically?
Show a strong answer
It lets Azure AI Search automatically convert a plain-text query into an embedding vector at query time by calling a configured embedding model internally, so application code can send text queries directly for vector/hybrid search without a separate embeddings call per query.
P2 · 12 Azure AI Search

Embeddings (in Search)

Within Azure AI Search, "embeddings" refers to how vector fields get populated at INDEXING time — either your application calls Azure OpenAI's embeddings endpoint before uploading documents (push model), or an indexer's skillset includes an embedding skill to generate them automatically (pull model). Both must use the same embedding model as whatever generates query-time vectors.

Production note
Document chunking happens BEFORE embedding — a text-splitting skill typically runs before the embedding skill in a skillset pipeline, and chunk size/overlap choices carry the exact same retrieval-quality trade-offs covered for RAG generally.
Interview question
In an indexer-based ingestion pipeline, what's the typical order of skillset steps before a document's embedding ends up in the index?
Show a strong answer
Extract/parse text from the source document, split it into chunks, generate an embedding for each chunk, and map the resulting vector into the index's vector field — each step feeding the next in the skillset pipeline.
P2 · 13 Azure AI Search

Retrieval pipeline

The full retrieval pipeline, from a user's question to ranked results, strings everything together: the query gets (optionally) vectorized, Azure AI Search executes vector/keyword/hybrid search with any filters applied, optionally reranks with semantic ranking, and returns the final ranked set — which your application formats into context for a chat completions call.

Diagram
User query→ vectorizer → Hybrid search + filters→ Semantic ranking→ Context for AOAI
Interview question
Walk through the full retrieval pipeline for a RAG query, from the user's question to the context handed to the LLM.
Show a strong answer
The query text (and optionally a vectorizer-generated embedding) goes to Azure AI Search; the service runs hybrid search with any access-control filters applied; if configured, semantic ranking reorders the top results; the final ranked documents return to the application, which formats them into context for the Azure OpenAI chat completion call.
P2 · 14 Azure AI Search

Reranking

Beyond the built-in semantic ranking, you can implement custom reranking in your application layer — calling a separate reranking model, or even using an Azure OpenAI chat completion to score/reorder candidates — useful when you need domain-specific relevance criteria the built-in semantic ranker doesn't capture, at the cost of extra latency and complexity you now own.

Production note
Try the built-in semantic ranker first and measure it against your eval set — only build custom reranking if its measured relevance genuinely falls short for your specific domain, not by default.
Interview question
When would you build a custom reranking step instead of relying on Azure AI Search's built-in semantic ranking?
Show a strong answer
When your domain has relevance criteria the general-purpose semantic ranker doesn't capture well — specialized terminology, business-specific relevance rules — and you've MEASURED that it falls short for your content, not as a default assumption that custom is always better.
P2 · 15 Azure AI Search

Search relevance

Whether the top results are actually the most useful ones depends on the combination of every decision covered so far — chunking strategy, embedding model quality, hybrid vs. vector-only search, filter correctness, and whether semantic ranking is enabled. Azure doesn't measure this for you; you build and run the evaluation yourself.

Production note
Azure doesn't ship a built-in "relevance score dashboard" for your specific content — building a lightweight evaluation harness, even a simple script running a golden query set and computing hit rate, is worthwhile before trusting default configuration choices in production.
Interview question
How would you actually validate that your Azure AI Search configuration is producing good relevance for your specific content?
Show a strong answer
Build a golden dataset of representative queries with known-relevant documents, and measure retrieval metrics (hit rate, MRR, or NDCG) against it — comparing configurations using that same measurement, rather than assuming any default setting is automatically well-suited to your content.
P2 · 16 Azure AI Search

RAG integration

A production RAG application on Azure has an ingestion path (documents → Blob Storage → indexer/skillset → Azure AI Search index, with embeddings generated along the way) and a query path (question → Azure AI Search hybrid/semantic query → ranked chunks → prompt → Azure OpenAI chat completion → grounded, cited answer) — the full "Enterprise RAG" project covered later in this workbook.

Diagram
Blob Storage→ Indexer + skillset→ Azure AI Search index
Question→ Hybrid/semantic query→ Chat completion→ Grounded answer + citations
Interview question
In a system design interview, how would you describe the two separate pipelines a RAG application on Azure needs?
Show a strong answer
An offline ingestion pipeline — documents land in Blob Storage, an indexer with an embedding skillset processes and indexes them into Azure AI Search — and an online query pipeline — a user's question triggers a hybrid/semantic search, and the top results become context for an Azure OpenAI chat completion producing a grounded, cited answer. These run independently and at different times.
Part 3 · Azure services

Azure Functions

A serverless compute option well-suited to event-driven or bursty GenAI workloads — a document lands in Blob Storage and triggers a Function to chunk/embed it; an HTTP-triggered Function can serve as a lightweight backend API for low-to-moderate, intermittent traffic, scaling to zero when idle, with cold-start latency to weigh for latency-sensitive chat.

ChatFunction.java
@FunctionName("chat")
public HttpResponseMessage run(
    @HttpTrigger(name = "req", methods = {HttpMethod.POST}, authLevel = AuthorizationLevel.FUNCTION) HttpRequestMessage<String> request,
    final ExecutionContext context) {
    ChatCompletions completions = openAIClient.getChatCompletions(deploymentName, buildOptions(request.getBody()));
    return request.createResponseBuilder(HttpStatus.OK).body(completions).build();
}
When to use / avoid
Use for: bursty traffic, event-driven ingestion (blob-triggered embedding). Avoid for: high-throughput low-latency chat where cold starts are unacceptable, or long-lived streaming connections exceeding the hosting plan's execution limits.
Interview question
When would Azure Functions be a poor fit for a GenAI backend API?
Show a strong answer
For high-throughput, latency-sensitive chat where cold-start latency is unacceptable, or long-lived streaming connections exceeding the hosting plan's execution limits — Container Apps or App Service with always-on instances fit better.

Comparisons

Four comparisons worth having crisp answers for

Azure OpenAI vs. public OpenAI API

Azure OpenAI
  • Runs inside your Azure subscription/network boundary — private endpoints, VNets
  • Authentication via Entra ID/managed identity or API keys — integrates with existing Azure RBAC
  • Covered by Azure's compliance certifications and regional data residency
  • Model availability can lag the public API slightly for brand-new releases
Public OpenAI API
  • Simpler to start with — no Azure resource provisioning
  • Often first access to the newest models
  • No Azure network/compliance integration — a separate third party entirely
  • Harder to justify for enterprises already standardized on Azure for compliance

For an enterprise already on Azure, Azure OpenAI is almost always the right default — the deciding factor is rarely capability, it's compliance, network isolation, and operating within an existing Azure governance model.

Azure AI Search vs. traditional databases

Azure AI Search
  • Purpose-built for relevance-ranked retrieval — full-text, vector, hybrid
  • Native semantic ranking and AI enrichment pipeline
  • Not a system of record — no transactions, limited relational querying
Traditional database
  • Strong transactional guarantees, relational querying, joins
  • Exact-match and structured queries are its strength, not relevance ranking
  • Vector search support (e.g. via an extension) exists but is typically less mature/performant at scale than a purpose-built search service

These aren't competitors for the same job — a production RAG system typically uses BOTH: a database (often Cosmos DB) for operational state, and Azure AI Search specifically for the relevance-ranked retrieval problem.

Vector search vs. hybrid search

Vector search alone
  • Strong at conceptual/semantic matching, paraphrase tolerance
  • Blind to exact terms — product codes, names, acronyms
  • Simpler to reason about and tune
Hybrid search
  • Combines vector + keyword, fused via Reciprocal Rank Fusion
  • Catches exact-term matches vector search alone would miss
  • Close to default best practice for enterprise RAG on Azure — minimal added complexity since it's native

Default to hybrid for production RAG unless you've specifically measured that vector-only performs equally well for your content — the native support makes the "added complexity" argument against it much weaker on Azure than it would be building hybrid search yourself.

Azure Functions vs. Container Apps

Azure Functions
  • True serverless, scale to zero, pay-per-execution
  • Best for event-driven and bursty workloads
  • Cold starts and execution time limits can be a problem for sustained/streaming workloads
Container Apps
  • Full control over your containerized application and runtime
  • Better suited to long-lived connections (streaming chat)
  • Still supports scale-to-zero, but with more operational surface than Functions

For a Java Spring Boot GenAI backend specifically, Container Apps is usually the more natural fit — you likely already have a containerized Spring Boot build process, and streaming chat responses benefit from Container Apps' more flexible connection handling.

ChatController.java
@RestController
@RequestMapping("/chat")
public class ChatController {
    private final OpenAIClient client;
    private final String deploymentName;

    @PostMapping(produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<String> chat(@RequestBody ChatRequest request) {
        List<ChatRequestMessage> messages = List.of(
            new ChatRequestSystemMessage("You are a helpful assistant."),
            new ChatRequestUserMessage(request.message())
        );
        ChatCompletionsOptions options = new ChatCompletionsOptions(messages).setTemperature(0.3);
        return Flux.fromIterable(client.getChatCompletionsStream(deploymentName, options))
            .mapNotNull(chunk -> chunk.getChoices().isEmpty() ? null : chunk.getChoices().get(0).getDelta().getContent());
    }
}

  • Model choice is the dominant cost lever — default to a smaller/cheaper model unless the task demonstrably needs the flagship model.
  • Streaming doesn't reduce total token cost — it's a latency-perception improvement only.

public RagAnswer answer(String question, String tenantId) {
    VectorizedQuery vectorQuery = new VectorizedQuery(embeddingClient.embed(question))
        .setFields("contentVector").setKNearestNeighborsCount(5);
    SearchOptions options = new SearchOptions()
        .setFilter("tenantId eq '" + tenantId + "'")
        .setQueryType(QueryType.SEMANTIC)
        .setSemanticSearchOptions(new SemanticSearchOptions().setSemanticConfigurationName("default-semantic-config"))
        .setVectorSearchOptions(new VectorSearchOptions().setQueries(vectorQuery));

    SearchPagedIterable results = searchClient.search(question, options, Context.NONE);
    String context = buildLabeledContext(results);  // "[Source: policy.pdf] ..." per chunk

    String prompt = "Answer using ONLY this context, citing the source file:\n" + context + "\n\nQuestion: " + question;
    ChatCompletions completions = openAIClient.getChatCompletions(chatDeployment,
        new ChatCompletionsOptions(List.of(new ChatRequestUserMessage(prompt))).setTemperature(0.1));
    return new RagAnswer(completions.getChoices().get(0).getMessage().getContent(), extractCitations(results));
}

  • Indexer execution history monitored for failures (malformed documents, skillset errors) via Azure Monitor alerts.

Cost considerations

  • Embedding costs are incurred once per document chunk at ingestion, not per query — the ongoing per-query cost is dominated by the chat completion call.
  • Semantic ranking has its own pricing tier implications on Azure AI Search — validate the relevance gain justifies it before enabling broadly.
  • Azure AI Search pricing tier (and replica/partition count) should be sized to actual query volume and index size, not provisioned at a guess.

Failure handling

  • Retrieval-confidence threshold: if top search scores fall below a calibrated bar, return an explicit "I don't have information about that" rather than generating from weak context.
  • Indexer failures for individual documents are isolated and logged (a malformed PDF shouldn't block the whole batch) rather than failing the entire indexing run.

Testing

  • A golden dataset of representative questions with known-correct source documents, used to measure hit rate and citation accuracy on every configuration change.
  • Cross-tenant isolation test: as tenant A, query for content only tenant B has, asserting zero results.

Interview explanation

"An indexer-driven RAG pipeline using Azure AI Search's native hybrid and semantic ranking rather than hand-building retrieval fusion — the actual engineering effort went into the tenant-isolation filter being server-side enforced on every query, and a retrieval-confidence threshold that makes the system say 'I don't know' instead of generating from irrelevant context."

Production GenAI API

The capstone: everything from Projects 1 and 2, plus persistent conversation state, full secret management, and a complete observability and resilience story across every dependency — the shape of what actually ships.

Security

  • Every Azure-to-Azure call (Container App → Azure OpenAI, Azure AI Search, Cosmos DB, Key Vault) uses the Container App's system-assigned managed identity — zero static secrets for internal traffic.
  • End users authenticate via Microsoft Entra ID; APIM validates the token before any request reaches the backend.
  • Private endpoints on Azure OpenAI, Azure AI Search, and Cosmos DB — none reachable from the public internet.
  • Per-RBAC-role least privilege: the backend identity gets "OpenAI User" and "Search Index Data Reader," never Contributor-level roles.

Code

ConversationService.java
@CircuitBreaker(name = "azureOpenAI", fallbackMethod = "fallbackResponse")
@Retry(name = "azureOpenAI")
public ChatTurn handleMessage(String sessionId, String userMessage) {
    List<ConversationTurn> history = cosmosRepository.getRecentTurns(sessionId, 10);
    RagAnswer ragAnswer = ragService.answer(userMessage, currentTenantId());
    ChatTurn turn = new ChatTurn(sessionId, userMessage, ragAnswer.text(), ragAnswer.citations(), Instant.now());
    cosmosRepository.save(turn);
    return turn;
}

private ChatTurn fallbackResponse(String sessionId, String userMessage, Throwable t) {
    log.warn("Azure OpenAI unavailable, degrading gracefully", t);
    return ChatTurn.degraded(sessionId, "Our assistant is temporarily unavailable. Please try again shortly.");
}

Deployment

  • Infrastructure as code (Bicep) provisioning every resource and RBAC role assignment, deployed via a GitHub Actions / Azure DevOps pipeline.
  • Blue/green rollout via Container Apps revisions — a new revision receives a small traffic percentage before full cutover.
  • Secrets referenced via Key Vault references in configuration, never committed to source control, even as placeholders.

Monitoring

  • Distributed tracing across the full call chain — APIM → backend → Azure OpenAI/Search/Cosmos — correlated by a single trace ID per user request.
  • Dashboards for token usage/cost, retrieval hit rate (sampled), p95/p99 latency per dependency, and circuit breaker state transitions.
  • Azure Monitor alerts on sustained circuit-breaker-open state, cost-per-day anomalies, and elevated content-filter trigger rates.

Cost considerations

  • Resource tagging (by team/feature) across all services enables cost allocation reporting in Azure Cost Management.
  • APIM and Container Apps both have idle-cost implications distinct from Azure OpenAI's pure usage-based billing — model the FULL stack's cost, not just the AI calls.
  • Cosmos DB provisioned throughput (RU/s) should be sized to actual conversation volume, with autoscale considered over fixed provisioning for unpredictable traffic.

Failure handling

  • A circuit breaker (Resilience4j) around every external dependency — Azure OpenAI, Azure AI Search, Cosmos DB — each with its own fallback behavior, not a single generic catch-all.
  • Graceful degradation: if Azure AI Search is unavailable, the chat can still respond without RAG context, clearly disclosing reduced capability rather than failing the whole request.
  • Cosmos DB write failures for conversation history are logged and retried asynchronously — a transient persistence failure shouldn't block the user from getting their chat response.

Testing

  • Unit tests per service layer with mocked Azure SDK clients.
  • Integration tests against test-tier Azure resources, run in a dedicated pipeline stage.
  • Chaos-style tests simulating each dependency's failure (timeout, 429, connection refused) to verify circuit breakers and fallbacks actually trigger.
  • Load testing to validate autoscaling behavior and confirm rate-limit handling under realistic concurrent traffic.
