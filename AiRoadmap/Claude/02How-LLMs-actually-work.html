01 Foundations

What is Artificial Intelligence?

Simple explanation

AI is software that performs tasks we normally associate with human intelligence — recognizing images, understanding language, making decisions — by learning patterns from data instead of following rules a person wrote down for every possible case.

Technical explanation

As a field, AI covers symbolic reasoning, search, and planning as well as statistical learning — but almost everything called "AI" today falls under machine learning: fitting a parameterized function to data so it generalizes to inputs it has never seen, rather than being hand-coded. What makes a system "AI" isn't magic — it's that the mapping from input to output was learned, not authored.

Real-world example
Spam filters, product recommendations, fraud-scoring models, voice assistants, and the perception stack in a self-driving car are all "AI" — most have nothing to do with generating text, and predate the current LLM wave by decades.
Backend developer analogy
A rules engine is code you write: if (creditScore < 600) reject();. An ML system is closer to inferring that threshold — and dozens of other interacting conditions — automatically from a million past loan outcomes, producing a function no human explicitly wrote line by line.
Common misconception
"AI" does not imply reasoning, understanding, or consciousness — it's pattern-matching at scale. It also isn't synonymous with machine learning: rule-based expert systems from the 1980s are classic AI with zero learning involved.
Interview question
How would you explain AI to a non-technical stakeholder, and how does it differ from a hardcoded rules engine?
Show a strong answer
Frame it around where the logic comes from: a rules engine encodes logic a person wrote; an AI/ML system encodes logic inferred statistically from historical examples. The tradeoff for the stakeholder: you get a system that can generalize to cases nobody explicitly anticipated, at the cost of losing the ability to point to a single line of code that explains any one decision.
Practical exercise
List 3 features in a system you've worked on that use hardcoded if/else business logic. For each, ask: "could this be learned from historical data instead?" Note what data you'd need to collect to train it.
02 Foundations

Machine Learning vs Deep Learning vs Generative AI

Simple explanation

Machine learning is the umbrella term for any system that learns from data. Deep learning is a type of machine learning that uses many-layered neural networks to learn patterns automatically instead of relying on features a human engineered by hand. Generative AI is a type of deep learning built specifically to produce new content — text, images, audio — rather than just predicting a label or a number.

Technical explanation

Classical ML (linear/logistic regression, decision trees, gradient-boosted trees, SVMs) typically consumes hand-engineered features. Deep learning replaces manual feature engineering with layered representation learning — each layer of the network learns increasingly abstract features straight from raw input. Generative AI models are deep learning models trained with an objective that lets them represent a full probability distribution over possible outputs, so they can sample new, coherent artifacts — not just score or classify an existing input.

Real-world example
ML: a credit-risk score built on structured features. Deep learning: an image classifier (CNN) trained end-to-end on raw pixels to output a category. Generative AI: an LLM drafting a code review, or a text-to-image model producing a product photo from a description.
Backend developer analogy
Classical ML is like a fraud-scoring microservice with a hand-built feature pipeline (ETL stage) feeding it. Deep learning skips that ETL stage — the model learns its own features from raw data. Generative AI changes the API contract entirely: instead of returning a score or class, the service returns a whole generated artifact.
Common misconception
"Deep learning and generative AI are the same thing" is false — an image-classification CNN is deep learning but not generative; it only ever outputs a label, never a new image. "ML always means neural networks" is also false — plenty of production ML (gradient-boosted trees, for instance) has nothing to do with neural nets.
Interview question
Is every deep learning model generative? Give a counter-example.
Show a strong answer
No. A deep learning model is generative only if it's trained to model a probability distribution it can sample new outputs from. A ResNet image classifier is deep learning — many stacked layers, learned features — but it only maps an image to a fixed set of class probabilities; it never produces new content, so it isn't generative.
Practical exercise
Classify these precisely — AI, ML, DL, and/or GenAI (some fit more than one): a spam filter, Netflix's recommendation engine, ChatGPT, a fraud-detection model, a text-to-image tool.
03 Foundations

What is an LLM?

Simple explanation

A large language model is a neural network trained on enormous amounts of text to predict what word or word-fragment comes next in a sequence. Through that one deceptively simple objective, repeated across trillions of examples, it ends up learning grammar, facts, reasoning patterns, and style well enough to hold conversations, write code, and summarize documents.

Technical explanation

Specifically, an LLM is a transformer-based neural network with (typically) billions of parameters, trained via self-supervised next-token prediction over massive text corpora — this stage is called pre-training. The resulting "base model" is then usually further refined with instruction tuning and preference optimization (like RLHF) so its outputs are helpful and aligned with what users actually want, rather than just statistically plausible internet text.

Real-world example
GPT, Claude, Gemini, and Llama are all LLMs — the same underlying idea (predict the next token, at scale) powers chat assistants, code-completion tools, summarizers, and agent frameworks.
Backend developer analogy
Treat an LLM like an extremely sophisticated, stateless autocomplete service: you send a full sequence of tokens as the request payload, it returns a probability distribution over "what's the most plausible next token," and you repeat the call to build a full response — much like a REST API where you resend the entire relevant context on every call because the server holds no session state for you.
Common misconception
LLMs do not look things up in a database of facts. There's no retrieval step inside the base model — everything it "knows" is compressed into billions of numeric weights learned during training, not stored as queryable records you could point to.
Interview question
In one sentence, what is an LLM actually trained to do at the lowest level?
Show a strong answer
Predict the probability distribution over the next token given all the tokens before it — everything else (conversation, reasoning, code generation) is an emergent behavior of doing that one task extremely well across a huge and varied training corpus.
Practical exercise
Ask any LLM chat interface: "What is your training objective at the lowest level?" Compare its answer to the technical explanation above and note anything it oversimplifies.
04 Foundations

How LLMs work, at a high level

Simple explanation

You send text in. The model breaks it into small pieces called tokens, converts those into numbers it can do math on, runs them through many layers of a neural network that mix information between all the tokens, and out comes a probability distribution over what the next token should be. It picks one, adds it to the sequence, and repeats — one token at a time — until it has produced a full response.

Technical explanation

The precise pipeline: text → tokenizer → token IDs → embedding lookup (plus positional information) → N stacked transformer blocks, each doing self-attention followed by a feed-forward layer with residual connections and normalization → a final linear projection onto the vocabulary → softmax → a probability distribution over the next token → a sampling strategy selects one → it's appended to the sequence → the whole thing repeats. This full pipeline gets its own deep dive right after this section.

Real-world example
This is literally what happens, end to end, every single time you send a message to Claude, ChatGPT, or Gemini — no exceptions, no shortcuts.
Backend developer analogy
Think of it as a deeply layered, learned request pipeline — similar to a chain of middleware in a web framework. But instead of distinct hand-written logic per stage, each "layer" is the SAME learned transformation (a matrix of trained weights) applied repeatedly, layer after layer, refining the representation a little more each time.
Common misconception
The model does not generate the whole response "at once," even though a fast UI can make it look that way. Generation is autoregressive — one token at a time, with each new token fed back in as part of the input for producing the next one.
Interview question
Why is text generation described as "autoregressive" — what does that term actually mean here?
Show a strong answer
"Autoregressive" means each new output is predicted using the model's own previous outputs as part of the input. The model predicts token N+1 using tokens 1...N (which include tokens it generated itself earlier in the same response), then predicts N+2 using 1...N+1, and so on — it's regressing on its own prior outputs, repeatedly.
Practical exercise
Take a short sentence and write out where you think the token boundaries would fall. You'll verify this for real in the Tokenizer Lab later in this workbook.

Let's trace one concrete prompt through all eight stages: "The capital of France is".

1 → 2. User prompt → Tokenizer

Your raw string arrives as a sequence of characters. The tokenizer — a separate, fixed algorithm trained once when the model was built, not something the model "decides" per request — splits it into sub-word chunks from a fixed vocabulary, typically 100,000–200,000 entries. Roughly: ["The", " capital", " of", " France", " is"]. Common words are usually single tokens; rarer words get split into smaller pieces.

2 → 3. Tokenizer → Token IDs

Each token string is looked up in the tokenizer's vocabulary table and replaced with an integer — its position in that table. Illustratively: [791, 6864, 315, 9822, 374]. From this point on, the model never sees text again — only integers.

3 → 4. Token IDs → Embeddings

Each integer ID indexes into an embedding matrix — one learned row-vector per vocabulary entry, often 4,000+ numbers long — giving each token a dense numeric representation. A positional signal is added on top so the model can tell that "France" appeared 4th, not 1st, since the embedding lookup alone has no sense of order.

4 → 5. Embeddings → Transformer

These vectors flow through dozens of stacked transformer blocks. Inside each block, self-attention lets every token's vector update itself by weighing information from every OTHER token in the sequence — this is how "capital" ends up strongly influenced by "France" by the time processing finishes. A feed-forward layer then further transforms each position. This repeats, layer after layer, each one refining the representation further.

5 → 6. Transformer → Probability distribution

After the last layer, the model takes the final position's vector and projects it through one more learned matrix onto a vector the size of the entire vocabulary — one raw score ("logit") per possible next token. A softmax function turns those scores into a proper probability distribution that sums to 1: maybe "Paris" at 0.87, "the" at 0.04, "a" at 0.02, and a long tail of everything else.

6 → 7. Probability distribution → Next-token prediction

A sampling strategy — greedy, temperature, top-k, top-p, or some combination — picks one token from that distribution. With most reasonable settings here, that's " Paris", since it's overwhelmingly the most probable continuation.

7 → 8. Next-token prediction → Generated response

The chosen token is appended to the sequence, and the ENTIRE pipeline — tokenize (already done, just append), embed, run through the transformer, get a new distribution, sample — repeats to produce the token after that, and the one after that, until a stop condition is hit (an end-of-sequence token, a max length, or a stop sequence you configured). What looks like one API response is actually dozens to thousands of individual passes through this exact pipeline.

Why this matters for engineering, not just trivia
Prompt engineering is really just controlling stage 1. System messages, few-shot examples, and retrieved context (RAG) are all just different ways of shaping the token sequence that gets fed into stage 4 onward. Once this pipeline clicks, "prompt engineering" stops feeling like folklore and starts feeling like designing the input to a well-understood function.
05 Under the hood

Pre-training

Simple explanation

Pre-training is the expensive process of teaching a raw neural network to predict the next word over a huge collection of text — books, websites, code, articles — so it absorbs grammar, facts, and reasoning patterns before it's ever adapted for a specific job like chatting helpfully.

Technical explanation

This is self-supervised learning: no human labels are needed, because the "label" for training is simply the next token in text that already exists. It requires massive compute — thousands of GPUs/TPUs running for weeks to months — performing gradient descent over trillions of tokens, producing a base model whose weights encode statistical regularities of language and, incidentally, whatever world knowledge was present in the training data up to some cutoff date.

Real-world example
Open releases sometimes ship the raw "base" checkpoint separately from the "instruct"/"chat" checkpoint — the base model completes text plausibly but doesn't reliably follow instructions or refuse harmful requests the way the instruction-tuned version does.
Backend developer analogy
Pre-training is like compiling a massive, general-purpose library once, at huge cost, that many downstream applications later link against. Instruction-tuning and fine-tuning are the thin adapter layer you write on top for your specific use case.
Common misconception
Pre-training doesn't involve humans manually labeling "correct answers." The correct answer for next-token prediction IS the existing text itself — which is exactly why it can scale to close to the entire internet, unlike traditional supervised learning that requires human-labeled datasets.
Interview question
Why is next-token prediction over raw text called "self-supervised" rather than "supervised"?
Show a strong answer
Supervised learning needs a human-provided label for every example. Self-supervised learning derives the label automatically from the data's own structure — here, the "label" for predicting token N is simply token N as it already appears in the text, so no human annotation step is needed at all.
Practical exercise
Search for the approximate training corpus size (in tokens) of one modern open LLM, and convert it into something intuitive — e.g., "roughly X times the entire English Wikipedia."
06 Under the hood

Tokenization

Simple explanation

Tokenization is the process of breaking raw text into the small chunks — tokens — that a model actually operates on, since a model can't do useful computation directly on arbitrary raw characters as its unit of work.

Technical explanation

Modern LLMs mostly use subword tokenization algorithms like Byte-Pair Encoding (BPE) or similar schemes (tiktoken, SentencePiece), trained once on a large corpus to find a fixed vocabulary of the most frequent character sequences — balancing vocabulary size against sequence length. Common whole words often become a single token; rare or foreign words fragment into several pieces. This is exactly why token count differs from word count.

Real-world example
LLM APIs bill per token, not per word or character — a prompt full of rare technical jargon or non-English text can cost noticeably more than a plain-English prompt of the same apparent length.
Backend developer analogy
Similar to a compiler's lexer breaking source code into tokens (identifiers, keywords, punctuation) before parsing — except the LLM tokenizer's vocabulary was learned statistically from data, not defined by a hand-written language grammar.
Common misconception
Tokens are not the same as words. A single word can be one token or several; punctuation and even a leading space are frequently folded into a token as part of its identity, which trips people up when they try to count tokens by eyeballing text.
Interview question
Why do LLM providers bill per token instead of per character or per word?
Show a strong answer
Because tokens — not characters or words — are the actual unit of compute the model consumes: every token requires a full pass through every layer of the network. Token count is the metric that directly tracks compute cost, so it's the natural billing unit.

07 Under the hood

Tokens and token IDs

Simple explanation

Once text is split into tokens, each token is converted into a plain integer — its token ID — by looking it up in a fixed vocabulary table built when the tokenizer was created. From here on, the model only ever deals with numbers.

Technical explanation

The vocabulary is a fixed bidirectional mapping between token strings and integer IDs, typically 32,000 to 250,000 entries depending on the model family. Token IDs are the literal values sent to and returned from a raw model endpoint; the readable text you see in a chat UI is decoded from IDs on the way out, after generation finishes.

Real-world example
Libraries like OpenAI's tiktoken let you inspect the exact IDs a given string maps to, entirely offline — useful for precisely estimating token counts and cost before making an API call.
Backend developer analogy
Like an employee ID number versus an employee's name — the backend (the model) only ever stores and processes the ID; the human-readable name (token text) is purely a display-layer lookup.
Common misconception
Token IDs are not stable across model families. "the" might be ID 262 in one tokenizer and something completely different in another — you can never mix or reuse raw token IDs between two models with different vocabularies.
Interview question
If you fine-tuned model A and tried to feed its raw output token IDs directly into model B, why would that break?
Show a strong answer
Token IDs are only meaningful relative to the specific vocabulary table they were assigned from. Model B's tokenizer maps a completely different set of strings to those same integers, so decoding model A's IDs with model B's vocabulary produces garbage text, not the intended content.
Practical exercise
If you have access to any tokenizer tool, look up the ID for " the" (with a leading space) versus "The" (capitalized, no leading space) and note whether they're different IDs.
08 Under the hood

Embeddings

Simple explanation

An embedding is a list of numbers — a vector — that represents the "meaning" of a piece of text in a way a neural network can do math with. Texts that mean similar things end up with vectors that sit close together in that numeric space.

Technical explanation

There are two related but distinct uses. Token embeddings are the per-token vectors looked up inside an LLM's input layer, learned jointly with the rest of the model purely to support next-token prediction. Standalone embedding models are separate models trained specifically so whole sentences or documents map to vectors useful for similarity search, clustering, and retrieval — the backbone of RAG. Similarity between two vectors is typically measured with cosine similarity.

Real-world example
A RAG system embeds a user's question and every document chunk, then finds the chunks whose embeddings are closest to the question's embedding — this is literally how a vector database like pgvector, Pinecone, or Chroma answers "find me similar text."
Backend developer analogy
Unlike a hash function, which deliberately scatters similar inputs randomly, an embedding function deliberately places semantically similar inputs NEAR each other — closer in spirit to a well-designed spatial index than to a hash table.
Common misconception
Embeddings used for retrieval and the token embeddings inside an LLM's input layer are usually produced by entirely different, separately-trained models. Mixing embeddings from two different embedding models in the same vector index will generally not produce meaningful similarity results — embedding spaces aren't interchangeable across models.
Interview question
Why can't you mix embeddings from two different embedding models in the same vector index and expect meaningful similarity search?
Show a strong answer
Each embedding model learns its own geometry during training — there's no guarantee two different models place the same concept at the same coordinates, or even use compatible distance notions. Comparing a vector from model A against one from model B is comparing two unrelated coordinate systems; the resulting "similarity" score is meaningless.
Practical exercise
Pick 5 words or phrases and guess which pairs an embedding model would place closest together. If you have access to any embedding API, check your intuition against real cosine similarity scores.
09 Under the hood

Transformer architecture

Simple explanation

The transformer is the specific neural network design nearly every modern LLM is built from. Its key innovation: it processes an entire sequence of tokens at once and lets every token directly "look at" every other token to decide what's relevant, instead of processing text strictly one word at a time in order the way older architectures did.

Technical explanation

A transformer block consists of multi-head self-attention followed by a position-wise feed-forward network, each wrapped with residual (skip) connections and layer normalization, stacked N times (N = the model's "depth"). Introduced in the 2017 paper "Attention Is All You Need," it replaced recurrent architectures (RNNs/LSTMs) specifically because self-attention parallelizes across the whole sequence during training — which scales dramatically better on modern GPU/TPU hardware than a mechanism that must process tokens strictly in order.

Real-world example
GPT, Claude, Gemini, Llama, BERT, and T5 are all transformer variants — decoder-only (autoregressive) architectures dominate today's chat-oriented LLMs specifically because that structure fits next-token generation naturally.
Backend developer analogy
An RNN processes a request queue strictly one item at a time, only ever knowing about what came before. A transformer gives every worker in a room simultaneous visibility into every other worker's current state, letting all of them update based on the full picture at once — far more parallelizable, which is exactly why it scales on GPUs.
Common misconception
"Transformer" is an architecture family, not one specific model. GPT and BERT are both transformers but differ substantially — decoder-only/autoregressive versus encoder-only/bidirectional — and are suited to different tasks accordingly.
Interview question
Why did transformers displace RNNs/LSTMs for large-scale language modeling?
Show a strong answer
RNNs must process tokens sequentially — each step depends on the previous one's hidden state — which prevents parallelizing across the sequence during training and creates long gradient paths that make learning long-range dependencies harder. Self-attention lets every token attend to every other token in a single parallel operation, which both trains far faster on GPUs and captures long-range relationships more directly.

Search for the "Attention Is All You Need" architecture diagram and try to label which part corresponds to tokenization, embeddings, attention, and the final output distribution, using what you've learned so far.
10 Under the hood

Attention and self-attention

Simple explanation

Self-attention is the mechanism that lets each token figure out which other tokens are relevant to it, and pull in information from them accordingly. It's how a model "knows" that in "The trophy didn't fit in the suitcase because it was too big," the word "it" refers to the trophy, not the suitcase.

Technical explanation

For every token, the model computes a Query vector; every token also produces a Key and a Value vector. The attention score between token i and token j is a scaled dot product of Query_i and Key_j, passed through softmax to get weights — those weights compute a weighted sum over all Value vectors, and that sum becomes token i's updated representation. "Multi-head" attention runs several of these computations in parallel with different learned projections, letting the model track several kinds of relationships (syntax, coreference, topical relevance) simultaneously.

Real-world example
This mechanism is exactly what resolves pronoun references, tracks subject-verb agreement over long distances, and connects a variable's use back to its definition when an LLM reads a large block of source code.
Backend developer analogy
Think of a JOIN with a dynamically-computed relevance weight instead of a fixed equality condition — every token "joins" against every other token, but how much weight that join gets is itself computed and learned, not hardcoded.
Common misconception
Self-attention does not mean the model "reads the sentence like a person, left to right, paying attention as it goes." The attention computation for a given pass considers ALL tokens simultaneously, in parallel — not sequentially, the way a human skims a page.
Interview question
What problem does multi-head attention solve that a single attention computation wouldn't?
Show a strong answer
A single attention "head" learns one particular pattern of relevance. Language has many simultaneous kinds of relationships — syntactic (subject/verb), coreference (pronoun/antecedent), topical relevance — and a single head can't specialize in all of them at once. Multiple heads, each with their own learned projections, let the model track several of these relationship types in parallel and combine the results.
Practical exercise
Write an ambiguous pronoun sentence like the trophy/suitcase example, ask an LLM chat interface what the pronoun refers to and why, and see if its explanation lines up with the attention intuition above.
11 Under the hood

Next-token prediction

Simple explanation

At every single step of generation, the model's only job is producing a probability for every possible next token, given everything so far — nothing more. Capabilities like "reasoning" and "planning" emerge from chaining this one operation over and over, not from a separate reasoning module bolted on somewhere.

Technical explanation

Formally, the model represents P(token_t | token_1, ..., token_{t-1}) — a conditional probability distribution over the vocabulary — and the autoregressive generation loop samples from it repeatedly, feeding each choice back in as new conditioning context, building up the full sequence probability as a product of these per-token conditional probabilities.

Real-world example
Chain-of-thought prompting ("think step by step") works because generation is conditioned on everything produced so far — forcing the model to write out intermediate steps changes what tokens are probable next, effectively giving it more working context before it commits to a final answer.
Backend developer analogy
Comparable to a recursive function whose only job is "compute the single next output element" — yet it achieves complex, coherent results purely through how many times it's called again, and with what accumulated state.
Common misconception
The model doesn't "decide" the full response in advance and reveal it token by token for dramatic effect. At each step it genuinely does not yet know what it will output several tokens later — long-range consistency emerges from context conditioning, not from an internal plan object it's secretly following.
Interview question
How does next-token prediction alone explain why "let's think step by step" tends to improve accuracy on reasoning tasks?
Show a strong answer
Every generated token becomes conditioning context for the next one. Writing out intermediate steps means the final answer token is predicted conditioned on those steps being present in context — effectively giving the model more relevant "working memory" to condition on, rather than forcing it to jump straight from question to answer in a single conditional probability estimate.
Practical exercise
Give an LLM a multi-step math word problem two ways: once asking only for the final number, once asking it to show its work first. Compare accuracy and consistency across a few repeated tries.
12 Under the hood

Context window

Simple explanation

The context window is the maximum number of tokens — input plus output combined — an LLM can consider at once in a single request. Anything beyond that limit simply isn't seen by the model at all.

Technical explanation

Context length is an architectural property tied to how the model was trained — its positional encoding scheme, and the attention computation's cost, which scales at best linearly and at worst quadratically with sequence length depending on the attention implementation. Modern models range from roughly 8K tokens up to 1M+ tokens depending on model and provider; exceeding the limit typically truncates, errors, or (in chat UIs) silently drops older messages.

Real-world example
A 200K-token context window is roughly hundreds of pages of text — but stuffing an entire codebase or knowledge base into every request is often still the wrong architectural choice, which is exactly the problem RAG exists to solve more efficiently and cheaply.
Backend developer analogy
Like the working memory of a single function call or stack frame — everything the model can "see" for this one call has to fit inside that frame. Nothing persists automatically between separate calls unless you deliberately pass it back in, exactly like a stateless service with no server-side session.
Common misconception
A bigger context window does not mean the model "remembers" a previous, separate conversation. Every API call is stateless — if the relevant tokens aren't included in THIS request's context window, the model has no access to them, no matter how large the window is in general.
Interview question
Your chat app's context window is full. What are your architectural options, and what does each cost you?
Show a strong answer
Options include: truncating/dropping oldest messages (loses history), summarizing older turns into a shorter recap (loses detail, costs an extra LLM call), switching to RAG to retrieve only relevant history/documents on demand (adds retrieval infrastructure and complexity), or moving to a model with a larger context window (costs more per token and may be slower). There's no free option — each trades away something.
Practical exercise
Estimate the context budget for a Document Q&A app: system prompt (~200 tokens) + 5 retrieved chunks (~500 tokens each) + conversation history (~1000 tokens) + room for a 500-token answer. Does it fit in an 8K window? A 32K window?
13 Under the hood

Model parameters

Simple explanation

Parameters are the individual numbers (weights) inside a neural network that get adjusted during training. When you hear a model has "70 billion parameters," that's the count of these tunable numbers — roughly correlated with capability and cost.

Technical explanation

Parameters live in the weight matrices of every embedding table, attention projection, and feed-forward layer throughout the network. More parameters generally mean more capacity to represent complex patterns, but also more memory (VRAM) and compute for both training and inference — a major reason serving cost scales with parameter count, and why smaller distilled or quantized models trade some capability for dramatically lower cost and latency.

Real-world example
Model families are frequently offered in multiple sizes (a small, fast tier alongside a large flagship tier) explicitly so engineers can trade capability against latency and cost per request depending on the feature's needs.
Backend developer analogy
Roughly like comparing a small config file with a handful of tunable settings to an enormous configuration surface with billions of independent knobs — more knobs allow finer-grained behavior, but every knob costs memory to store and compute to evaluate on every request.
Common misconception
A model with more parameters isn't automatically "better" for a given task. Training data quality/quantity, architecture choices, and fine-tuning matter enormously too — a well-tuned smaller model frequently beats a poorly-tuned larger one on a specific task, at a fraction of the cost.
Interview question
Why might you deliberately choose a smaller, cheaper model for a production feature even if a larger one scores higher on general benchmarks?
Show a strong answer
Production features usually have a specific, narrower task than "general capability" — classification, extraction, simple rewriting. If a smaller model hits acceptable accuracy on that specific task, its lower latency and per-request cost at high volume usually outweigh a marginal accuracy gain from a much more expensive flagship model.

For a feature like classifying support tickets by urgency, list the tradeoffs between a small fast model and a large flagship model: latency, cost per call, accuracy needed, and expected request volume.
Deep dive

What is the context window, really?

The one-line definition from earlier — "the max tokens the model can see at once" — is correct but hides three things engineers building real systems need to know.

1. It isn't free to make bigger

Self-attention computes a relevance score between every pair of tokens. In the most straightforward implementation, that's a cost that grows quadratically with sequence length — double the context, and the attention computation can cost roughly four times as much. Providers use various optimizations (sparse attention, sliding windows, better kernels) to soften this, but it's why enormous context windows come with real latency and cost implications, not just a config flag someone forgot to raise.

2. Position in context affects reliability — "lost in the middle"

Research on long-context models has repeatedly found that models are most reliable at using information placed near the very beginning or the very end of the context, and measurably less reliable at using information buried in the middle of a very long prompt — even when that information is technically "within the window." Practically: if you're stuffing 20 retrieved documents into a prompt, don't assume document #11 gets the same attention as document #1 or #20.

3. Context window, fine-tuning, and RAG are three different ways to give a model information — and they're not interchangeable

Inference

Simple explanation

Inference is simply "running the trained model to produce an output," as opposed to training, which adjusts the model's weights. Every call to an LLM API is an inference call — the weights are already fixed and don't change as a side-effect of your request.

Technical explanation

Inference is a forward pass through the network with frozen weights, given an input sequence, producing output logits/probabilities. Cost is dominated by tokens processed (both the input "prefill" pass and the output "decode" steps) and model size. Providers optimize heavily with KV-caching — reusing previously computed key/value vectors instead of recomputing attention over the whole sequence from scratch for every new token — plus batching and quantization.

training (once, expensive)
Data → gradient descent → updated weights, repeat
inference (every request)
Fixed weights + new input → forward pass → output
Real-world example
Every single API call to GPT, Claude, or Gemini is an inference call — no learning happens as a side-effect of normal usage, unless you've explicitly opted into a separate fine-tuning workflow.
Backend developer analogy
Training is like compiling and building a piece of software once; inference is like running that already-built binary against new input, over and over, without ever recompiling it.
Common misconception
Using a chat product does not retrain or fine-tune the underlying deployed model in real time from your conversation — your chats don't "teach" that specific model instantly, regardless of any separate, explicit data-usage policy a provider might have for future training runs.
Interview question
Why is inference cost proportional to both input AND output token count, even though you only "asked" for the output?
Show a strong answer
The model must run every input token through every layer during the prefill pass to build up the context it needs before it can generate anything — that's real compute, even though no new text is produced yet. Output tokens then each require their own additional forward step. Both phases consume GPU compute, so both are billed.
Practical exercise
Research how KV-caching reduces the cost of generating each subsequent output token in a long response, compared to naively recomputing attention over the whole sequence from scratch every single step.

Temperature

Simple explanation

Temperature controls how "adventurous" the model's word choices are. Low temperature makes it pick the most likely next token almost every time — focused and predictable. High temperature makes it more willing to pick less-likely tokens — more varied, occasionally less coherent.

Technical explanation

Temperature rescales the logits before the softmax: divide every logit by T before applying softmax. T<1 sharpens the distribution, making the model MORE confident in its top choice than it "naturally" was. T>1 flattens it, spreading probability mass more evenly across candidates. T=1 leaves the raw distribution unchanged. T=0 is a special case: always greedily pick the single highest-probability token — deterministic, modulo hardware-level nondeterminism.

Real-world example
Use temperature 0 (or near it) for classification, structured extraction, and code generation, where you want the single "obviously correct" answer. Use higher temperature (0.7–1.0+) for brainstorming and creative writing, where varied outputs are the point.
api_call.py
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=200,
    temperature=0.2,          # low = focused, near-deterministic
    messages=[{"role": "user", "content": "Classify this ticket's urgency: ..."}]
)
print(response.content[0].text)
Backend developer analogy
Like a randomness/jitter parameter in a load-balancing or retry algorithm — turn it down for the deterministic "best" choice every time, turn it up to deliberately explore more of the solution space.
Common misconception
Temperature=0 does not guarantee bit-for-bit identical output across repeated calls on most production APIs. Floating-point operation ordering on GPUs and routing across different hardware can still introduce small sources of nondeterminism even when sampling is nominally "off."
Interview question
Why doesn't temperature=0 always guarantee perfectly reproducible output in production LLM APIs?
Show a strong answer
Temperature=0 removes the SAMPLING source of randomness (it always greedily picks the top token), but doesn't remove every source of numerical variability in the underlying computation — floating-point arithmetic isn't perfectly associative across different execution orders, and production systems may batch or route requests differently across runs, which can occasionally flip a near-tied top token.

Top-k

Simple explanation

Top-k sampling restricts the model to choosing only among the k most likely next tokens, discarding every other candidate no matter how the probabilities actually shake out.

Technical explanation

Given the full probability distribution over the vocabulary, top-k keeps only the k tokens with the highest probability, renormalizes their probabilities to sum to 1 among just that subset, and samples from that restricted distribution. Small k is very restrictive, close to greedy decoding; large k is closer to sampling from the full, unrestricted distribution.

Real-world example
top_k=1 is equivalent to greedy/deterministic decoding. A moderate top_k (say, 40–50) is common when you want some variety while still guarding against the model ever picking a wildly implausible token from the long statistical tail.
Backend developer analogy
Like a rate limiter that only ever considers the top K requests in a priority queue and ignores everything below that fixed rank, regardless of how close request K+1 actually was in priority.
Common misconception
Top-k uses a FIXED candidate count regardless of how probability mass is actually distributed. If the top 3 tokens already account for 99% of the probability, top-k=40 still keeps 37 essentially irrelevant tokens eligible — exactly the shortcoming that motivated top-p.
Interview question
What's a scenario where top-k performs noticeably worse than top-p, and why?
Show a strong answer
When the model is extremely confident (one token holds 95%+ of the probability), a fixed top-k still forces in k-1 near-irrelevant tokens as "eligible," adding unnecessary noise to sampling. Top-p would collapse the nucleus down to just 1–2 tokens automatically in that same situation, since it responds to the actual shape of the distribution rather than a fixed count.
Practical exercise
In the Parameter Playground, set top-k very low (1–2) versus high (40+) on the same prompt and temperature, and observe how much the candidate pool changes.

Top-p (nucleus sampling)

Simple explanation

Top-p keeps adding the next most-likely tokens to the candidate pool until their combined probability crosses a threshold p, then samples only from that pool — so the SIZE of the pool adapts automatically to how confident the model's distribution actually is.

Technical explanation

Sort tokens by probability descending, accumulate probability until the cumulative total reaches p, keep that "nucleus" of tokens, renormalize, and sample from it. When the model is very confident (one token at 95% probability), the nucleus might be just 1–2 tokens even at p=0.9. When the model is uncertain (probability spread across many tokens), the nucleus naturally grows to include more candidates.

Real-world example
top_p=0.9 is a commonly used default across many providers, often used instead of, or together with, top_k as an additional safeguard.
Backend developer analogy
Compare to a dynamic autoscaling policy versus top-k's fixed instance count — top-p adapts the "acceptable candidate pool" size to the shape of current demand (the distribution), rather than always keeping a hardcoded count on hand.
Common misconception
Temperature and top-p are not the same lever, and using both together is common, not redundant. Temperature reshapes how peaked the distribution is BEFORE sampling; top-p decides which portion of that reshaped distribution is even eligible to be sampled from.
Interview question
How do temperature and top-p interact when both are set at once — what happens first?
Show a strong answer
Temperature is applied first, rescaling the raw logits and reshaping how peaked or flat the distribution is via softmax. Top-p is applied second, on that already-reshaped distribution, cutting it down to the smallest set of tokens whose cumulative probability reaches p. The final sample is drawn from that filtered, temperature-adjusted distribution.

In the Parameter Playground, set temperature high (1.3) with top_p=1.0 (no truncation), then repeat with top_p=0.5 (aggressive truncation), and compare how "wild" the surviving candidate pool looks in each case.

Simple explanation

The prompt is everything you send TO the model — system/user messages and any retrieved context included. The completion is everything the model generates back. Together they make up the full sequence the model actually processes in one call.

Technical explanation

API responses typically report token usage split into prompt/input tokens and completion/output tokens, since providers usually price these differently — output tokens are typically more expensive per token than input tokens, because generating each one requires its own additional forward step, while input tokens are processed together in one prefill pass.

Cost estimation for a feature must account for both sides — a RAG app with a large retrieved context has high prompt-token cost even when the final answer is short.

Like separating a function's argument payload from its return value — same call, two separately measured (and, here, separately priced) halves.

A "short prompt" doesn't necessarily mean a cheap API call. If that short prompt triggers a very long completion, completion-token cost can dominate the total, even though what you typed was tiny.

Input tokens are processed together in one batched "prefill" forward pass. Hallucinations

Simple explanation

A hallucination is when an LLM generates text that sounds fluent and confident but is factually wrong or entirely made up — a fabricated citation, a nonexistent API method, an incorrect date — stated in exactly the same confident tone as something true.

Technical explanation

Hallucinations arise naturally from how these models work: next-token prediction optimizes for "what's a statistically plausible continuation," not "what's verifiably true." There is no built-in fact-checking or grounding step in base generation unless one is explicitly added (RAG, tool use, a verification pass). The model has no reliable internal signal distinguishing "I recall this precisely" from "this is a plausible-sounding guess."

Real-world example
LLMs confidently inventing a plausible-looking but nonexistent library function, or citing a real-sounding academic paper that doesn't actually exist, are two extremely common, well-documented hallucination patterns.
Backend developer analogy
Like a junior engineer under time pressure giving a confident-sounding answer to something they don't actually know, rather than saying "I'm not sure" — the fluency of the answer carries no signal about its accuracy.
Common misconception
Hallucination is not a rare bug that will simply be patched away. It's a structural consequence of the generation objective itself — techniques like RAG, tool use, and lower temperature reduce it, but no current LLM architecture eliminates it entirely. There's a full deep dive on this right after this module.
Interview question
Why can't hallucinations simply be "fixed" with better training data alone?
Show a strong answer
Better data reduces the RATE of certain hallucinations, but the underlying mechanism — sampling a plausible next token with no ground-truth verification step — remains. Even a perfectly-trained model will occasionally sample a fluent, wrong continuation for questions genuinely outside its knowledge, unless an external grounding mechanism (retrieval, tools) is added to check claims against a verifiable source.

Deterministic vs probabilistic behavior

Simple explanation

Traditional software is deterministic — the same input reliably produces the same output every time. LLMs are fundamentally probabilistic — the same prompt can produce different outputs across calls (unless settings are pinned down tightly), because generation involves sampling from a probability distribution, not executing a fixed set of instructions.

Technical explanation

Even at temperature 0 (nominally deterministic/greedy), floating-point non-associativity, GPU parallelism ordering, and load-balancing across slightly different hardware or batches can introduce small variability in production systems. At nonzero temperature, variability is by design, not an implementation quirk — sampling IS the generation mechanism.

Real-world example
This is exactly why testing an LLM-powered feature can't just be "run it once and assert the exact output" the way a typical unit test would work against deterministic backend code — teams need semantic/structural assertions, multi-sample evaluation, or acceptance of a range of valid outputs.
Backend developer analogy
Like the difference between a pure function and a function with a random or hidden-state dependency injected in — the second needs a fundamentally different testing strategy (property-based testing, statistical sampling) than "assert exact equals."
Common misconception
"Probabilistic" doesn't mean "unreliable" or "broken." It's an intentional design property enabling creativity and variation. The real mistake is applying the wrong expectation — exact reproducibility — to a system that was never designed to guarantee it.
Interview question
How would you design automated tests for an LLM-powered feature, given that exact output equality isn't a reliable test strategy?
Show a strong answer
Test at the level of structure and meaning rather than exact text: assert the output parses as valid JSON matching a schema, contains required fields/keywords, passes a rubric-based LLM-as-judge check, or falls within an expected semantic-similarity range of a reference answer. For critical paths, sample multiple generations and assert on aggregate pass rate rather than a single run.
Practical exercise

Why does temperature affect output? (the actual math, worked through)

"Temperature makes it more random" is true but skips the mechanism. Here's the arithmetic, with real numbers, so the effect stops being a black box.

Step 1 — the model produces raw scores (logits), not probabilities

Say the model is predicting the word after "The weather today is" and produces these raw logits for 4 candidate tokens: sunny = 3.0, cold = 2.0, strange = 1.0, purple = 0.1. These numbers aren't probabilities yet — they're unnormalized scores.

Step 2 — divide every logit by the temperature T

TokenRaw logitT = 0.5 (logit ÷ 0.5)T = 2.0 (logit ÷ 2.0)
sunny3.06.01.5
cold2.04.01.0
strange1.02.00.5
purple0.10.20.05

Dividing by a small T (0.5) makes the GAPS between logits bigger. Dividing by a large T (2.0) makes the gaps smaller.

Step 3 — softmax turns those into probabilities

TokenProbability at T = 0.5Probability at T = 2.0
sunny~85%~35%
cold~11%~21%
strange~2%~13%
purple~1%~8%

Because softmax is exponential, small gaps in the divided logits (T=0.5's bigger gaps) turn into LARGE gaps in probability — "sunny" dominates almost completely. Large T compresses the logit gaps, so softmax produces a much flatter, more evenly-spread probability distribution — "cold," "strange," even "purple" all become genuinely competitive candidates for sampling.

Why this explains the qualitative behavior

At low temperature, the already-most-likely token becomes drastically MORE likely relative to the rest — outputs converge toward the single "safest" continuation almost every time. At high temperature, the gaps between good and mediocre choices shrink, so genuinely less-likely (and occasionally incoherent) tokens get sampled meaningfully often. Nothing else about the model changes — same weights, same computation up through the logits — only this one rescaling step, right before sampling.

Deep dive

Why do LLMs hallucinate?

Four separate, compounding causes — worth knowing individually, because each one implies a different mitigation.

1. The training objective rewards fluency, not truth

Next-token prediction is scored against "does this match plausible text," not "is this verifiably correct." A confident, fluent, wrong sentence and a confident, fluent, correct sentence look statistically almost identical to the training objective — nothing in the loss function specifically penalizes confidently-stated falsehoods differently from confidently-stated truths.

2. There's no built-in grounding or citation mechanism

Unless a system explicitly adds retrieval (RAG) or tool use, the model has no mechanism to check a claim against an external, verifiable source before stating it — it's generating from compressed statistical patterns in its weights, not looking anything up.

3. Confidence is not calibrated to correctness

The model's OWN sense of "how sure am I" (insofar as that's even a coherent concept for it) doesn't reliably track whether a specific claim is true. It can be just as fluent and "confident-sounding" fabricating a nonexistent citation as stating a well-known fact — fluency and accuracy are produced by related but distinct aspects of the underlying computation.

4. Long-tail and rare facts get compressed lossily

Training data about very common facts appears many times, reinforcing accurate recall. Rare, obscure, or highly specific facts (an exact function signature, a niche statistic) appear rarely if at all — the model may only have a vague statistical impression to draw on, which it will still express in the same confident, fluent register as something it "knows" solidly.

Function / tool calling

Simple explanation

Function (tool) calling lets an LLM, instead of answering directly, output a structured request to call one of a set of functions you've described to it — like "call get_weather(city='Paris')" — which YOUR code then actually executes, feeding the result back to the model to continue.

Technical explanation

You provide the model a list of tool definitions — name, description, JSON-schema-typed parameters. At inference, based on context, the model decides whether to respond in plain text or emit a structured tool-call block naming a tool and matching arguments. Crucially, the model never executes anything itself — it only proposes a call; your application code runs it, handles errors, and sends the result back as a new message so the model can use it in its next generation.

Real-world example
This is the core mechanism behind agentic AI — an agent "searching the web," "querying a database," or "sending an email" is really the LLM repeatedly proposing tool calls that your orchestration code executes and returns results from.
tool_calling.py
tools = [{
    "name": "get_weather",
    "description": "Get the current weather for a city",
    "input_schema": {
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"],
    },
}]

response = client.messages.create(
    model="claude-sonnet-4-6", max_tokens=500,
    tools=tools,
    messages=[{"role": "user", "content": "What's the weather in Paris?"}],
)

for block in response.content:
    if block.type == "tool_use" and block.name == "get_weather":
        real_result = call_real_weather_api(block.input["city"])  # YOUR code runs this
        # ...send real_result back as a tool_result message to get the final answer
Backend developer analogy
Almost exactly like a strongly-typed RPC interface (think gRPC or an OpenAPI-described service) the model can choose to invoke — the model is the client deciding which remote call to make and with what arguments; your backend is the server actually executing it.
Common misconception
The model "calling a tool" doesn't mean it has any inherent ability to access the internet, a database, or anything external. It can only ever request that YOUR code do so — without your code implementing and safely executing that function, tool calling produces nothing but a structured request that goes nowhere.
Interview question
Walk through exactly what happens, end to end, when an LLM "calls a tool" to check the weather.
Show a strong answer
The model receives the user's question plus a list of available tool schemas in its context. It generates a structured tool-call output (not prose) naming the tool and arguments it judges relevant. Your application code intercepts that structured output, validates the arguments, calls the real weather API, and packages the result as a new "tool result" message. That message is appended to the conversation and sent back to the model in a fresh inference call, where the model now generates the final natural-language answer using the real data it was just given.
Practical exercise
Design a tool schema (name, description, parameters) for a hypothetical get_stock_price(ticker) function precise enough that a model could reliably produce valid arguments for "what's Apple's stock price?"

Streaming responses

Simple explanation

Streaming means the API sends the response back incrementally, token by token (or in small chunks), as it's generated — instead of making you wait for the entire response to finish before you get anything back.

Technical explanation

Typically implemented via a persistent connection (Server-Sent Events or a chunked HTTP response), where the server emits each newly generated token as soon as it's produced by the autoregressive loop, rather than buffering the full output server-side first. This doesn't make total generation faster — it just delivers each piece as soon as it exists, dramatically improving PERCEIVED latency.

non-streaming
…silence… → full response, all at once
streaming
token → token → token → token → …
Real-world example
Every major chat product's "typing" effect is literally the raw streaming API output, rendered incrementally in the UI as chunks arrive.
streaming.py
with client.messages.stream(
    model="claude-sonnet-4-6",
    max_tokens=500,
    messages=[{"role": "user", "content": "Write a short poem about backend engineering."}],
) as stream:
    for text_chunk in stream.text_stream:
        print(text_chunk, end="", flush=True)   # render each piece as it arrives
Backend developer analogy
Like the difference between an HTTP response that buffers an entire large file before sending anything, versus one that streams bytes as they're produced — same total transfer time, very different perceived responsiveness.
Common misconception
Streaming does not reduce the total time to generate a full response — the model still produces every token in sequence at the same underlying speed. Streaming only changes WHEN you start seeing partial results, not how fast generation as a whole completes.
Interview question
Why might you choose NOT to stream a response in some backend use cases, even though it improves perceived latency for chat UIs?
Show a strong answer
If you need to validate or post-process the FULL response before it's usable — e.g., parsing it as structured JSON, running it through a content filter, or needing the complete answer to make a downstream decision — partial chunks aren't useful to your caller anyway, and streaming just adds connection-management complexity without a real UX benefit for a non-interactive backend job.
Practical exercise
If you have API access, make the same request once with streaming enabled and once without, and compare time-to-first-visible-token versus total time-to-completion.

Multimodal models

Simple explanation

A multimodal model can take in and/or produce more than just text — images, audio, sometimes video — using largely the same underlying transformer architecture, by converting those other media types into token-like representations the model can process alongside text.

Technical explanation

A common approach: an image is chopped into patches, each embedded into a vector (via a vision encoder) that lives in a space compatible with the model's text token embeddings, and these image-patch "tokens" are interleaved with text tokens as input — attention then works across both image and text tokens uniformly. Many "multimodal" chat LLMs today are input-multimodal but text-output only; a few can also produce image or audio output.

Real-world example
Uploading a screenshot of an error and asking an LLM to explain it; a model describing a photo; voice assistants processing raw audio directly instead of requiring a separate speech-to-text step first.
Backend developer analogy
Like extending a well-typed API to accept a new payload type by first normalizing it into the same internal representation your existing pipeline already knows how to process, rather than building an entirely separate pipeline per media type.
Common misconception
A model being "multimodal" doesn't mean every modality is equally strong. Image/audio understanding often lags text precision — for example, exact counting of small objects in a photo, or reading fine print, are common weak spots even in strong multimodal models.
Interview question
At a high level, how does a transformer originally designed for text tokens end up able to process an image as input?
Show a strong answer
The image is never processed "as pixels" by the transformer itself. A separate vision encoder first converts image patches into dense vectors living in the same representational space as the model's text embeddings. Once in that shared vector space, the transformer's self-attention mechanism treats them like any other sequence position — it doesn't need to "know" one came from a pixel grid rather than a word.
Practical exercise
Upload a photo to a multimodal LLM and ask it to count a specific small object in the image. Check the answer against reality and note whether it's reliable.

Text generation vs embeddings

Simple explanation

Text-generation models and embedding models are trained for fundamentally different jobs — one produces new text, the other produces a fixed-size numeric fingerprint of meaning — and picking the right one for the right job is a basic but important architectural decision in any GenAI system.

Technical explanation

A generative LLM's output is a sequence of sampled tokens, produced autoregressively, variable length. An embedding model's output is typically a single fixed-length vector (384, 768, 1536+ dimensions) representing the whole input, optimized so semantic similarity between inputs corresponds to geometric closeness between their vectors — usually a single forward pass, no autoregressive generation involved.

Embedding model
  • Input: text
  • Output: one fixed-length vector
  • Used for: search, clustering, dedup
  • Cost: cheap, single pass
Generative model
  • Input: text
  • Output: new text, one token at a time
  • Used for: composing answers, writing, reasoning
  • Cost: scales with output length
Real-world example
A RAG pipeline uses a cheap embedding model to index and retrieve documents, and a separate, larger generative model to actually compose the final answer from the retrieved context — mixing the two roles into one model is possible but usually not the most cost-efficient split.
Backend developer analogy
Like the difference between a database index (a fast lookup structure that doesn't "answer" anything by itself) and a query engine that actually composes a result — embeddings are the index; the generative model is the query engine producing the final response.
Common misconception
A bigger, more capable generative LLM is not automatically a better embedding model, and vice versa — they're trained with different objectives. Using a chat LLM's internal hidden states as makeshift embeddings usually performs worse than a model actually trained end-to-end for retrieval quality.
Interview question
In a RAG system, why do you typically use a separate embedding model rather than using your main chat LLM to "embed" documents?
Show a strong answer
Embedding quality for retrieval depends on a training objective specifically shaped around semantic similarity — pulling related texts close together and unrelated ones apart in vector space. A generative chat model was never optimized for that geometry; it was optimized to produce plausible next tokens. A dedicated embedding model is both cheaper per call and more effective for retrieval than repurposing a generative model's internals.
Practical exercise
Look up the embedding dimensionality of a real embedding model, and work out the storage cost of embedding 1 million document chunks at that dimensionality.

Open-source vs proprietary LLMs

Simple explanation

Proprietary LLMs (GPT, Claude, Gemini) are accessed only through a provider's hosted API — you never receive the model weights. Open-weight LLMs (Llama, Mistral, and others) let you download the actual trained weights and run them yourself, on your own infrastructure or a cloud provider of your choosing.

Technical explanation

"Open-source" here is often more precisely "open-weight" — the trained parameters are released, but the training code, exact dataset, and full training recipe may or may not also be open (a genuine spectrum, not a binary). Licenses vary widely, from permissive to usage-restricted. Running an open-weight model yourself means you take on the infra burden — GPUs, serving stack, scaling, security patching — that a hosted API otherwise abstracts away entirely.

Proprietary API
  • No infra to manage
  • Often strongest frontier capability
  • Pay per token
  • Data typically leaves your infra
Open-weight, self-hosted
  • You manage serving/scaling/ops
  • Capability varies by model choice
  • Cost shifts to compute + ops
  • Full data control is possible
Real-world example
A team with strict data-residency or compliance requirements might self-host an open-weight model specifically to guarantee no data leaves their infrastructure, accepting the added operational burden as the price of that control.
Backend developer analogy
Similar to choosing a managed cloud database service (proprietary, zero infra ownership, pay-per-use) versus self-hosting an open-source database on your own servers (full control, but you own patching, scaling, and uptime).
Common misconception
"Open-source" doesn't automatically mean "worse." Some open-weight models are highly competitive with proprietary models on many tasks — the right choice depends far more on your specific constraints (compliance, cost at scale, customizability) than a blanket capability ranking.
Interview question
What's a concrete business reason a company might choose a lower-benchmark open-weight model over a stronger proprietary API model?
Show a strong answer
Data residency/compliance requirements that forbid sending certain data to a third-party API; extremely high request volume where self-hosted inference cost undercuts per-token API pricing at scale; or needing deep customization (fine-tuning, custom serving optimizations) that a closed API doesn't expose. Any of these can outweigh a modest gap in general benchmark performance for the specific task at hand.
Practical exercise
List 3 factors, beyond raw benchmark scores, you'd weigh when choosing between a proprietary API and self-hosting an open-weight model for a new product feature.

Major model families

Simple explanation

A handful of model families dominate current GenAI engineering — GPT (OpenAI), Claude (Anthropic), Gemini (Google), and Llama (Meta) among others — each with its own API conventions, strengths, and tooling ecosystem, though they all share the same fundamental transformer-based, next-token-prediction foundation covered throughout this workbook.

Technical explanation

What actually differs day to day for an engineer: API shape and conventions (message formats and tool-calling syntax details vary slightly across providers), context window sizes, pricing, latency/throughput characteristics, and specific strengths from each provider's training and tuning choices — not some fundamentally different underlying technology. Conceptually, everything covered in this workbook (tokenization, attention, sampling, context windows) applies across all of them.

An engineer picking a model for a new feature typically benchmarks a couple of candidate models on their SPECIFIC task and data, rather than relying purely on general leaderboard rankings, since relative strengths shift by task and change often as providers release new versions.
Backend developer analogy
Similar to choosing between major cloud providers for a new backend service — broadly comparable core capability, but real differences in specific offerings, pricing structure, and ecosystem fit that matter enormously for a given use case.

LLMs in context

Why can't an LLM simply search the internet?

A raw LLM has no built-in internet access. It's a static, frozen set of weights produced once during training — no network connection, no live browsing capability baked into the model itself. It cannot fetch anything, ever, on its own.

Any "search" or "browsing" capability you see in a product is an external TOOL bolted on via function calling, covered earlier: the model requests a search by emitting a structured tool call, an external system actually executes the HTTP request or search API call, and the results come back as text that gets placed in the model's context — which it then reads and synthesizes exactly like any other retrieved content. Remove that tool integration, and a raw model API call has zero ability to fetch anything live; it can only draw on statistical patterns learned up to its training cutoff.

base model alone
Frozen weights → training-cutoff knowledge only
model + search tool
Frozen weights + live external call + synthesis of results

It doesn't even make architectural sense to build "live access" directly into a model's weights — the model doesn't run a browser; it runs one fixed mathematical function computed the same way every time. Search-as-a-tool is the only sensible way to combine static weights with live data, and it uses the exact same tool-calling mechanism as any other tool the model might call.

The most common interview trip-up on this topic
Saying "the model searches the web" instead of "the orchestration layer searches the web and feeds text back into the model's context." The distinction matters: it's your application code's responsibility to call the search API, handle failures, and decide what to feed back — the model never reaches out anywhere on its own.

LLM vs traditional software

You already know how to reason about traditional backend systems. Here's the dimension-by-dimension contrast that determines how much of that intuition transfers — and where it actively misleads you.

DimensionTraditional softwareLLM
Control flowExplicit, written by a developerLearned, emergent from training
Behavior sourceSource code you can readBillions of opaque numeric weights
Same input twiceSame output, always (bugs included)Can vary — probabilistic by design
TestingExact-match unit/integration testsStatistical/semantic evaluation, sampled

LLM vs search engine

These get conflated constantly, but they solve fundamentally different problems.

DimensionSearch engineLLM

Where they combine, powerfully: a RAG system uses a search-like retrieval step to find real, current, traceable documents, then hands them to an LLM to synthesize into a natural-language answer — getting a search engine's grounding together with an LLM's synthesis and conversational ability. LLM vs database

This is the comparison with the highest real-world stakes, because getting it wrong in production means shipping a feature that quietly returns wrong account balances or invented inventory counts with total confidence.

DimensionDatabaseLLM
StorageExact, structured, queryable recordsCompressed, lossy statistical patterns in weights
Retrieval guaranteeExact match, every time (ACID)No retrieval guarantee at all — no "rows," no query
AuditabilityFull — you can point to the exact stored rowNone — you cannot point to "where" a fact is stored
Updating one factA single UPDATE statementNot possible without retraining/fine-tuning the whole model
PrecisionExact, by designApproximate, by design
The rule this leads to
Never treat an LLM as a system of record. If you need exact, auditable, guaranteed-correct data retrieval — account balances, inventory counts, user records — that data MUST live in a real database. The LLM's role is to read data given to it in context and reason or communicate about it, never to "remember" it authoritatively on your behalf.

RAG vs LLM knowledge

This is the distinction that separates "I can call an LLM API" from "I can design a real GenAI system" — the two sources a model draws on when answering are fundamentally different, and knowing which one is in play changes almost every design decision.

DimensionParametric knowledge (baked into weights)RAG (retrieved at query time)
Where it livesCompressed into billions of trained weightsAn external, updatable knowledge base (documents, vector DB)
FreshnessFrozen at the training cutoffAs current as your knowledge base
Updating itRequires retraining/fine-tuning — slow, expensiveUpdate the knowledge base — instant, cheap
TraceabilityNone — you can't cite "where" it learned a factFull — you can cite the exact retrieved document/chunk
ScopeEverything it was ever trained on, diffuselyOnly what's actually relevant to THIS query, via retrieval

Practical guidance: lean on parametric knowledge for general language ability, broad reasoning, and widely-known world knowledge. Lean on RAG for anything specific, current, proprietary, or that needs to be cited and audited. Almost every serious production GenAI system relies on BOTH simultaneously — the model's general capability to understand and communicate, plus retrieved, current, specific grounding for anything that actually needs to be correct and traceable.
